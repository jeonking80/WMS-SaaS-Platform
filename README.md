# WMS Lite

### 고객사별 물류·창고 운영관리 SaaS

여러 회사가 하나의 웹서비스를 이용하면서 각자의 품목·창고·입출고·재고·작업이력을 독립적으로 관리하는 물류 운영 시스템입니다.

AI 개발도구를 활용한 1인 기획·개발 프로젝트로, 단순한 재고 조회 화면을 넘어 **고객사 데이터 격리, 재고 정합성, 작업 이력 추적**을 구현하는 것을 목표로 합니다.

> **현재 상태:** 6단계 조회·대시보드 구현 — 기준정보, 입출고·이동·확정 취소, 검색·페이지 처리, 확정 이력·감사 조회, 서울 기준 운영 집계를 제공합니다.
>
> 로컬 검증 결과와 성능 측정은 [6단계 검증 결과](docs/6단계-검증결과.md), [6단계 성능 측정](docs/6단계-성능측정.md)에 기록합니다. 외부 배포는 이후 단계입니다.

## 1. 프로젝트 목적

물류 업무를 분석하여 웹 UI, 백엔드 API, 데이터베이스로 구체화하고, 여러 고객사가 이용할 수 있는 SaaS 형태로 구축합니다.

| 핵심 목표 | 구현할 내용 |
|---|---|
| 물류 업무 시스템화 | 입고·출고·보관위치 이동·재고 조회 |
| 고객사별 데이터 격리 | 회사별 계정·역할·데이터 접근 제어 |
| 재고 정합성 | 중복 반영 방지, 동시 출고 제어, 트랜잭션 처리 |
| 변경 이력 추적 | 전표와 연결된 재고 원장 및 담당자 기록 |
| 개발 결과 검증 | 업무 규칙·DB·API·UI 자동화 테스트 |
| AI 기반 개발 | 작업 단위 구현, 검수, 테스트를 통한 단계별 개발 |

상용 WMS 전체를 구현하기보다, 핵심 물류 업무를 정확하게 처리하는 **웹 SaaS 프로토타입**을 완성하는 데 집중합니다.

## 2. 서비스 이용 흐름

```text
회사별 로그인
    ↓
품목·창고·보관위치 등록
    ↓
입고 전표 작성 및 확정
    ↓
재고 조회 / 창고 내부 이동
    ↓
출고 전표 작성 및 확정
    ↓
재고 변동 이력 / 운영 대시보드 확인
```

초기에는 가상의 고객사 A와 B를 구성합니다.

각 회사는 자신의 품목·창고·재고·전표만 관리할 수 있으며, 다른 회사의 데이터에는 접근할 수 없습니다.

### 사용자 역할

| 역할 | 허용 업무 |
|---|---|
| 관리자 | 기준정보 관리, 전표 작성·확정·확정 취소, 전체 이력 조회 |
| 작업자 | 입고·출고·이동 전표 작성 및 확정, 재고·작업이력 조회 |
| 조회자 | 재고·대시보드·확정된 작업이력 조회 |

초기 버전은 사용자당 하나의 소속 회사만 지원합니다. 회사와 계정은 초기 데이터 생성 절차로 제공하며, 공개 회원가입과 초대 기능은 제외합니다.

## 3. 핵심 기능

| 기능 | 개발 범위 |
|---|---|
| 로그인·권한 | 세션 인증, 소속 회사 확인, 역할별 접근 제어 |
| 품목 관리 | 품목코드·품목명·최소재고 기준·사용 여부 |
| 창고·보관위치 관리 | 창고 및 창고 내부 보관위치 등록·관리 |
| 입고 관리 | 전표 작성·수정·취소, 확정 시 재고 증가 |
| 출고 관리 | 전표 작성·수정·취소, 재고 검증 후 확정 |
| 내부 이동 | 동일 창고 내 위치 간 재고 이동 |
| 확정 취소 | 원본 전표와 연결된 반대 거래 생성 |
| 재고 조회 | 품목·창고·보관위치별 현재고 검색 |
| 이력 조회 | 재고 변동, 담당자, 처리 시각, 원본·취소 관계 |
| 대시보드 | 입출고 현황, 출고 대기, 부족 재고, 최근 작업 |

### 초기 업무 범위

- 수량은 개 단위의 양의 정수로 입력합니다.
- 전표 하나는 하나의 창고를 대상으로 합니다.
- 입고·출고 전표는 하나의 보관위치와 여러 품목을 지원합니다.
- 이동 전표는 동일 창고의 출발 위치와 도착 위치를 지정합니다.
- 전표당 품목은 최대 20개로 제한합니다.
- 출고 예약은 하지 않으며, 확정 시점의 현재고로 처리 가능 여부를 판단합니다.
- 부분 확정·부분 취소는 지원하지 않습니다.

## 4. 핵심 업무 규칙

### 4.1 전표 상태

```text
DRAFT ── 확정 ──▶ POSTED ── 확정 취소 ──▶ REVERSED
  │
  └── 초안 취소 ──▶ CANCELLED
```

| 상태 | 의미 |
|---|---|
| `DRAFT` | 작성 중인 전표. 재고에 반영되지 않음 |
| `POSTED` | 확정되어 재고 반영이 완료된 전표 |
| `CANCELLED` | 재고 반영 전에 취소한 전표 |
| `REVERSED` | 반대 거래를 생성해 확정 취소한 전표 |

확정된 전표의 품목·수량·위치는 수정하지 않습니다. 취소된 전표는 재확정하지 않고 새 전표를 작성합니다.

### 4.2 재고 원장과 현재고

```text
현재고 = 해당 회사·품목·보관위치의 재고 원장 증감 합계
```

- 재고는 입고·출고·이동·확정 취소를 통해서만 변경합니다.
- 초기 재고도 입고 전표로 생성합니다.
- 현재고를 직접 덮어쓰는 기능은 제공하지 않습니다.
- 현재고와 원장 합계가 일치하는지 검증합니다.
- 확정 취소는 기존 기록 삭제가 아닌 반대 거래로 처리합니다.
- 취소로 재고가 음수가 되는 경우에는 취소를 거절합니다.

### 4.3 중복·동시성 처리

동일 전표를 반복 확정하거나 응답 유실 후 재요청하더라도 재고에는 한 번만 반영합니다.

동시에 여러 출고가 요청되면 DB 트랜잭션 안에서 재고를 다시 확인하고, 재고가 부족한 요청은 거절합니다.

여러 품목을 처리하는 전표에서 하나라도 검증에 실패하면 전체 작업을 취소합니다. 위치 이동의 출발지 차감과 도착지 증가도 함께 성공하거나 함께 취소되어야 합니다.

## 5. 시스템 구조

```text
웹 브라우저
    ↓
Next.js / React UI
    ↓
백엔드 API
 ├─ 인증 및 소속 회사 확인
 ├─ 역할·대상 데이터 권한 검사
 └─ 입력 검증
    ↓
업무 서비스
 ├─ 기준정보 관리
 ├─ 전표 작성·확정·취소
 ├─ 재고 처리
 └─ 조회·집계
    ↓
PostgreSQL
 ├─ 고객사별 업무 데이터
 ├─ 현재고
 ├─ 재고 변동 원장
 └─ 작업 이력
```

하나의 애플리케이션과 하나의 PostgreSQL 데이터베이스로 시작합니다.

인증, 업무 로직, 데이터 접근의 책임은 코드 안에서 분리하되, 초기에는 별도 마이크로서비스나 메시지 브로커를 도입하지 않습니다.

### 기술스택 계획

| 영역 | 기술 |
|---|---|
| Frontend | Next.js, React, TypeScript, Tailwind CSS |
| Backend | Node.js, Next.js Route Handlers |
| Database | PostgreSQL |
| 데이터 접근 | `pg`, SQL, 버전 관리형 마이그레이션 |
| 인증 | 인증 라이브러리를 활용한 세션 인증 |
| 테스트 | 단위 테스트, PostgreSQL 통합 테스트, Playwright |
| 로컬 환경 | Docker Compose 기반 PostgreSQL |
| 자동 검증 | 로컬 `npm run verify` (GitHub Actions 사용 금지) |
| 개발 방식 | AI 코딩 에이전트 활용 |
| 데모 배포 | 기존 프로젝트와 분리된 환경, 배포 대상 추후 확정 |

0단계의 런타임·직접 의존성 버전은 `.nvmrc`, `package.json`에, 전이 의존성은 `package-lock.json`에 고정했습니다. 선택 근거는 [기술 결정](docs/기술결정.md)에 기록합니다.

## 6. 데이터 설계 방향

### 주요 데이터 모델

| 모델 | 역할 |
|---|---|
| `tenants` | 서비스 이용 회사 |
| 인증 관련 테이블 | 사용자 계정·세션 |
| `memberships` | 사용자 소속 회사·역할 |
| `items` | 품목 |
| `warehouses` | 창고 |
| `locations` | 창고 내부 보관위치 |
| `inventory_documents` | 입고·출고·이동 전표 |
| `inventory_document_lines` | 전표별 품목·수량 |
| `stock_balances` | 회사·위치·품목별 현재고 |
| `stock_ledger` | 재고 변동 원장 |
| `idempotency_requests` | 중복 요청 식별 및 처리 결과 |
| `audit_logs` | 주요 업무 처리 이력 |

상세 컬럼과 관계는 [DB 설계](docs/DB-설계.md)에 기록합니다.

### 설계 원칙

- 업무 데이터에는 `tenant_id`를 포함합니다.
- 회사 ID는 로그인한 사용자의 소속을 기준으로 서버에서 결정합니다.
- 회사 간 잘못된 데이터 연결은 복합 외래키 등 DB 제약으로도 차단합니다.
- PostgreSQL RLS를 사용하고 애플리케이션 계정과 마이그레이션 계정을 분리합니다.
- 현재고는 0 미만이 될 수 없도록 제한합니다.
- 재고 원장은 일반 애플리케이션 권한으로 수정·삭제하지 않습니다.
- 전표·원장·현재고·요청 처리 결과를 하나의 트랜잭션으로 반영합니다.
- 목록뿐 아니라 상세 조회·수정·확정·집계에도 회사별 권한을 적용합니다.

## 7. 완료 검증 기준

| 검증 시나리오 | 기대 결과 |
|---|---|
| 입고 100개 확정 | 현재고 100개 |
| 같은 입고 확정 요청 재전송 | 현재고 100개 유지 |
| 재고 100개에서 출고 30개 | 현재고 70개 |
| 재고 100개에서 출고 80개 두 건 동시 실행 | 한 건만 성공, 최종 20개 |
| 여러 품목 중 하나가 재고 부족 | 전표 전체 미반영 |
| 위치 A에서 B로 20개 이동 | A -20, B +20, 전체 수량 동일 |
| 확정 처리 중 DB 오류 | 부분 반영 없이 롤백 |
| 커밋 후 응답 유실 및 재요청 | 기존 결과 반환, 추가 반영 없음 |
| A 회사 계정으로 B 회사 데이터 접근 | 조회·변경 차단 |
| 조회자가 확정 API 호출 | 변경 차단 |
| 재고 부족 상태에서 입고 취소 | 취소 거절, 기존 재고 유지 |
| 오래된 전표 버전으로 수정·확정 | 충돌 안내, 덮어쓰기 방지 |
| 원장 합계와 현재고 대조 | 모든 대상에서 일치 |

업무 규칙은 단위 테스트로, 트랜잭션·동시성·데이터 격리는 실제 PostgreSQL 통합 테스트로 검증합니다.

사용자의 로그인부터 전표 확정·재고 조회까지의 흐름은 E2E 테스트로 확인합니다.

3. 결과와 테스트를 확인한 후 다음 작업을 진행합니다.
4. 기존 변경을 덮어쓰거나 요청과 무관한 기능을 추가하지 않습니다.
5. 코드 생성·컴파일 성공과 업무 검증 완료를 구분합니다.
6. 커밋·배포·DB 변경은 승인된 환경과 범위에서만 수행합니다.

## 9. 제외 범위와 선택 확장

### 1차 제외 범위

ERP·쇼핑몰·택배사 연동, 실제 바코드 장비·PLC 연결, LOT·시리얼·유통기한, 재고 예약, 부분 출고, 창고 간 운송, 생산관리·BOM, 회계·정산, 구독 결제, 3D 창고, 수요 예측은 포함하지 않습니다.

### 선택 확장: AI 물류 조회 도우미

핵심 WMS가 완성된 이후, 자연어 질문을 읽기 전용 조회 API와 연결하는 기능을 검토합니다.

예시 질문:

- 현재 재고가 부족한 품목은?
- 특정 품목의 재고가 오늘 감소한 이력은?
- 아직 확정하지 않은 출고 전표는?

AI에는 허용된 조회 도구만 제공하며, 임의 SQL 실행이나 재고 변경·출고 확정 권한은 부여하지 않습니다.

이 기능은 1차 프로젝트 완료 조건에 포함하지 않습니다.

## 10. 실행 및 데모

### 개발 실행

Node.js 24.19.0, npm 11.9.0, Docker와 Docker Compose가 필요합니다. 저장소 루트에서 실행합니다.

```sh
npm ci
npm run env:init
docker compose --env-file .env.local --profile test up -d --wait
npm run db:setup
npm run db:check
npm run dev
```

`env:init`은 로컬 DB 계정별 난수 암호, 인증 시크릿, 데모 비밀번호를 `.env.local`에 생성합니다. 기존 파일은 덮어쓰지 않습니다. 직접 설정하려면 `.env.example`을 참고합니다. DB의 기본 포트는 개발 5432, 테스트 5433이며, 포트를 바꾸면 `.env.local`의 포트와 연결 URL을 함께 변경합니다. 영속 볼륨이 이미 생성된 후에는 `POSTGRES_PASSWORD`만 바꿔 초기 관리자 암호를 변경할 수 없습니다.

0단계에서 생성한 `.env.local`이 있다면 서버를 중지하고 먼저 `npm run env:init -- --upgrade`를 실행합니다. 변경하지 않은 로컬 P0 설정만 자동 변환하고 원본은 Git에서 제외된 `.env.local.p0-backup`에 보존합니다. 사용자 설정이 다르면 덮어쓰지 않고 중단하므로 `.env.example`을 기준으로 직접 조정합니다. 이후 `npm run db:setup`을 실행합니다.

`db:setup`은 관리자 연결로 앱·마이그레이션 역할을 준비하고, 마이그레이션 적용 후 앱 권한을 제한하여 부여하고, 합성 회사·계정을 생성합니다. 역할·스키마를 변경하므로 서버를 시작하기 전에 실행합니다. 앱은 `DATABASE_URL`의 `wms_app`, 마이그레이션·시드는 `MIGRATION_DATABASE_URL`의 `wms_migrator`, 역할 준비는 `BOOTSTRAP_DATABASE_URL`을 사용합니다. 관리용 연결을 앱 실행에 사용하지 않습니다.

개발 서버 기본 포트는 3000입니다. `/`는 초기 화면, `/api/health`는 앱 응답, `/api/ready`는 DB 연결과 최초 테이블 조회를 확인합니다. DB가 준비되지 않으면 readiness는 503을 반환합니다.

개발 시드는 합성 회사 A/B와 아래 계정만 생성하며 재고는 만들지 않습니다. 마이그레이션과 시드는 반복 실행할 수 있고 기존 계정의 비밀번호·역할을 덮어쓰지 않습니다.

| 역할 | A 회사 | B 회사 |
|---|---|---|
| 관리자 | `admin.a@example.test` | `admin.b@example.test` |
| 작업자 | `worker.a@example.test` | `worker.b@example.test` |
| 조회자 | `viewer.a@example.test` | `viewer.b@example.test` |

`/login`에서 로그인합니다. 비밀번호는 초기 생성 때의 `.env.local` 내 `DEMO_PASSWORD`이며 저장소나 채팅에 공개하지 않습니다. 이 계정은 독립 로컬·테스트 환경용입니다. 공개 회원가입은 제공하지 않습니다. 초기 생성 후 `DEMO_PASSWORD`만 바꾸어도 기존 계정 비밀번호는 변경되지 않습니다.

### 검증 실행

위 DB 준비를 마친 뒤 실행합니다. 통합 테스트는 DB 이름이 `_test`로 끝나는 `TEST_DATABASE_URL`만 허용합니다.

```sh
npm run typecheck
npm run test:unit
npm run test:integration
npm run build
npx playwright install --with-deps chromium
npm run test:e2e
```

Playwright는 프로덕션 서버를 포트 3100에서 자동 실행하고 종료합니다. 빌드 후 실행해야 하며, 패키지 설치와 테스트를 동시에 실행하지 않습니다. 이 클라우드처럼 브라우저 다운로드가 제한되고 시스템 Chromium이 설치되어 있다면 설치 명령 대신 다음으로 실행할 수 있습니다.

```sh
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e
```

설치된 브라우저 경로는 환경에 맞게 지정합니다. GitHub Actions는 사용하지 않습니다. npm 기본 캐시 경로에 쓰기 권한이 없는 클라우드에서는 `npm --cache /workspace/.npm-cache ci`를 사용합니다.

### 현재 제공 범위

로그인·로그아웃과 회사·역할을 표시하는 업무 화면을 제공합니다. `/dashboard/master`에서 품목·창고·로케이션을 관리하고, `/dashboard/documents`에서 입고·출고·이동 초안을 작성·수정·취소할 수 있습니다. 기준정보 변경은 관리자만, 조회와 초안 작업은 관리자·작업자만 가능합니다. 조회자는 초안에 접근할 수 없습니다. 입고·출고·같은 창고 내 이동 확정과 `/dashboard/stock`의 현재고·원장·수량 대조를 제공합니다. 출고·이동 초안에는 참고 재고를 표시하고 확정 시 잔량을 다시 검사합니다. 관리자는 확정 취소로 반대 전표를 생성할 수 있으며 원본과 반대 전표를 연결하여 조회합니다.

6단계에서는 `/dashboard`의 실제 운영 집계, `/dashboard/history`의 모든 역할용 읽기 전용 확정 이력, `/dashboard/audit`의 관리자 감사 기록을 제공합니다. 조회자는 `/dashboard/documents`의 초안 관리 화면에 접근할 수 없습니다. 전표·현재고·원장·감사 목록은 검색·필터와 기본 25개 페이지 처리를 지원하며 API 최대 페이지 크기는 100개입니다. 품목 최소재고는 관리자가 0~1,000,000,000 정수로 설정합니다. 창고·위치 조회 선택지는 회사별 각 1,000개로 제한합니다.

구현·검증 범위는 [6단계 검증 결과](docs/6단계-검증결과.md), 측정 조건과 결과는 [6단계 성능 측정](docs/6단계-성능측정.md), 요청 계약은 [API 명세](docs/API-명세.md)를 확인하세요.

프로덕션 빌드 실행은 `npm run build` 후 `npm run start`로 확인합니다. 외부 배포의 `BETTER_AUTH_URL`은 HTTPS여야 합니다. 로컬 빌드 검증에만 loopback HTTP를 허용합니다. E2E는 자체 서버에 맞춰 인증 주소를 포트 3100으로 덮어씁니다. 인증의 요청 제한은 유지하며 테스트는 429 응답의 대기 시간을 지킨 뒤 재시도합니다.

DB만 중지하려면 `docker compose --env-file .env.local --profile test stop`을 사용합니다. 개발 DB 볼륨을 지우는 명령은 일상 실행 절차에 포함하지 않습니다.

로컬·테스트·데모 환경은 다른 프로젝트의 운영 DB와 분리합니다. 실제 고객정보 대신 합성 데이터를 사용하며, 비밀번호·API 키·DB 접속정보는 저장소에 커밋하지 않습니다.

## 프로젝트 성공 기준

**여러 회사가 서로의 데이터를 볼 수 없고, 재고가 정확하게 반영되며, 모든 재고 변경의 원인을 전표와 이력으로 추적할 수 있어야 합니다.**

화면의 개수보다 업무 규칙의 정확성, 재현 가능한 검증, 설명 가능한 시스템 구조를 우선합니다.

## 로컬 검증 정책

2026-10-20부터 GitHub Actions 워크플로를 제거하고 로컬 검증만 사용합니다. 개발 서버를 중지하고 DB 준비 후 `npm run verify`를 실행합니다. 현재 클라우드에서는 `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run verify`를 사용합니다. 이 명령은 타입·단위·DB 통합·빌드·브라우저 검사를 순서대로 수행하고 실패하면 중단합니다.

성능 측정은 일반 검증 체인과 분리하여 `npm run test:performance`로 실행합니다. 로컬 `wms_lite` DB에 전용 합성 회사를 만들고 측정 후 제거하며, 목표 시간과 실측 결과를 구분합니다. 프로덕션 빌드 후 다른 검증과 동시에 실행하지 않습니다. 측정 환경·구간·반복 횟수는 [6단계 성능 측정](docs/6단계-성능측정.md)을 참고합니다.
