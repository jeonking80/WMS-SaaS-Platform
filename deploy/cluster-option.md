# Optional two-process Docker web mode

The candidate is applied to working source. Local application verification with `WMS_STANDALONE=1` passed; the later external supervisor follow-up and focused checks are recorded below. Production adoption and measured throughput benefit remain unestablished. Bounded Docker packaging checks are recorded below. The existing Docker CMD remains `node server.js`; Vercel remains unchanged. Optional Compose overlay `compose.cluster.yaml` selects the standard-library Node cluster launcher, with one primary and two standalone workers on the same port. No HAProxy, new Node dependency, header hop, request replay or source/client rate change is introduced.

The primary imports no application/database code. cluster.fork merges overrides onto the real process environment, so forbidden inherited flags are overridden with explicit undefined values rather than merely deleted. A real child-environment fixture asserts those flags are absent. Worker count is explicitly one or two; pool partitions are exactly five or three plus two. Authentication, readiness and telemetry share each worker's existing pool. Do not supply a parent WMS_DB_POOL_MAX override to the launcher. Startup rejects operations credentials and unsafe inherited Node preload/debug flags, clears inherited Next private/development startup flags, and runs the same generated standalone server.js as each worker's exec. Default standalone ESM/CommonJS handling remains Next's responsibility.

This does not increase the total host budget. Provision one parent cgroup with CPUQuota=400% and MemoryMax=32G (systemd cgroup driver example: wms.slice), and put the DB, web primary/children, background worker, existing local TLS proxy and diagnostic client in that parent. The overlay requires its reviewed name via WMS_CGROUP_PARENT; it does not create or raise cgroup limits. Verify effective ancestor limits and total memory/CPU/throttling before comparison. Do not give each component a separate four-core allowance. The two heaps and framework caches consume the same combined 32-GiB budget.

The shared listener uses explicit SCHED_RR: this balances new TCP connections, not individual HTTP requests. Keepalive can pin a busy client's traffic to one worker; no tenant-affinity rule or client connection changes are allowed to make a benchmark pass. Measure per-PID CPU, event-loop delay, RSS, requests and pool pressure along with aggregate cgroup values.

Readiness is 503 until both current workers are listening and have successfully queried the existing schema/readiness checks within 45 seconds. Reports use a namespaced IPC protocol, never business payloads. The optional health helper makes fresh connections to sample workers. A missing/disconnected/unhealthy worker makes aggregate readiness degraded while the supervisor replaces exited workers. Docker health status alone does not remove traffic or restart an unhealthy-but-live process; the existing deployment edge must respect readiness, and liveness versus saturation must be reviewed. No automatic CPU-stall kill is added.

A worker is replaced only after exit, retaining that slot's pool allocation. Restart delays grow from 250ms to a maximum five seconds; more than five failures per minute stops the cluster. On SIGTERM/SIGINT, the primary sets stopping first and cancels replacement timers, then requests a drain over namespaced IPC. A fixed preload initializes a per-process global lifecycle state before Next starts. Every API wrapper, including direct authentication endpoints, holds its complete original handler/telemetry Promise in the active count even after the client disconnects. Missing managed preload fails closed. New API work during drain returns503 with a fresh server-generated x-request-id and a fixed-label minimal rejection record that contains no auth/request/body data; nested authentication belonging to a live admitted operation is allowed to finish through an expiring per-operation ALS token. Each child is counted independently, including unawaited tracked children; a detached descendant cannot reuse a settled parent token to bypass drain. Server-rendered requireIdentity calls are tracked separately without an API logging wrapper; unavailable new lookups throw a distinct unavailable error rather than turn into a login redirect, and unmanaged behavior remains unchanged. The primary sends SIGTERM only after the corresponding worker acknowledges zero active operations. There is no shutdown respawn. Next's existing production server.close waits for ordinary requests. A 60-second supervisor bound then forces remaining workers to exit, and the optional container stop grace is 90 seconds. A forced stop can leave HTTP outcome uncertain: PostgreSQL commits or rolls back atomically, accepted queue rows remain durable and transaction advisory locks release. Never automatically resend POSTs; resolve original request/event identities. The lifecycle barrier intentionally does not infer completion from socket counts. Current APIs materialize JSON/CSV before handler completion; any future stream that performs deferred database work needs its own tracked completion. Ordinary SSR response streaming still relies on Next's close behavior after the tracked authentication work; real Next validation of both ordinary and disconnected cases remains mandatory.

Use the exact same image/build, public origin, auth secret, cookies and existing TLS/header-trust policy for both workers. Business state, live role checks, sessions, idle-lock state and rate limits remain database-backed; preserve RLS and existing advisory/header/entity locking. Authenticated data must remain private and dynamic. Framework cache/tag coordination and deployment version skew still require review; no new business-state cache is introduced. Avoid overlapping a third live worker during replacement, which would violate the configured aggregate pool cap. Cold process death may leave server-side connections briefly cleaning up; confirm the actual cap and error behavior during lifecycle validation.

Run the ordinary production image for the single-instance comparator, or optional cluster launcher with WMS_WEB_WORKERS=1 (pool five) when measuring the primary's overhead. The two-worker arm uses the same image, exact fixed workload, unchanged rates/timeouts/validation and aggregate PG cap five, under the same parent quota. No new integration worker or raised resources. The existing background worker short-batch delays are unchanged. Vercel's autoscaled function model cannot promise these two fixed workers or this parent-resource envelope; this is an optional Docker-host deployment mode only.

Independent static review preceded source application, including corrections for inherited environment leakage and expiring nested-operation drain tokens. Local unit/TCP fixtures and the current full verification do not replace real Next, PostgreSQL and image lifecycle gates. The TCP fixture checks shared-port operation, both allocations, worker replacement, no launcher replay after a received POST loses its connection, and an in-flight response during shutdown. It does not prove database transactions or Next authentication. Configured3+2 is not evidence that a dead worker's PostgreSQL backends have already disappeared before replacement; the absolute live-backend cap remains a separate real-PostgreSQL validation gate, and the250ms restart delay is not that proof.

Observe all bodies and telemetry rather than dropping checks.
