# 1단계 인증·회사 격리 검증 결과

검증일: 2026-10-19. 현재 클라우드 환경에서 실제 앱과 PostgreSQL로 검증했다. 공개 데모 배포·운영 검증을 의미하지 않는다.

## 구현한 기능

- Better Auth 로그인·로그아웃과 보호된 업무 홈, 회사·역할 표시
- `/api/me`에서 세션 사용자의 활성 소속과 역할 조회
- 회사 A/B × 관리자·작업자·조회자 6개 개발 계정과 반복 가능한 시드
- `wms_migrator` 소유자 계정과 `wms_app` 일반 앱 계정 분리
- 최초 회사업무 테이블 `items`에 FORCE RLS, 회사별 코드·복합 고유키·회사 참조 제약
- 트랜잭션에 한정된 회사 컨텍스트와 읽기 전용 품목 목록·상세 API
- 공개 가입 차단, 출처 검사, 요청 제한, 만료·폐기 세션 검사

## 검증 결과

| 검사 | 결과 | 근거 |
|---|---|---|
| P0 설정 업그레이드 | 통과 | 기존 로컬 관리자·테스트 DB 값 유지, 역할별 새 연결 및 인증값 생성, 원본을 무시되는 백업에 보존 |
| `npm run db:setup` 최초·반복 | 통과 | 기존 데이터 보존, 최초 신규 마이그레이션 2개 적용, 재실행 0개, 6개 계정 중복·재설정 없음 |
| `npm run db:check` | 통과 | 실제 wms_app은 테이블 비소유자·비슈퍼유저·RLS 우회권한 없음 |
| `npm run typecheck` | 통과 | 경로 타입 생성 및 전체 TypeScript 검사 |
| `npm run test:unit` | 18개 통과 | 앱 연결 권한, 세션·소속·역할 판단, 오류 응답 |
| `npm run test:integration` | 7개 통과 | 마이그레이션·인증 라이브러리 호환성과 실제 제한 계정 RLS |
| 프로덕션 빌드 | 통과 | 로그인·보호 화면·사용자·품목·상태 API 빌드 |
| 시스템 Chromium E2E | 14개 통과 | 브라우저 로그인 및 실제 앱 API 경계 검사 |

최종 자동 테스트는 **18 + 7 + 14 = 39개 통과**, 건너뜀 없음이다. RLS 테스트는 별도 테스트 DB의 임시 LOGIN 역할로 실행하고 실제 `withTenant` 코드와 최대 연결 수 1인 풀을 사용했다.

### 확인한 접근 경계

- 미인증 `/api/me`·품목 API는 401, 보호 화면은 로그인 화면으로 이동한다.
- 관리자·작업자·조회자로 로그인하면 회사명과 역할이 정확히 표시된다.
- 로그아웃과 세션 만료 후 사용자 API는 401을 반환한다.
- 로그인 후 DB 역할을 바꾸면 기존 쿠키를 가진 요청에도 즉시 반영된다.
- 조회자는 기준정보 품목 조회에서 403을 받는다. 관리자·작업자는 자사 품목을 조회한다.
- A 계정이 B 회사 ID를 쿼리·헤더로 지정해도 A의 목록만 반환한다. B의 품목 상세는 404다. B→A도 동일하게 차단된다.
- DB 회사 컨텍스트가 없으면 조회·수정·삭제 대상이 없고 삽입은 거절된다.
- 다른 회사로의 INSERT/UPDATE 위조, RLS 비활성화, 관리자 역할 전환, DDL·TRUNCATE가 거절된다.
- 동일 물리 연결에서 A/B 요청을 교대하고 커밋·롤백한 뒤에도 회사 컨텍스트가 다음 요청에 남지 않는다.
- 공개 가입과 신뢰하지 않는 origin을 차단한다. 로그인 요청 제한은 테스트에서도 유지한다.

## 발견한 문제와 해결

- 최초 브라우저 검사에서 Next.js 자체 알림과 로그인 오류가 모두 `role=alert`여서 테스트 선택자가 모호했다. 로그인 오류 문구로 대상을 좁혔다.
- 출처 차단 검사보다 요청 제한 429가 먼저 발생했다. 테스트가 `Retry-After`를 지킨 후 재시도하도록 수정했고, 제한·출처 검사 자체는 유지했다.
- `gpt-6.1-sol` 검토 에이전트가 기존 README의 `db:migrate`만으로는 신규 역할이 준비되지 않는 문제를 확인했다. 실제 실행 순서에 맞춰 `db:setup`과 P0 업그레이드·계정 안내를 반영했다.
- Next.js가 생성하는 `next-env.d.ts`는 실행 방식에 따라 경로가 변하므로 Git 추적에서 제외했다. 타입 검사는 `next typegen`으로 먼저 재생성한다.

## 범위와 남은 작업

현재 회사 격리의 실제 업무 대상은 품목 조회 API와 `items` 테이블이다. 아직 없는 창고·위치·전표·확정·재고·집계에 대한 격리까지 검증한 것으로 표현하지 않는다. 이들은 각 구현 단계에서 동일한 경계를 적용하고 테스트를 확장한다.

품목 등록·수정·비활성화 UI와 업무 API는 P2, 입출고·재고·동시성은 P3 이후다. 현재 로그인 후 화면은 회사·역할을 보여주는 업무 홈이며 운영 대시보드 집계는 아직 없다.

GitHub Actions 실행 결과 조회는 GitHub API의 Forbidden 응답으로 확인하지 못했다. 로컬에서 타입·테스트·빌드가 통과했으며 CI 설정에는 역할 준비와 인증 시드를 추가했다. Playwright 다운로드 제한 때문에 현재 클라우드 E2E는 설치된 Chromium을 사용했다.

환경 설정의 재설치·시작 지침은 P1 절차로 갱신했다. 초안 저장과 실제 환경 게시·새 작업 복원은 별개다. 데모 계정과 실행 방법은 [README](../README.md), 권한·RLS 구조는 [DB 설계](DB-설계.md)를 따른다.
