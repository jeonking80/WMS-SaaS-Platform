## 1. 목적과 현재 상태

기획서에 정의한 입고·출고·재고·창고 위치·작업이력 관리 기능을 구현 순서, 작업 단위, 산출물, 검증 기준으로 구체화한다. 핵심 완료 조건은 **고객사 데이터 격리, 정확한 재고 반영, 변경 원인 추적**이다.

계획서 최초 작성 시점에는 README와 기획서만 있었다. 아래 단계별 표는 최초 개발 계획이며, 실제 완료 여부는 진행 현황과 검증 결과로 구분한다.

**진행 현황 (2026-10-19):** 0단계의 앱·DB·마이그레이션·테스트·CI 기반 구성 및 현재 환경의 실행 검증을 완료했다. 단위 10개·DB 통합 2개·E2E 3개가 통과했다. 인증 라이브러리 호환성은 검증했으며, 앱의 인증·회사 격리 등 1단계 업무는 아직 구현 전이다. 상세 근거와 환경 제약은 [0단계 검증 결과](0단계-검증결과.md)에 기록한다.

**진행 갱신 (2026-10-20):** 6단계 전표·재고·원장·감사 검색과 페이지 처리, 읽기 전용 확정 이력, 대시보드·최소재고 설정과 확정 전 확인 화면을 구현했다. GitHub Actions 없이 로컬 `npm run verify`로 검증한다. 최종 근거는 [6단계 검증 결과](6단계-검증결과.md), 별도 `npm run test:performance`의 조건·결과는 [6단계 성능 측정](6단계-성능측정.md)에 기록한다. 배포는 7단계 범위다.

기획서의 업무 범위와 규칙을 기준으로 삼는다. 이 문서에서 추가한 구현 제안은 0단계에서 결정하고, 이후 변경이 필요하면 이유와 영향을 해당 설계 문서에 기록한다.

## 2. 1차 개발 범위와 고정 조건

| 구분 | 개발 내용 |
|---|---|
| 인증·권한 | 세션 로그인, 사용자당 회사 하나, 관리자·작업자·조회자 |
| 기준정보 | 품목·창고·보관위치 등록, 수정, 비활성화 |
| 작업 전표 | 입고·출고·동일 창고 내 이동의 작성, 수정, 초안 취소, 확정 |
| 확정 취소 | 관리자에 의한 전표 전체 취소, 원본과 연결된 반대 거래 생성 |
| 조회 | 회사·품목·창고·위치별 현재고, 원장, 작업이력, 대시보드 |
| 품질·배포 | 실제 PostgreSQL 통합 테스트, 브라우저 테스트, CI, 독립 데모, 복원 검증 |

회사와 계정은 초기 데이터 생성 절차로 제공하며, 공개 회원가입·초대·회사 전환 기능은 제외한다. 인증 라이브러리를 연결할 때도 공개 가입 경로가 노출되지 않도록 구성한다.

다음 조건은 모든 단계에서 유지한다.

- 전표 수량은 개 단위의 양의 정수이고, 전표당 품목은 최대 20개다.
- 전표 하나는 창고 하나를 대상으로 한다. 입출고는 위치 하나, 이동은 같은 창고의 출발·도착 위치를 사용한다.
- 초안 저장은 재고를 변경하지 않는다. 출고 가능 여부는 확정 시점의 현재고로 판단한다.
- 여러 품목은 모두 성공하거나 모두 실패한다. 부분 확정·부분 취소는 제공하지 않는다.
- 현재고는 0 미만이 될 수 없으며, 회사·위치·품목별 원장 증감 합계와 일치해야 한다.
- 확정된 원장은 수정·삭제하지 않는다. 초기 재고도 입고 전표로 생성한다.
- 회사는 인증된 사용자 소속에서 결정한다. 요청자가 보낸 회사 ID를 신뢰하지 않는다.

ERP·택배·장비 연동, 위탁물류, LOT·유통기한·시리얼·선입선출, 재고 예약, 부분 출고, 창고 간 운송, 생산·회계·결제는 1차에서 제외한다. AI 조회 도우미, 지도, 3D·디지털트윈, 예측 모델도 필수 일정에 포함하지 않는다.

## 3. 기술 구성과 착수 시 결정 사항

### 3.1 구현 방향

하나의 Next.js 애플리케이션과 하나의 PostgreSQL DB로 시작한다. Route Handler는 인증·권한·입력 검증과 응답 처리를 맡고, 업무 서비스는 재고 규칙과 트랜잭션을 담당한다. SQL과 연결 관리는 데이터 접근 계층으로 모은다.

| 영역 | 기준 또는 제안 | 확정 시점·확인 사항 |
|---|---|---|
| UI·API | Next.js App Router, React, TypeScript, Tailwind CSS, Route Handlers | 0단계: 지원 버전 및 호환성 확인 |
| 실행 환경 | 지원 중인 Node.js LTS, npm 사용 제안 | 0단계: Node 버전과 패키지 잠금 파일 고정 |
| 데이터 접근 | `pg` 기반 SQL, 버전 관리형 마이그레이션 | 0단계: 마이그레이션 도구 하나 선택, 빈 DB 적용 확인 |
| 인증 | 유지보수 중인 세션 인증 라이브러리 | 0단계: Next.js·PostgreSQL 연동, 계정 초기 생성, 로그인·로그아웃 지원 확인 |
| 테스트 | 단위·통합 테스트 도구로 Vitest 제안, E2E는 Playwright | 0단계: 실행 도구 구성, 1단계부터 업무 검증 추가 |
| 로컬 DB | Docker Compose 기반 PostgreSQL, 개발 DB와 테스트 DB 분리 | 0단계: 컨테이너 실행 가능 여부와 연결 확인 |
| 클라우드 개발 | 동일 PostgreSQL 버전과 스키마 사용 | 컨테이너 미지원 시 독립 PostgreSQL 서비스 또는 로컬 프로세스 사용 가능 여부 확인 |
| 자동 검증 | GitHub Actions | 0단계: 기본 CI 구성, 이후 기능별 검사 추가 |
| 데모 | 기존 프로젝트와 분리된 앱·DB | 0단계: 배포 방식·비용 제약 조사, 7단계: 배포 및 검증 |

구체적인 버전과 인증·마이그레이션 라이브러리는 이 문서에서 확정하지 않는다. 0단계에서 공식 지원 범위와 실제 실행 결과를 확인한 뒤 기록한다. 인증 서버·비밀번호 암호화·세션 토큰 체계를 직접 새로 만들지 않는다.

### 3.2 상세 설계 전에 정할 업무 규칙

아래는 기획서를 구현할 때 필요한 추가 결정이다. 제안은 확정 전 가정으로 관리한다.

| 결정 항목 | 기본 제안 | 완료 시점 |
|---|---|---|
| 날짜·시간 | 시각은 UTC로 저장하고, 데모의 일별 집계·표시는 `Asia/Seoul` 기준 사용. 날짜 범위는 시작 포함·종료 제외 | 0단계 |
| 조회자와 출고 대기 | 대시보드의 대기 건수는 제공하되 초안 목록·상세는 숨김. 조회자의 이력은 확정된 작업으로 제한 | 0단계 |
| 수량·코드 | 수량 상한과 DB 정수형 범위, 코드 길이·공백·대소문자 처리 결정. 동일 전표 내 동일 품목 중복은 거절하는 방식 제안 | 2단계 전 |
| 비활성 기준정보 | 과거 이력은 조회 가능. 신규 전표 선택과 일반 확정은 차단하고, 과거 확정 취소에 필요한 참조는 허용하는 방식 검토 | 2단계 전 |
| 비활성화 조건 | 잔량이 있는 위치 차단은 필수. 품목·창고 비활성화와 하위 위치·미확정 전표의 관계도 명시 | 2단계 전 |
| 확정 취소 모델 | 원본 상태는 `REVERSED`로 변경하고 별도 반대 전표·원장을 연결. 원본당 반대 전표는 하나만 허용 | 3단계 전 |
| 중복 요청 | 키 범위, 요청 해시 구성, 결과 보존 범위, 실패 후 재시도, 확정 취소 요청의 중복 처리 정책 결정 | 3단계 전 |
| 대시보드 집계 | 부족 재고는 활성 품목만, 잔량 없는 품목은 0으로 포함. 재고 보유 품목은 활성 여부 무관. 원본 확정 실적 유지·취소일 별도 집계 | 6단계 구현 |

인증용 계정·세션 조회는 회사 컨텍스트를 얻기 전에 필요하다. 이 인증 데이터 접근 경로와 회사업무 테이블의 RLS 경로를 분리하여, 회사 확인을 위해 RLS를 우회하는 일반 업무 쿼리가 생기지 않도록 설계한다.

## 4. 일정과 단계 의존관계

하루 4~6시간, 1인 개발을 가정한다. 기획서의 **15작업일은 1차 목표**이며 약 60~90시간에 해당한다. 환경·인증·동시성 오류를 위한 여유 5작업일을 별도로 고려하고, 검증 결과에 따라 20작업일 이상으로 재산정한다. 착수일은 정하지 않고 상대 작업일로 관리한다.

| 단계 | 작업일 | 기간 | 핵심 결과 | 다음 단계로 넘어가는 조건 |
|---|---|---|---|---|
| 0. 환경·설계 기반 | D1 | 1일 | 앱·DB·검증 도구와 기술 결정 | 앱 실행, DB 연결, 빈 DB 마이그레이션, 빌드 성공 |
| 1. 인증·회사 격리 | D2~D3 | 2일 | 로그인·역할·RLS·회사 컨텍스트 | A/B 접근 차단과 연결 재사용 격리 통과 |
| 2. 기준정보·전표 초안 | D4~D5 | 2일 | 품목·위치·전표 작성 흐름 | 입력·권한·상태·버전 검사 통과, 재고 미변경 |
| 3. 입고·원장 | D6~D7 | 2일 | 입고 확정과 공통 재고 처리 | 입고·중복·롤백·원장 일치 통과 |
| 4. 출고·동시성 | D8~D9 | 2일 | 확정 시 재고 검사와 동시 출고 | 동시 출고·다품목 원자성 통과 |
| 5. 이동·확정 취소 | D10~D11 | 2일 | 위치 이동과 반대 거래 | 수량 보존·취소 제약·중복 취소 방지 통과 |
| 6. 조회·대시보드 | D12~D13 | 2일 | 실제 데이터 기반 조회·집계 | 회사·역할·기간별 집계와 성능 측정 완료 |
| 7. 배포·포트폴리오 | D14~D15 | 2일 | 데모·복원 검증·시연 자료 | 전체 필수 검증과 재현 문서 완료 |

의존 순서는 `환경 → 인증·격리 → 기준정보·초안 → 입고 → 출고 → 이동·취소 → 종합 조회 → 배포`다. 각 업무 단계에서 API와 최소 UI를 함께 연결한다. 재고·원장의 기본 조회는 3단계부터 제공하고, 6단계에서 검색·집계·화면을 완성한다.

일정이 지연되면 원인을 환경, 설계, 구현 오류로 구분해 남은 작업량을 갱신한다. 화면 장식과 선택 확장은 미룰 수 있지만, 회사 격리·재고 정합성·동시성 검증은 완료 조건에서 제외하지 않는다.

## 5. 단계별 실행 작업

작업 ID 하나를 AI 개발도구에 전달할 기본 변경 단위로 사용한다. 한 번에 검증하기 크면 하위 작업으로 나눈다. 아래 산출물 경로는 생성 예정이며 현재 존재하는 파일을 뜻하지 않는다.

### 5.1 0단계 — 환경과 설계 기반

| ID | 작업 | 산출물·완료 기준 |
|---|---|---|
| P0-01 | 런타임·라이브러리·DB 버전과 실행 방식 선택 | `docs/기술결정.md`에 선택 이유·버전·제약 기록, 인증 연동 가능성 확인 |
| P0-02 | Next.js·TypeScript·Tailwind 프로젝트 구성 | 잠금 파일·버전 핀 생성, 개발 서버·타입 검사·프로덕션 빌드 실행 |
| P0-03 | 개발·테스트 DB, 마이그레이션, 초기 데이터 실행 구조 구성 | `.env.example`에는 변수명·비밀이 아닌 예시만 기록. 빈 DB에 적용하고 마이그레이션 재실행 시 중복 적용 없음 확인 |
| P0-04 | 테스트·CI·설계 문서 기반 구성 | Vitest 등 선택 도구와 Playwright 실행 환경, 기본 CI, `docs/DB-설계.md`·`docs/API-명세.md` 초안 |

**단계 완료:** 깨끗한 의존성 설치 후 앱 실행·DB 연결·빌드·빈 DB 마이그레이션을 재현한다. 테스트 실행기만 준비된 상태를 업무 기능 검증 완료로 기록하지 않는다.

### 5.2 1단계 — 인증, 역할, 회사 격리

| ID | 작업 | 산출물·완료 기준 |
|---|---|---|
| P1-01 | 인증 라이브러리 연결, 회사·사용자·소속·역할 데이터 생성 | A/B 회사와 각 역할 계정 로그인 가능. 사용자당 소속 하나, 로그아웃·만료 세션 거절 확인 |
| P1-02 | 권한 검사와 `GET /api/me` 구현 | 서버에서 사용자·회사·역할 결정. 미인증 401, 역할 부족 403, 다른 회사 개별 대상 404 |
| P1-03 | DB 역할 분리와 회사 트랜잭션 헬퍼 구현 | 마이그레이션 계정과 일반 앱 계정 분리. 앱 계정은 테이블 소유자·슈퍼유저·`BYPASSRLS`가 아님 |
| P1-04 | 최초 업무 테이블과 RLS 검증, 로그인·공통 화면 연결 | 최초 `items` 등 실제 회사업무 테이블로 A/B 직접 SQL 접근 차단 확인. 회사명·역할 상시 표시 |

**단계 완료:** 실제 앱 DB 권한으로 RLS를 검증한다. 연결 풀에서 A/B 요청을 번갈아 실행하고 커밋·롤백 후 회사 컨텍스트가 남지 않는지 확인한다. 회사 컨텍스트가 없을 때도 업무 데이터 접근을 차단한다. 새 테이블이 생기는 이후 단계에서도 같은 검사를 추가한다.

## 6. 데이터·API 구현 공통 기준

### 6.1 마이그레이션과 DB 권한

| 구현 시점 | 대상 | 필수 설계 |
|---|---|---|
| 1단계 | `tenants`, 인증 테이블, `memberships`, 최초 업무 테이블 | 사용자 소속 하나, 인증 데이터 접근 경로, RLS와 앱 역할 |
| 2단계 | `items`, `warehouses`, `locations`, `inventory_documents`, `inventory_document_lines` | 회사 범위 고유성, 복합 외래키, 위치·창고 관계, 전표 버전·상태·수량 |
| 3단계 | `stock_balances`, `stock_ledger`, `idempotency_requests`, `audit_logs` | 비음수 잔량, 한 번만 반영하는 고유 제약, 원장 불변성, 반대 거래 연결을 위한 확장 지점 |
| 5단계 | 반대 전표 관계와 제약 완성 | 원본당 반대 전표 하나, 취소 트랜잭션과 원본 시각 보존 |

새 회사업무 테이블에는 읽기·쓰기를 제한하는 RLS와 회사 ID를 포함한 참조 제약을 함께 적용한다. 앱 계정으로 검증하고, 마이그레이션용 소유자 계정의 성공 결과를 격리 테스트로 사용하지 않는다. 원장 수정·삭제 및 `TRUNCATE` 권한을 부여하지 않고 필요한 읽기·추가 권한만 부여한다.

트랜잭션 내부에서는 하나의 체크아웃된 DB 연결을 끝까지 사용한다. 회사 컨텍스트는 그 트랜잭션에만 적용하고, 오류 시 롤백한 뒤 연결을 반환한다. 기존 마이그레이션의 임의 수정 대신 새 버전으로 스키마 변경을 기록한다.

### 6.2 API와 상태 규칙

기획서의 `/api/me`, 기준정보, `/api/inventory-documents`, `post`, `cancel`, `reverse`, `/api/stock`, `/api/stock-ledger`, `/api/dashboard`, `/api/audit-logs`를 기준으로 API 명세를 작성한다. 요청·응답 필드, 역할, 입력 조건, 업무 오류 코드, 요청 ID를 정의한다.

전표 상태는 `DRAFT → POSTED → REVERSED`와 `DRAFT → CANCELLED`만 허용한다. 상태 검사와 버전 검사는 DB 변경과 함께 수행하여 검사 이후 다른 요청이 상태를 바꾸는 경쟁 조건을 막는다.

중복 결과를 반환할 때도 현재 요청자의 인증·회사·역할·대상 접근권한을 먼저 검사한다. 새로운 확정 요청의 오래된 버전 충돌과, 이미 완료된 동일 요청의 결과 재반환을 구분한다. 원본이 나중에 취소되었을 때 과거 성공 응답을 조회하는 행위가 재확정이나 현재 상태 오인으로 이어지지 않도록 응답 규약을 명시한다.

DB 커밋 후 화면을 갱신하고, 회사업무 응답은 공용 서버 캐시에 보관하지 않는다. 인증 라이브러리의 세션·쿠키 설정과 변경 요청 보호 방식을 적용한다. 로그에는 요청·회사·사용자·전표 식별자와 결과 코드를 남기고 비밀번호·세션 토큰·연결 비밀값은 제외한다.

## 7. 검증 계획과 요구사항 연결

각 시나리오는 독립된 초기 데이터와 테스트 DB를 사용한다. 개발·데모 DB를 자동 초기화 대상으로 사용하지 않는다. RLS·트랜잭션·잠금은 실제 PostgreSQL로, 브라우저 흐름은 Playwright로 검증한다.

| 검증 ID | 시나리오 | 기대 결과 | 유형·최초 단계 |
|---|---|---|---|

CI는 잠금 파일 기반 설치, 타입 검사, 단위 테스트, 실제 DB 통합 테스트, 빌드, 핵심 E2E를 실행하도록 단계별로 확장한다. 매번 새 테스트 DB에 마이그레이션을 적용하며, 동시성 검증은 DB 모의 객체로 대체하지 않는다.

테스트 결과에는 실행한 시나리오, 통과·실패·건너뜀 수, 실패 원인과 재실행 결과를 구분해 남긴다. 필수 테스트 실패나 미실행 상태로 다음 완료 조건을 충족했다고 기록하지 않는다.

## 8. 저장소 구조와 관리할 산출물

다음은 최소 구성 제안이다. 선택한 도구의 관례에 맞게 조정할 수 있으며, 사용하지 않는 빈 계층은 미리 만들지 않는다.

```text
src/
  app/                  # 화면, 레이아웃, Route Handlers
  components/           # 공통 화면 요소
  server/
    auth/               # 인증 라이브러리 연결, 세션·역할 검사
    db/                 # 연결 풀, 회사 트랜잭션, SQL 접근
    inventory/          # 전표·확정·취소 업무 서비스
    queries/            # 재고·이력·대시보드 조회
db/
  migrations/           # 버전 관리형 스키마·제약·RLS
  seeds/                # 합성 회사·계정·기준정보·입고 초기화
tests/
  unit/
  integration/
  e2e/
docs/                   # 기획·개발계획·기술결정·DB·API·검증·운영 문서
package.json            # npm run verify로 로컬 검증
```

| 산출물 | 작성·갱신 시점 | 반드시 포함할 내용 |
|---|---|---|
| README | 0단계부터, 7단계 최종 검증 | 설치·DB 준비·실행·테스트, 계정 역할, 범위·제한, 문서 링크 |
| 기술결정·DB 설계·API 명세 | 관련 구현 직전과 변경 시 | 버전·선택 이유, 제약·RLS·잠금 순서, 요청·응답·권한·오류 |
| 검증 결과 | 각 단계 완료 시 | 실행 명령, 조건, 결과, 실패 원인·잔여 문제 |
| 배포·복원 절차 | 7단계 | 환경변수 이름, 마이그레이션, 상태 확인, 장애 시 대응, 별도 DB 복원 결과 |
| 시연 자료 | 7단계 | 대표 업무 흐름, 격리·중복·동시성 검증 근거, 약 3분 영상 |

실행 명령은 실제 스크립트가 만들어진 후 README에 확정한다. 인증값·DB 연결 비밀값은 저장소에 넣지 않는다. 커밋은 검증 가능한 변경 단위로 만들고, GitHub에서 확인하려면 푸시까지 완료되어야 한다. 커밋·푸시·배포 실행은 해당 작업에서 정한 범위에 따른다.

## 9. 진행 관리와 위험 대응

| 위험·의존성 | 발견 시점 | 대응 |
|---|---|---|
| 개발 환경에서 컨테이너 실행 불가 | 0단계 | 동일 버전 PostgreSQL의 지원되는 실행 방식 확인, 실제 DB 검증 가능 여부를 먼저 해결 |
| 인증 라이브러리 호환성·계정 초기 생성 제약 | 0~1단계 | 로그인·세션·초기 계정의 작은 구현으로 확인 후 업무 기능 착수 |
| RLS를 우회하는 DB 계정 또는 컨텍스트 누수 | 1단계부터 | 실제 앱 역할과 연결 재사용 검사, 새 테이블마다 정책·권한 검증 |
| 최초 잔량 생성·동시 확정·중복 취소 경쟁 | 3~5단계 | 고유 제약·일관된 잠금·원자적 트랜잭션과 독립 연결 테스트 |
| 일정 초과 | 각 단계 완료 시 | 남은 작업량 재산정, 선택 기능·화면 장식 후순위, 핵심 검증 유지 |
| 데모 배포 자원·접근권한 미확보 | 0단계 조사, 7단계 사용 | 필요한 앱·DB·환경변수 요구를 미리 기록. 배포 미실행은 기능 구현 완료와 구분 |

AI 작업지시에는 목표 하나, 선행 완료 항목, 관련 파일, 변경 허용 범위, 완료 기준을 넣는다. 결과는 변경 파일, 실행한 검증과 결과, 남은 문제로 짧게 기록한다. 매 작업마다 전체 기획서를 재작성하지 않고 해당 부분만 참조한다.
