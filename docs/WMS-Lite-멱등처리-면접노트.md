# WMS Lite 멱등 처리 설명 노트

포트폴리오 15쪽의 실제 코드를 설명하기 위한 자료입니다. 앱 코드 기준은 `11e2095`이며, 문서 보강 과정에서 처리 코드는 변경하지 않았습니다.

## 30초 설명

“확정 결과를 받지 못해도 새 키를 만들지 않고 같은 요청 키로 다시 확인합니다. 서버는 회사와 요청 키로 DB 트랜잭션 잠금을 잡고, 저장된 요청 해시를 비교합니다. 같은 키·같은 내용으로 이미 성공했다면 작업을 재실행하지 않고 원래 결과를 반환합니다. 새 요청은 재고·원장·요청 결과를 같은 트랜잭션에 저장합니다. 그래서 COMMIT 후 응답이 유실되어도 원래 키로 성공 결과를 찾을 수 있습니다.”

## 실제 코드에서 따라갈 순서

| 위치 | 읽고 설명할 내용 |
| --- | --- |
| `src/server/v2/workflow/index.ts`의 `executeWorkflow` | `requireV2Access`로 해당 명령의 회사·창고·권한을 검사한 뒤 `withTenant`에 진입 |
| 같은 파일의 `executeWorkflowInTransaction` | `parseWorkflowInput` → 조회자 거절 → `pg_advisory_xact_lock` → 창고 상태 잠금 → 요청 해시 계산 → 기존 결과 조회 |
| 같은 파일의 `canonical`·`hash` | 객체 키를 정렬하여 같은 의미의 객체 키 순서 차이를 정규화하고 SHA-256 계산. 배열 순서는 유지 |
| 같은 파일의 기존 요청 분기 | 같은 키의 해시가 다르면 `IDEMPOTENCY_CONFLICT`. 같으면 저장된 작업 결과를 `replayed: true`로 반환 |
| 같은 파일의 `persist` | 재고 변경·요청 결과·원장을 같은 DB 연결과 트랜잭션에서 저장 |
| `src/server/db/tenant.ts`의 `withTenant` | 트랜잭션 범위 회사 컨텍스트 설정 → 작업 → COMMIT → 응답 반환. 실패하면 ROLLBACK |
| `db/migrations/1792368000010_v2-workflow.sql` | 요청 테이블의 `PRIMARY KEY(tenant_id, request_id)`와 재고·원장·요청의 연결 |

권한 검사는 생략하지 않습니다. 저장된 결과가 있다는 사실은 권한을 부여하는 근거가 아닙니다.

## 예상 질문과 답변

### 같은 키인데 수량을 바꾸면?

요청 해시가 달라져 충돌로 거절됩니다. 해시는 정규화된 `warehouse_id`, `request_id`, `command`, `payload`를 대상으로 합니다. 수량을 수정하려면 원래 확정 결과를 먼저 확인한 후 별도의 적법한 업무를 진행해야 합니다.

### 두 서버가 같은 키를 동시에 받으면?

같은 회사·키에 대해 PostgreSQL 트랜잭션 advisory lock을 사용하므로 두 요청이 동시에 신규 처리를 진행하지 않습니다. 앞선 트랜잭션이 끝나면 뒤 요청이 저장 결과를 확인합니다. DB 기본키 제약도 같은 회사·키의 중복 저장을 제한합니다. 서로 다른 요청의 창고 재고 경합은 별도의 상태 잠금·업무 규칙으로 제어합니다.

### COMMIT 전에 실패하거나 COMMIT 후 응답이 끊기면?

COMMIT 전 실패는 DB 변경을 롤백합니다. COMMIT 후 응답만 끊겼다면 성공한 요청 결과가 남으므로 같은 키로 재조회·재전송하여 결과를 확인합니다. 클라이언트가 실패를 추측해 새 키로 확정하는 방식은 피해야 합니다.

### 원래 응답을 그대로 다시 주는가?

원래 작업의 `result`를 재사용합니다. compact 응답에서는 저장된 `version`도 재사용합니다. 전체 응답의 `snapshot`은 현재 창고 상태를 조회하므로 예전 응답 JSON 전체를 무조건 그대로 반환한다고 설명하면 부정확합니다.

### 새 키로 같은 물건을 또 요청하면?

멱등 처리는 동일한 원요청 키를 보존한다는 전제가 있습니다. 새 키를 발급한 논리적 중복까지 이 장치 하나로 전부 막지는 못합니다. 잔량·수령 식별자·원행 등의 업무 규칙과 클라이언트의 미확인 요청 복구를 함께 적용합니다.

### 요청 해시는 보안 장치인가?

내용 일치 확인 장치입니다. 인증·권한을 대신하지 않습니다. 회사는 로그인 소속에서 결정하고, 서버 권한 검사와 DB RLS를 별도로 사용합니다.

### 왜 메모리 캐시나 버튼 비활성화만 사용하지 않았는가?

페이지 새로고침·서버 재시작·여러 인스턴스에서도 같은 요청의 결과가 필요합니다. 영속 DB의 요청 기록과 트랜잭션을 기준으로 삼고, UI의 버튼 비활성화·키 보존은 이를 보조합니다.

## 검증 근거와 주의점

- `tests/e2e/v2-acceptance.spec.ts`에는 동일 요청 재전송과 같은 키의 다른 내용 충돌을 검사하는 코드가 있습니다.
- `tests/integration/v2-workflow.test.ts`에는 요청 결과 조회와 재반환을 확인하는 검사가 있습니다.
- 실제 실행 결과와 범위는 [전체 회귀 기록](v2-local-regression-latest.json)을 확인합니다. 이번 문서 변경에서 이 검사를 새로 실행했다고 주장하지 않습니다.
- 포트폴리오 12쪽의 시뮬레이터 이미지는 재시도 0회인 정상 흐름입니다. 재시도·응답 유실 재현의 화면 근거로 사용하지 않습니다.
