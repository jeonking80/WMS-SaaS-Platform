# WMS Lite 프로젝트 기획서
### 고객사별 물류·창고 운영관리 SaaS

**문서 버전:** v0.1 — 기획 초안  
**개발 방식:** AI 개발도구를 활용한 1인 기획·개발  
**프로젝트 목적:** 물류 업무를 웹서비스로 구현하고, 고객사별 데이터 분리와 재고 정합성을 검증하는 포트폴리오 구축

---

## 1. 프로젝트 개요

### 1.1 한 문장 소개

> **여러 회사가 같은 웹서비스를 이용하면서, 각자의 창고·품목·입출고·재고·작업이력을 독립적으로 관리하는 물류 운영 SaaS를 개발한다.**

단순한 재고 목록 화면이 아니라, 다음 업무 흐름이 연결되는 시스템을 목표로 한다.

```text
회사별 로그인
    ↓
품목·창고·보관위치 등록
    ↓
입고 등록 및 확정
    ↓
재고 조회 / 창고 내부 이동
    ↓
출고 등록 및 확정
    ↓
재고 변동 이력 / 운영 대시보드
```

### 1.2 개발 목적

이번 프로젝트에서는 다음 세 가지를 결과물로 보여준다.

| 목표 | 보여줄 결과 |
|---|---|
| 서비스 기획 | 사용자의 업무를 정의하고 화면·데이터·처리 규칙으로 구체화 |
| 웹 개발 | 프론트엔드·API·DB를 연결한 실제 동작하는 업무시스템 |
| SaaS 및 백엔드 설계 | 고객사 데이터 격리, 동시 출고 처리, 중복 반영 방지, 변경 이력 추적 |

쿨스는 공식 홈페이지에서 재고 위치·재고관리, 항만 운송관리, 항만 CFS 물류 운영관리 솔루션을 소개하고 있다. 이 프로젝트는 해당 제품을 복제하는 것이 아니라, **물류 업무를 웹서비스로 구현하는 공통 역량을 보여주기 위한 독립 프로젝트**다. [KULS](https://www.kuls.co.kr/)

### 1.3 프로젝트의 중심 과제

MELIGO-WEB과 다른 기능을 많이 추가하는 것보다, 이번에는 아래 세 가지에 집중한다.

**고객사별 데이터 분리 → 정확한 재고 처리 → 변경 원인을 추적할 수 있는 이력**

AI 챗봇, 예측 모델, 지도, 디지털트윈은 초기 완성 조건에 포함하지 않는다.

## 2. 서비스 대상과 이용 시나리오

### 2.1 가상의 고객사

소규모 부품 유통업체 두 곳이 서비스를 이용한다고 가정한다.

| 구분 | A 회사 | B 회사 |
|---|---|---|
| 취급 품목 | 산업용 부품 | 포장·소모품 |
| 창고 | 본창고, 보조창고 | 본창고, 보조창고 |
| 사용자 | 관리자·작업자·조회자 | 관리자·작업자·조회자 |
| 관리 대상 | 자사 품목·재고·입출고 | 자사 품목·재고·입출고 |

**여기서 고객사는 서비스를 사용하는 회사다.** 한 물류회사가 여러 화주의 물건을 대신 보관하는 복잡한 위탁물류 구조는 초기 범위에서 제외한다.

### 2.2 해결하려는 문제

다음은 실제 고객 인터뷰 결과가 아니라, 프로젝트에서 검증할 **가상의 업무 문제**다.

| 업무 문제 | 제공할 기능 |
|---|---|
| 재고 수량은 알지만 어느 위치에 있는지 찾기 어려움 | 품목별·창고별·보관위치별 재고 조회 |
| 입출고를 여러 사람이 처리하면서 수량이 맞지 않음 | 확정 처리와 트랜잭션 기반 재고 반영 |
| 버튼을 다시 눌러 출고가 중복 반영됨 | 동일 작업의 중복 반영 방지 |
| 재고가 바뀐 이유를 알 수 없음 | 전표와 연결된 재고 변동 이력 |
| 서로 다른 회사의 데이터가 섞일 우려가 있음 | 회사별 접근권한 및 데이터 격리 |
| 당일 작업 상황을 한눈에 보기 어려움 | 입출고 현황·대기 작업·부족 재고 대시보드 |

### 2.3 사용자 역할

| 역할 | 허용 업무 |
|---|---|
| **관리자** | 기준정보 관리, 입출고·이동 작성 및 확정, 확정 취소, 전체 이력 조회 |
| **작업자** | 입출고·이동 작성 및 확정, 재고·작업이력 조회 |
| **조회자** | 재고·대시보드·확정된 작업이력 조회만 가능 |

모든 권한은 **소속 회사 안에서만** 유효하다. A 회사 관리자도 B 회사 데이터에는 접근할 수 없다.

초기에는 사용자당 소속 회사를 하나로 제한한다. 회사와 계정은 초기 데이터 생성 절차로 제공하며, 공개 회원가입·초대메일·복잡한 조직 전환 기능은 만들지 않는다.

## 3. 개발 범위

### 3.1 1차 필수 범위

| 영역 | 구현 범위 |
|---|---|
| 로그인·권한 | 세션 인증, 소속 회사 확인, 관리자·작업자·조회자 구분 |
| 기준정보 | 품목, 창고, 창고 내 보관위치 |
| 입고 | 전표 작성, 수정, 취소, 입고 확정 |
| 출고 | 전표 작성, 수정, 취소, 재고 확인 후 출고 확정 |
| 내부 이동 | 동일 창고의 보관위치 간 재고 이동 |
| 재고 조회 | 품목·창고·보관위치별 현재고 및 검색 |
| 변경 이력 | 입고·출고·이동·확정 취소의 원장과 담당자 기록 |
| 대시보드 | 당일 작업 현황, 출고 대기, 부족 재고, 최근 작업 |
| 품질검증 | 데이터 격리·동시성·중복 방지·회귀 테스트 |
| 배포 | 독립된 데모 환경과 포트폴리오 자료 |

### 3.2 초기 업무 제약

혼자 완성할 수 있도록 다음 조건을 둔다.

- 수량은 **개 단위의 양의 정수**로 입력한다. 중량·길이·박스 환산은 제외한다.
- 전표 하나는 **하나의 창고**를 대상으로 한다.
- 입고·출고 전표는 하나의 보관위치를 대상으로 하되 여러 품목을 담을 수 있다.
- 이동 전표는 동일 창고의 출발 위치 한 곳과 도착 위치 한 곳을 지정한다.
- 전표당 품목은 최대 20개로 제한한다.
- 출고 예정 수량의 예약은 하지 않는다. **확정 시점의 현재고를 기준으로 출고 가능 여부를 판단한다.**

### 3.3 1차에서 제외할 내용

| 제외 영역 | 이유 |
|---|---|
| ERP·쇼핑몰·택배사 연동 | 외부 시스템 없이 핵심 업무를 먼저 검증 |
| 바코드 장비·PLC·센서 연결 | 이번 프로젝트는 물류 업무용 웹 SaaS에 집중 |
| LOT·유통기한·시리얼·선입선출 | 별도의 재고 배정 규칙이 필요 |
| 재고 예약·부분 출고·분할 피킹 | 전표 및 재고 상태가 복잡해짐 |
| 창고 간 운송·배송 추적 | 이동 중 재고와 운송 상태 관리가 추가됨 |
| 생산관리·BOM·품질검사 | MES 영역으로 범위가 확대됨 |
| 원가·회계·정산 | 수량 관리와 다른 업무 체계가 필요 |
| 구독 결제·요금제 | 이번에는 SaaS의 데이터 분리와 업무 기능을 검증 |
| 3D 창고·디지털트윈·수요 예측 | 초기 핵심 흐름의 완성에 불필요 |

**최종 결과물은 상용 WMS 전체가 아니라, 핵심 물류 업무와 SaaS 구조를 구현한 프로토타입이다.**

## 4. 주요 기능 기획

### 4.1 기준정보 관리

**품목**

품목코드, 품목명, 단위, 최소재고 기준, 사용 여부를 관리한다. 같은 회사 안에서는 품목코드가 중복될 수 없지만, A 회사와 B 회사는 같은 코드를 사용할 수 있다.

**창고·보관위치**

창고를 등록하고 내부 위치를 관리한다.

```text
본창고
 ├─ A-01
 ├─ A-02
 └─ B-01
```

보관위치는 창고 안에서 유일한 코드를 갖는다. 실제 거래 이력이 있는 기준정보는 삭제하지 않고 비활성화한다. 잔량이 있는 위치의 비활성화는 차단한다.

### 4.2 입고 관리

사용자가 창고·보관위치·품목·수량을 입력하여 입고 전표를 작성한다.

```text
입고 전표 작성
    ↓
수량·위치 확인
    ↓
입고 확정
    ↓
재고 증가 + 재고 원장 기록
```

**초안 저장만으로는 재고가 증가하지 않는다.** 실제 입고 완료 여부는 작업자가 확인하고 확정한다.

### 4.3 출고 관리

출고 전표를 작성할 때 참고용 현재고를 보여주되, 최종 재고 검사는 확정 시점에 서버에서 다시 수행한다.

예를 들어 재고가 100개일 때 두 작업자가 각각 80개를 동시에 출고하면, 두 건 모두 처리되어서는 안 된다.

**기대 결과:** 한 건만 확정되고 다른 건은 재고 부족으로 거절되며, 최종 재고는 20개다.

여러 품목을 포함한 전표에서 하나라도 수량이 부족하면 전표 전체를 확정하지 않는다. 부분 출고는 이번 범위에서 제외한다.

### 4.4 창고 내부 이동

동일 창고에서 재고 위치를 변경한다.

```text
이동 전
A-01: 70개 / A-02: 0개

20개 이동 후
A-01: 50개 / A-02: 20개

창고 전체 재고: 70개로 동일
```

출발 위치 차감과 도착 위치 증가가 함께 처리되어야 한다. 한쪽만 반영되면 전체 작업을 취소한다.

### 4.5 재고 및 이력 조회

재고 화면에서는 품목·창고·보관위치로 검색한다. 특정 재고를 선택하면 관련 입고·출고·이동 이력을 확인할 수 있다.

이력에는 다음 정보를 제공한다.

| 정보 | 예시 |
|---|---|
| 작업 종류 | 출고 확정 |
| 전표번호 | OUT-000123 |
| 품목·위치 | PART-001 / 본창고 A-01 |
| 변동 수량 | -30 |
| 담당자 | 작업자 A |
| 처리 시각 | 서버에서 기록한 확정 시각 |
| 연관 작업 | 원본 전표, 취소 전표 |

**사용자가 현재고를 직접 덮어쓰는 기능은 제공하지 않는다.** 초기 재고도 입고 전표를 통해 생성한다.

### 4.6 운영 대시보드

화면 상단에는 다음 지표를 배치한다.

| 지표 | 계산 기준 |
|---|---|
| 재고 보유 품목 수 | 회사 전체 합산 현재고가 0보다 큰 품목 |
| 오늘 입고·출고 확정 건수 | 오늘 확정된 원본 전표 건수 |
| 출고 대기 건수 | 아직 확정되지 않은 출고 초안 |
| 부족 재고 품목 수 | 회사 전체 현재고가 품목별 최소재고 기준보다 적은 품목 |

하단에는 최근 7일의 입출고 확정 건수, 최근 작업이력, 부족 재고 목록을 표시한다. 확정 취소 건수는 별도로 표시한다.

**출고 대기와 배송 지연은 구분한다.** 이 프로젝트에서는 배송 예정일이나 실제 운송 과정을 관리하지 않으므로 배송 지연 분석은 제공하지 않는다.

## 5. 핵심 업무 규칙

### 5.1 전표 상태

```text
DRAFT ── 확정 ──▶ POSTED ── 확정 취소 ──▶ REVERSED
  │
  └── 초안 취소 ──▶ CANCELLED
```

| 상태 | 의미 | 수정 가능 여부 |
|---|---|---|
| DRAFT | 작업 내용을 작성한 상태 | 가능 |
| POSTED | 재고 반영이 완료된 상태 | 품목·수량·위치 수정 불가 |
| CANCELLED | 재고 반영 전 취소 | 재사용 불가 |
| REVERSED | 확정 후 반대 거래로 취소 | 재확정 불가 |

### 5.2 확정 취소

확정된 전표를 지우거나 원장의 수량을 수정하지 않는다. **원본과 연결된 반대 거래를 생성하여 재고를 되돌린다.**

예를 들어 출고 30개를 취소하면 +30의 반대 거래를 기록한다.

입고 취소나 이동 취소로 재고가 음수가 되는 경우에는 취소를 거절한다. 이미 다른 작업에 사용된 재고를 강제로 되돌리지 않는다.

초기에는 원본 전표 전체 취소만 지원한다. 부분 취소와 취소의 재취소는 제외한다.

### 5.3 재고의 기준

```text
현재고 = 해당 회사·품목·보관위치의 재고 원장 증감 합계
```

현재고 테이블은 빠른 조회를 위한 잔량 정보이고, 재고 원장은 변동 근거를 보존하는 기록이다. 두 값이 일치하는지 테스트와 점검 기능으로 확인한다.

입출고 실적은 처리 당시의 확정 시각으로 집계하고, 나중에 발생한 취소는 취소 시각에 별도 기록한다. 현재 상태가 바뀌었다고 과거의 확정 이력을 지우지 않는다.

### 5.4 중복 및 동시 작업

동일 전표를 여러 번 확정하거나 응답 유실 후 재요청하더라도 재고에는 한 번만 반영한다.

전표를 수정하는 동안 다른 사용자가 확정한 경우에는 오래된 화면의 수정 요청을 거절한다. 이를 위해 전표 버전을 관리한다.

## 6. 화면 구성

| 화면 | 주요 구성 | 핵심 사용자 행동 |
|---|---|---|
| 로그인 | 계정 입력, 오류 안내 | 자신의 회사로 접속 |
| 대시보드 | 작업 현황, 부족 재고, 최근 이력 | 우선 확인할 업무 파악 |
| 품목·창고 관리 | 검색, 등록, 수정, 비활성화 | 기준정보 관리 |
| 입출고·이동 목록 | 종류·상태·기간 필터 | 처리할 전표 선택 |
| 전표 상세·작성 | 창고, 위치, 품목, 수량, 확정 버튼 | 작업 작성 및 확정 |
| 재고 현황 | 품목·창고·위치별 잔량 | 재고 위치와 수량 확인 |
| 재고·작업 이력 | 변동 내역, 담당자, 원본·취소 연결 | 재고 변경 원인 추적 |

### UI 설계 원칙

PC와 태블릿 사용을 우선한다. 화면 상단에는 현재 회사명과 사용자 역할을 항상 표시한다.

확정 전에는 품목·수량·위치를 다시 보여주고, 처리 중에는 반복 클릭을 막는다. 다만 버튼 비활성화는 편의 기능일 뿐이며, 중복 반영은 서버에서 방지한다.

빈 목록, 재고 부족, 권한 부족, 처리 실패를 서로 다른 상태로 안내한다. 재고는 서버의 확정 응답을 받은 후 갱신하고, 실패한 요청을 성공한 것처럼 표시하지 않는다.

## 7. 시스템 구성과 기술스택

### 7.1 전체 구조

```text
웹 브라우저
    ↓
Next.js / React UI
    ↓
API
 ├─ 로그인·소속 회사 확인
 ├─ 역할·대상 데이터 권한 검사
 └─ 입력 검증
    ↓
업무 서비스
 ├─ 기준정보

 ├─ 재고 확정·취소

PostgreSQL
 ├─ 회사별 데이터
```

**하나의 애플리케이션과 하나의 PostgreSQL DB**로 시작한다. 코드 내부에서는 인증, 재고 업무, 데이터 접근을 분리하되 별도 마이크로서비스로 나누지 않는다.

### 7.2 기술스택 초안

|---|---|
| 웹 UI | Next.js, React, TypeScript, Tailwind CSS |
| 백엔드 | Next.js Route Handlers, Node.js |
| DB | PostgreSQL |
| 데이터 접근 | `pg` 기반 SQL 및 버전 관리형 마이그레이션 |
| 인증 | 유지보수 중인 인증 라이브러리를 이용한 세션 인증 |
| 테스트 | 단위 테스트, 실제 PostgreSQL 통합 테스트, Playwright |
| 개발환경 | 독립 저장소, 로컬 PostgreSQL 컨테이너 |
| 자동 검증 | GitHub Actions |
| 데모 배포 | 기존 서비스와 분리된 소규모 앱·DB 환경 |

인증 서버 자체를 새로 만드는 작업은 하지 않는다. Next.js 공식 문서도 인증 라이브러리 활용과 데이터 접근 계층의 권한 검사 구성을 안내한다. 이번 프로젝트에서는 **재고 업무와 고객사별 데이터 분리**에 개발 시간을 집중한다. [Next.js](https://nextjs.org/docs/app/guides/authentication)

패키지와 DB의 구체적인 버전은 개발환경 확인 단계에서 호환성을 검토한 후 고정한다.

## 8. 데이터 모델 초안

아래는 설계 방향을 정하기 위한 모델이며, 상세 컬럼과 마이그레이션은 이후 별도 설계 작업에서 확정한다.

| 테이블 | 역할 | 주요 정보 |
|---|---|---|
| `tenants` | 서비스 이용 회사 | 회사 ID, 회사명, 상태 |
| 인증 관련 테이블 | 계정·세션 | 인증 라이브러리 기준 |
| `memberships` | 사용자 소속·역할 | 사용자 ID, 회사 ID, 역할 |
| `items` | 품목 | 회사 ID, 품목코드, 이름, 최소재고 |
| `warehouses` | 창고 | 회사 ID, 창고코드, 이름 |
| `locations` | 보관위치 | 회사 ID, 창고 ID, 위치코드 |
| `inventory_documents` | 작업 전표 | 종류, 상태, 창고·위치, 버전, 원본 전표 |
| `inventory_document_lines` | 전표별 품목 | 전표 ID, 품목 ID, 수량 |
| `stock_balances` | 현재고 | 회사·위치·품목별 잔량 |
| `stock_ledger` | 재고 변동 원장 | 전표·품목·위치, 증감 수량, 처리 시각 |
| `idempotency_requests` | 중복 요청 관리 | 회사, 작업 종류, 요청 키, 입력 해시, 처리 결과 |
| `audit_logs` | 주요 작업 기록 | 담당자, 작업 종류, 대상, 요청 ID, 시각 |

### 필수 데이터 제약

품목코드는 회사 안에서, 위치코드는 창고 안에서 유일하게 관리한다. 현재고는 `회사 + 위치 + 품목` 조합당 하나만 존재하고 0 미만이 될 수 없다.

또한 A 회사 전표에 B 회사 품목을 연결할 수 없도록, 관련 참조에는 회사 ID를 포함한 복합 외래키를 적용한다. PostgreSQL은 복수 컬럼의 고유 제약과 외래키를 지원하므로 이러한 관계를 DB에서도 검증할 수 있다. [PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html)

재고 원장은 일반 애플리케이션 권한으로 수정·삭제할 수 없게 구성한다. 취소는 기존 기록 변경이 아닌 새로운 반대 거래로 표현한다.

## 9. 핵심 기술 설계

### 9.1 고객사 데이터 격리

화면에서 회사별 목록을 나누는 것만으로 끝내지 않는다.

**서버 측 권한 검사**

로그인한 사용자와 소속 정보를 바탕으로 회사 ID를 결정한다. 요청 본문에 들어온 회사 ID를 그대로 신뢰하지 않는다.

**DB 측 격리**

회사업무 테이블에 `tenant_id`를 두고 PostgreSQL RLS를 적용한다. 요청의 DB 트랜잭션 안에서만 회사 컨텍스트를 설정하여 커넥션 재사용 시 다른 요청에 남지 않도록 한다.

애플리케이션 DB 계정은 테이블 소유자·슈퍼유저·RLS 우회 권한을 사용하지 않는다. 이 계정들은 RLS를 우회할 수 있으므로 마이그레이션 계정과 분리해야 한다. [PostgreSQL](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

**검증 범위**

목록뿐 아니라 상세 조회, 수정, 확정, 대시보드 집계에도 동일한 권한 검사를 적용한다. OWASP 역시 객체 ID를 받는 API에서 해당 객체에 대한 접근권한을 검사하도록 권고한다. [OWASP Foundation](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)

초기 버전은 회사별 업무 응답을 공용 서버 캐시에 저장하지 않는다.

### 9.2 재고 확정 트랜잭션

입고·출고·이동은 아래 처리를 하나의 DB 트랜잭션으로 묶는다.

```text
사용자·회사·권한 확인
    ↓
중복 요청 확인
    ↓
전표 잠금 및 상태·버전 재확인
    ↓
대상 재고 행 확보·잠금
    ↓
재고 충분 여부 검증
    ↓
재고 원장 추가
    ↓
현재고 갱신
    ↓
전표 확정 + 작업 이력 + 요청 처리 결과 기록
    ↓
커밋
```

대상 잔량 행이 없다면 먼저 0 수량 행을 확보한 후 잠금 처리한다. 여러 품목·위치를 처리할 때는 일정한 순서로 잠금을 얻는다.

PostgreSQL 공식 문서는 여러 대상을 일관된 순서로 잠그는 것이 교착상태를 줄이는 방법이라고 설명한다. 교착상태나 잠금 시간 초과 발생 시에는 트랜잭션을 취소하고, 재고를 일부만 반영하지 않는다. [PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html)

### 9.3 중복 요청 방지

확정 요청에는 `Idempotency-Key`를 사용한다.

| 상황 | 처리 |
|---|---|
| 같은 키·같은 요청 재전송 | 이미 처리한 결과 반환 |
| 같은 키로 다른 내용 전송 | 충돌 오류 반환 |
| 다른 키로 이미 확정된 전표 재요청 | 추가 재고 반영 없이 기존 확정 상태 반환 |
| 확정 취소된 전표 재확정 | 거절 |
| DB 커밋 후 응답만 유실 | 재요청으로 기존 결과 확인 |

중복 요청 방지 키만 믿지 않고, 전표 상태와 원장 고유 제약도 함께 사용한다.

### 9.4 추적 가능한 오류

로그에는 요청 ID, 회사 ID, 사용자 ID, 전표 ID, 작업 종류, 결과 코드를 남긴다. 비밀번호와 세션 토큰은 기록하지 않는다.

재고 불일치가 발견되면 해당 품목·위치의 원장과 전표를 조회할 수 있어야 한다. 원인 확인 없이 자동으로 잔량을 덮어쓰는 복구 기능은 만들지 않는다.

## 10. API 구성 초안

| 구분 | API 예시 | 목적 |
|---|---|---|
| 사용자 | `GET /api/me` | 사용자·회사·역할 확인 |
| 기준정보 | `/api/items`, `/api/warehouses`, `/api/locations` | 조회·등록·수정 |
| 전표 | `/api/inventory-documents` | 목록 및 초안 생성 |
| 전표 수정 | `PATCH /api/inventory-documents/:id` | 초안 수정 |
| 확정 | `POST /api/inventory-documents/:id/post` | 재고 반영 |
| 초안 취소 | `POST /api/inventory-documents/:id/cancel` | 미확정 작업 취소 |
| 확정 취소 | `POST /api/inventory-documents/:id/reverse` | 반대 거래 생성 |
| 재고 | `GET /api/stock` | 현재고 조회 |
| 원장 | `GET /api/stock-ledger` | 변동 이력 조회 |
| 대시보드 | `GET /api/dashboard` | 집계 조회 |
| 감사 기록 | `GET /api/audit-logs` | 관리자 작업 추적 |

로그인·로그아웃 API는 선택한 인증 라이브러리 구성을 따른다.

미인증은 401, 역할 부족은 403, 다른 회사의 개별 데이터 접근은 404로 처리한다. 재고 부족·버전 충돌·잘못된 상태 전이는 구분 가능한 업무 오류 코드와 함께 반환한다.

## 11. 검증 기준

### 11.1 반드시 통과할 시나리오

각 테스트는 독립된 초기 데이터를 사용한다.

| 테스트 | 기대 결과 |
|---|---|
| 입고 100개 확정 | 현재고 100, 원장 +100 |
| 같은 입고 확정 요청 반복 | 현재고 100 유지 |
| 재고 100에서 출고 30 | 현재고 70 |
| 재고 100에서 출고 80 두 건 동시 실행 | 한 건만 성공, 최종 20 |
| 여러 품목 중 한 품목 재고 부족 | 전표 전체 미반영 |
| 위치 A에서 B로 20개 이동 | A -20, B +20, 전체 수량 동일 |
| 확정 중 DB 오류 발생 | 원장·현재고·전표 상태 모두 롤백 |
| 커밋 후 응답 유실 및 재요청 | 재고 추가 반영 없이 기존 결과 확인 |
| A 회사 계정으로 B 회사 데이터 접근 | 조회·변경·집계 차단 |
| 조회자 계정으로 확정 API 호출 | 변경 차단 |
| 확정 취소 후 재고 점검 | 원본·반대 거래 추적 및 잔량 일치 |
| 입고 취소 시 되돌릴 재고 부족 | 취소 거절, 현재고 유지 |
| 전표의 오래된 버전으로 수정·확정 | 충돌 안내, 무단 덮어쓰기 없음 |
| 원장 합계와 현재고 대조 | 모든 회사·품목·위치에서 일치 |

연결 풀에서 A·B 회사 요청을 번갈아 실행하는 테스트도 포함해 회사 컨텍스트가 다음 요청으로 남지 않는지 확인한다.

### 11.2 테스트 구성

업무 규칙은 단위 테스트로 확인하고, 트랜잭션·동시성·RLS는 **실제 PostgreSQL 통합 테스트**로 검증한다. 로그인부터 확정·조회까지의 흐름은 Playwright로 확인한다.

CI에는 타입 검사, 테스트, 빌드, 새 DB의 마이그레이션 적용 검증을 연결한다. 각 기능을 개발할 때 관련 테스트를 함께 추가하며, 마지막 주에 검증을 몰아서 하지 않는다.

### 11.3 초기 성능 목표

합성 재고 원장 1만 건을 기준으로 주요 목록·재고 조회가 2초 이내에 표시되는 것을 초기 목표로 한다.

이는 **실측 성과가 아닌 목표치**다. 측정 시 서버 사양, 데이터량, 동시 사용자 수와 측정 구간을 함께 기록한다.

## 12. 개발·배포 환경

### 환경 분리

MELIGO-WEB·TPRI와 별도의 저장소, DB, 환경변수, 배포 리소스를 사용한다. 기존 프로젝트의 운영 DB나 인증 서버를 연결하지 않는다.

```text
로컬 개발
    ↓
독립된 테스트 DB / CI
    ↓
데모 환경
```

기존 프로젝트의 설계 경험은 활용하되, 대규모 코드 복사나 인증·결제·메시징 구조의 통째 이식은 하지 않는다.

### 데모 운영

공개 데모에는 합성 데이터만 사용하고, 기본적으로 조회 전용 계정을 제공한다. 입출고 확정과 취소는 시연 영상 또는 제한된 계정으로 보여준다.

배포 전에는 기본 동작과 DB 마이그레이션을 확인하고, 백업을 별도 DB로 복원하는 절차를 한 번 검증한다. 단일 서버 데모를 고가용성 상용 서비스로 표현하지 않는다.

## 13. 단계별 개발계획

| 단계 | 목표 | 완료 기준 | 계획 기간 |
|---|---|---|---|
| 0. 기획·환경 확정 | 업무 범위, 기술 선택, 독립 환경 | 문서와 실행 환경 확인 | 1일 |
| 1. 인증·회사 격리 | 로그인, 역할, 회사별 접근 | A/B 접근 차단 테스트 통과 | 2일 |
| 2. 기준정보·전표 초안 | 품목·위치·전표 작성 | 초안 저장·수정·취소 가능 | 2일 |
| 3. 입고·원장 | 입고 확정과 재고 반영 | 입고·중복·롤백 검증 통과 | 2일 |
| 4. 출고·동시성 | 재고 검증 및 출고 | 동시 출고·다품목 원자성 검증 | 2일 |
| 5. 이동·확정 취소 | 위치 이동과 반대 거래 | 수량 보존·취소 규칙 검증 | 2일 |
| 6. 조회·대시보드 | 검색·이력·집계·화면 개선 | 실제 전표 데이터로 화면 연결 | 2일 |
| 7. 배포·포트폴리오 | 통합 검증, 데모, 설명자료 | 재현 가능한 결과물 제공 | 2일 |

**이 표는 전체 일정이며, AI에게 한 번에 실행시키는 작업지시가 아니다.** 각 단계 안에서도 하나의 변경 단위씩 구현하고 결과를 확인한다.

일정이 부족하면 AI 기능과 추가 시각화를 미룬다. 데이터 격리와 재고 검증은 줄이지 않는다.

## 14. AI 개발도구 운영 방식

기획·설계·구현·검수 모두 AI를 활용하되, 각 작업의 목표와 확인 기준을 분리한다.

```text
이번 작업 하나 선정
    ↓
관련 문서·코드만 전달
    ↓
구현
    ↓
해당 기능 테스트 및 필요한 독립 검수
    ↓
결과 확인
    ↓
다음 작업
```

작업지시에는 **목표 하나, 관련 파일, 변경 허용 범위, 완료 기준**만 전달한다. 매번 전체 저장소를 재조사하거나 기획서를 전부 다시 작성하게 하지 않는다.

검수는 재고 불일치, 권한 누락, 회귀 오류처럼 실제 영향을 주는 문제에 집중한다. 근거 없는 추가 기능과 취향에 따른 반복 리팩터링은 보류한다.

작업 결과는 변경 파일, 테스트 결과, 남은 문제로 짧게 기록한다. 커밋·배포는 사전에 정한 승인 범위를 따른다.

## 15. 선택 확장 — AI 물류 조회 도우미

**핵심 WMS가 완성된 이후에만 착수한다.** 이 기능이 없어도 1차 프로젝트는 완료로 인정한다.

### 목표

자연어 질문을 읽기 전용 조회 기능으로 연결한다.

| 질문 예시 | 조회할 정보 |
|---|---|
| “현재 재고가 부족한 품목은?” | 현재고와 최소재고 기준 |
| “PART-001 재고가 오늘 왜 줄었어?” | 해당 품목의 출고·이동·취소 이력 |
| “아직 확정하지 않은 출고를 보여줘.” | 출고 초안 목록 |

AI에는 정해진 조회 도구만 제공한다.

```text
getStockSummary
getStockMovementHistory
getPendingOutboundDocuments
```

회사와 권한은 서버에서 결정하며, AI가 다른 회사 ID를 지정할 수 없게 한다. AI는 임의 SQL 실행, 재고 변경, 출고 확정을 수행하지 않는다.

응답에는 조회 기간과 관련 전표를 표시한다. 기록이 없으면 이유를 만들어내지 않고 확인 불가로 안내한다.

이 확장은 **업무 데이터 조회형 LLM 기능**으로 제한하며, RAG·Vector DB·예측 모델은 추가하지 않는다.

### 16.1 산출물

| 산출물 | 포함 내용 |
|---|---|
| 실행 가능한 코드 | 웹 UI, API, DB 마이그레이션, 테스트 |

| 데모 환경 | 합성 데이터를 사용하는 조회용 웹서비스 |
| 시연 영상 | 약 3분 분량의 핵심 업무 흐름 |

### 16.2 대표 데모

```text
A 회사 로그인
    ↓
품목 100개 입고 확정
    ↓
30개 출고 확정 → 재고 70개
    ↓
같은 출고 요청 재전송 → 재고 70개 유지
    ↓
20개를 다른 위치로 이동
    ↓
위치별 50개·20개, 전체 70개 확인
    ↓
원장에서 입고·출고·이동 근거 확인
    ↓
B 회사 로그인 → A 회사 데이터 조회 불가
```

동시 출고와 DB 오류 복구는 화면에서 연출하기보다 자동화 테스트 결과로 증명한다.

### 16.3 완료 후 포트폴리오 설명

실제 구현과 검증을 마친 뒤에는 다음과 같이 설명할 수 있다.
