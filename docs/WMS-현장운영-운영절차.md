# 현장 운영 배포·전환·장애 대응 절차

기준: 기획서 v1.1. 현재 개발·검증 중인 기능 브랜치의 절차이며, 공개 운영환경에 적용한 기록이 아니다. 실행 결과는 구현 추적표와 실제 검증 보고서로 확인한다.

## 환경과 실행 프로세스

- WMS 웹은 PostgreSQL의 제한된 `wms_app` 계정으로 실행한다. `WMS_ENVIRONMENT=production`이 기본값이며 시험 환경만 `test`로 설정한다.
- 독립 시뮬레이터는 `apps/simulator`의 Node 프로세스와 SQLite 저장소를 사용한다. WMS DB 접속 정보를 전달하지 않는다. 시험 회사·시험 키·URL을 지정하고 실제 업무는 인증된 API로 처리한다.
- 연계 처리기는 `src/server/v2/integration/worker.mjs`의 별도 프로세스다. `WMS_URL`, 처리 전용 `WMS_INTEGRATION_PROCESS_KEY`, 명시된 `WMS_INTEGRATION_WAREHOUSE_IDS`가 필요하다. Docker 설치에서는 `deploy/compose.yaml`의 `integration` 프로필을 사용한다. 승인·실물 작업 권한이 없는 처리 키를 사용한다.
- 처리기가 중단돼도 접수 사건과 재시도 일정은 PostgreSQL에 남는다. 재시작은 같은 사건의 결과를 확인하며 처리한다. 401/403이면 프로세스가 종료되므로 키 권한·회수를 확인한다.
- GitHub Actions를 사용하지 않는다. 로컬 검증 결과를 확인한 이미지와 커밋만 배포한다.

## 최초 회사·관리자 발급

일반 사용자에게 회사 생성·이동 API를 제공하지 않는다. 플랫폼 운영자가 별도 운영 접근으로 회사와 최초 관리자를 발급하고 회사, 승인 근거, 담당자, 실행 시각을 남긴다. 개발용 `auth:seed`의 고정 계정이나 시험 비밀번호를 실제 회사 발급에 사용하지 않는다. `node --env-file-if-exists=.env.local scripts/provision-company.mjs`를 사용한다. 운영 설정은 `PROVISION_COMPANY_NAME`, `PROVISION_ADMIN_NAME`, `PROVISION_ADMIN_EMAIL`, `PROVISION_WAREHOUSE_CODE`, `PROVISION_WAREHOUSE_NAME`, `PROVISION_OPERATOR`, `PROVISION_REASON`, `PROVISION_REQUEST_ID`(UUID), `BETTER_AUTH_URL`, `PROVISION_INVITATION_FILE`(새 비공개 파일), `MIGRATION_DATABASE_URL`이다. 시험 회사만 `PROVISION_TEST_COMPANY=true`로 표시한다. 기존 이메일은 재배정하거나 초기화하지 않는다. 최초 초대는 24시간 유효하며 해시는 DB에, 실제 초대 링크는 권한 0600 파일에만 저장한다. 운영자가 승인된 전달 경로로 전달한다. 후속 사용자 초대는 회사 관리자의 계정 화면에서 수행한다. 조정·과납·잔량 마감 시험에는 서로 다른 승인 가능한 사용자 두 명을 준비한다.

발급은 실제 마이그레이터 소유자 계정(비슈퍼유저·RLS 우회권한 없음)으로 실행한다. 일반 앱 계정에는 회사 발급 권한이 없다. 회사·사용자·초대대기 관리자 소속·최초 창고 권한·토큰 해시·감사 기록은 한 DB 트랜잭션으로 반영하고, 토큰 파일과 상위 디렉터리를 동기화한 뒤 커밋한다. 기존 출력 파일은 덮어쓰지 않는다. 같은 이메일(대소문자 포함)이나 이미 사용한 요청 ID의 재실행은 기존 계정·암호·소속을 변경하지 않고 거절한다. 성공 응답을 재생하는 API 방식의 멱등 재실행은 제공하지 않는다.

커밋 전 실패는 DB 작업을 롤백하고 이번 실행이 만든 출력 파일만 제거한다. COMMIT 이후 응답이 유실되면 DB 성공 여부가 불확실하므로 출력 파일을 보존하고 `PROVISION_COMMIT_UNKNOWN`으로 종료한다. 파일 존재만으로 발급 성공을 판단하거나 즉시 재발급하지 않는다. 운영자는 요청 ID로 `COMPANY_PROVISION` 감사 기록과 회사·초대 상태를 대조한 후 전달 또는 복구를 결정한다. 이 경로는 기존 계정의 암호 재설정 경로가 아니다.

최초 관리자가 아직 초대를 수락하지 않았고 초대가 만료되거나 전달 링크를 잃어버린 경우에만 운영자 재발급 모드를 사용한다. 같은 회사·초기 관리자 이메일·이름·최초 창고 설정을 유지하고 `PROVISION_REISSUE_INITIAL_INVITATION=true`, `PROVISION_INITIAL_REQUEST_ID=최초발급요청UUID`, 새 `PROVISION_REQUEST_ID`, 새 `PROVISION_INVITATION_FILE`, 현재 운영 담당자와 재발급 사유를 명시해 같은 스크립트를 실행한다. 계정은 초대대기 관리자여야 하며 원발급 감사가 일치해야 한다. credential·세션·소비된 링크가 하나라도 있거나 이미 활성화된 계정이면 거절한다. 기존 계정의 암호·회사·역할·창고를 변경하지 않는다. 기존 미사용 링크 폐기와 새 링크 해시·`COMPANY_INITIAL_INVITE_REISSUE` 감사는 원자적으로 반영되며 초대 수락과 경합해도 같은 회사 잠금으로 직렬화한다. 활성 계정의 재설정은 이 모드에서 처리하지 않는다.

## 배포 및 기존 창고 전환 순서

1. 대상 앱·DB·회사·창고·담당자·작업 중지 시간을 기록한다. 공개 데모와 부하 시험 DB를 분리한다.
2. DB 백업과 체크섬을 생성하고 접근 제한된 저장소에 보관한다. 목표 호스팅의 별도 복원 환경에서 복원을 검증한다. 같은 로컬 클러스터 복원 결과는 호스팅 복원이나 RPO 달성의 근거가 아니다.
3. 기존 화면의 새 확정을 중지하고 미확인 요청 결과, 미완료 초안, 현재고와 원장을 대조한다. 미확인 실적은 새 요청 키로 반복하지 않는다.
4. 마이그레이션용 계정으로 DB 변경을 적용하고 제한 앱 계정 권한을 갱신한다. 마이그레이션·권한 갱신 완료 전에 새 웹 버전을 공개하지 않는다.
5. 신규 웹 버전을 올리고 readiness·로그인·역할·회사/창고 범위·연계 키 거절 규칙을 확인한다.
6. 관리자 전환 화면에서 원장 대사와 초안 잔여를 확인한다. 기존 위치별 실물을 실제 품질에 따라 S/Q/B 및 목적 위치로 분할 매핑한다. 가용 상태를 자동 가정하지 않는다.
7. 백업 확인과 전환 영향 확인 후 확정한다. 미확인 응답은 같은 요청으로 결과를 확인한다. 수량 합계, 신규 원장, 기존 전표·원장 보존을 확인한다. 전환한 창고의 기존 재고 변경은 차단된다.
8. 수령→검수→적치, 예약→피킹→포장→인계 표본을 확인한 후 책임자가 제한 재개를 기록한다.

### 실사 품목 보호 보강 이관

`1792368000020_v2-count-master-usage.sql`은 21번째 마이그레이션이다. 장부에 없던 품목을 실사에서 새로 발견한 경우에도 계수·승인 대기 중 비활성화를 막는다. 기존 0019 파일을 바꾸거나 데이터를 초기화하지 말고 새 이관을 적용한다. 서비스와 직접 SQL 변경은 같은 보호 함수를 사용하며, 증분 적용 후에도 저장된 `search_path`의 마지막 `pg_temp`와 기존 소유자·권한이 유지되어야 한다.

이관을 되돌리면 신규 발견 품목 보호가 사라진다. 되돌리기 전에 해당 품목의 진행 중 실사를 확인하고 기준정보 변경을 중지해야 한다. `42331d6` 이미지의 schema20 검증은 이 이관의 검증 근거가 아니다. schema21 전체 회귀·별도 복원 결과는 최신 보고서의 실행 상태를 확인한다.

## 관측과 교대

### 외부 엑셀·타 시스템 개시재고

외부 자료는 기존 MVP 잔량 전환과 별도 경로로 처리한다. 기존 전표·원장·잔량이나 v2 실적이 있는 창고에는 외부 개시재고를 더할 수 없다. 새 창고에 필요한 품목·위치 코드를 먼저 등록하고 `item_code,location_code,bucket,quantity` CSV를 준비한다. 상태는 S(보관), Q(검수·적치 대기), B(보류), 수량은 정수 EA이며 한 회차는 최대 1,000행이다. 원본 시스템명·추출 시각·실물 대조 근거를 함께 제출한다.

미리보기는 현재 회사·창고의 활성 코드와 상태별 위치 유형을 대조한다. 제출 회차는 원본 CSV, 원문 SHA-256, 코드 대응 결과, 행별 오류, 제출자를 불변 기록으로 보존한다. 오류가 있는 회차는 승인할 수 없으며 원본을 수정해 새 회차로 제출한다. 제출자와 다른, 같은 회사의 승인권자가 실물을 확인하고 승인 또는 반려 사유를 남긴다. 승인 시 참조 정보를 다시 확인하고 개시재고와 승인 이력을 한 트랜잭션으로 반영한다. 승인 응답이 불명확하면 같은 요청으로 확인한다. 승인 이후에는 기존 전표 쓰기가 차단되며, 같은 물건을 기존 입고나 외부 개시재고로 다시 넣지 않는다. 과거 거래 이력을 임의의 입고·피킹 실적으로 재구성하지 않는다.

운영 책임자는 창고별 모니터에서 원장 불일치, 오래된 접수 사건, 격리 사건, 장기 예약, 백업·복구 증거를 확인한다. 독립 실행 명령과 결과 형식은 [모니터 계약](v2-monitor-contract.md)을 따른다. `unknown`은 성공이 아니라 증거·설정 부족을 뜻한다.

교대 전에 미확인 확정 결과를 해소하고, 미수령·미적치·미피킹·미출하·승인 대기에 다음 담당자와 사유를 지정한다. 보고서는 확정 시각의 상태를 보존한다. 이후 실적을 이전 보고서에 덮어쓰지 않는다. 자동 잠금은 기본 15분이며 관리자 설정에서 1~240분으로 변경한다. 만료 1분 전 경고하며 오프라인에서는 먼저 화면을 잠그고 연결 복구 후 세션 종료를 재시도한다. 서버도 보호 API의 유휴 기간을 검사한다. 공용 단말은 인계 후 로그아웃하고 다음 사용자가 자신의 계정으로 로그인한다.

실제 운영 시작 전에 지원시간, 경보 수신자, 현장 연락자, 장애 대응 책임자를 지정해야 한다. 현재 저장소에 외부 수신자나 실제 알림 발송 성공을 가정한 값은 두지 않는다.

## 장애·복구

1. 신규 확정을 중지하고 영향 회사·창고, 서버 시각, 요청 ID, 마지막 확인 결과를 기록한다. 암호·토큰·전체 요청 원문을 장애 기록에 넣지 않는다.
2. 재접속 후 동일 요청 ID 조회로 미확인 결과를 확인한다. 성공한 요청을 새 키로 재전송하지 않는다.
3. DB 복원이 필요하면 원본을 덮어쓰기 전에 별도 대상에 복원한다. 체크섬, 마이그레이션, 사용자·권한·키 상태, 불변 원장, 예약, 작업, 외부 사건·중복 식별자를 대조한다.
4. 시뮬레이터 SQLite 저널도 보존한다. 중단 전 전송 사건을 서버에서 조회한 후 같은 키로 재개한다. 복원된 서버에서 확인되지 않는 실적은 자동 성공으로 간주하지 않는다.
5. 외부 사건·작업·원장·예약을 대사하고 예상 밖 대기·격리·결과 미확인을 해소한다. 책임자 확인 후 제한 재개한다.

DB를 되돌리면 새 버전에서 발생한 정상 실적도 사라질 수 있다. 전환 뒤의 복구는 단순 앱 버전 되돌리기로 끝내지 않으며, 전환 이후 실제 입출고 기록과 외부 사건을 함께 대조한다.

## 아직 실제 환경에서 확인할 조건

RPO 15분·RTO 2시간은 목표다. 일회성 dump/restore 시험만으로 충족했다고 기록하지 않는다. 호스팅 백업 주기·보관·복원 지점·별도 환경 복원 시간, 실제 PC·태블릿·스캐너, 현장 승인과 5영업일 운영 대조는 해당 환경에서 실행한 근거가 필요하다.
