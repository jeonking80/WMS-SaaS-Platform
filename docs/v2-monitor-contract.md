# V2 operations monitor

`GET /api/v2/operations/monitor?warehouse_id=<uuid>` rechecks an active admin/supervisor membership and explicit warehouse grant. The result is limited to that tenant and warehouse. It reports `status` (`ok`, `warning`, `critical`), `checked_at`, `checks`, `alerts`, and `notifications`. Every check includes its status and evidence/details. Missing schema, backup evidence, restore evidence and delivery configuration remain `unknown`; they never become a successful check by default.

Checks include DB connectivity/schema readiness; an independent persisted ledger-to-stock full join; integration pending count/oldest age, quarantine and rejection counts; live reservations older than 24 hours; and backup evidence older than 26 hours. Pending integration events warn after 15 minutes. Reservations without their own timestamp use the explicitly labelled order creation estimate; missing both timestamps warns with unknown age. No physical stock changes, queue processing, notification sending or restoration occurs.

Standalone command (exit 0 healthy, 1 warnings/unknowns, 2 critical):

```bash
node --env-file-if-exists=.env.local scripts/v2-monitor.mjs
```

Required operator configuration: restricted `DATABASE_URL` using `wms_app`, `WMS_MONITOR_TENANT_ID`, comma-separated `WMS_MONITOR_WAREHOUSE_IDS`. It runs in a repeatable-read, read-only transaction with the tenant RLS context and explicit SQL tenant/warehouse filters. Stdout is one structured JSON report; connection/configuration failures are sanitized and report critical readiness failure.

Optional `WMS_BACKUP_EVIDENCE_FILE` points to JSON `{ "tenant_id":"...", "completed_at":"ISO timestamp", "archive_sha256":"64 hex characters", "restore_verified_at":"optional ISO timestamp", "provider_restore_verified_at":"optional ISO timestamp" }`. A company map `{ "tenants": { "<tenant UUID>": <same record> } }` is also accepted. The monitor reports this as recorded evidence, without exposing archive paths or claiming a fresh provider restore. Missing, invalid, foreign-tenant or unreadable evidence is unknown.

The monitor also reports `low_available_stock` using A (S−R at active STORAGE locations, excluding master, shortage and count blocks), compared with active item `min_stock` in the selected warehouse scope. `operational_kpis.details` includes its captured time, 24-hour window, committed command counts and per-command EA, open-object waiting age, overdue open orders, and count differences. Every denominator and time scope is stated. Count differences cover recorded rows in the captured selected warehouse state. Replayed requests do not count as new throughput.

API requests emit structured correlated logs and migration 15 adds durable `api_request_metrics`. When available, the monitor reports rejected scan validations / all order.pick requests and HTTP 5xx / all telemetry-recorded requests after successful tenant/warehouse authorization in the last 24 hours, with HTTP 4xx separately counted. Empty windows are `no_samples` (0/0), never a claimed zero-percent error rate. Missing telemetry remains `not_measured` with null values. The scan ratio describes rejected server validations, not physical damaged/mis-picked items. Overdue orders, rejected pick scans, or a technical failure ratio above 0.1% warn. API latency p95 uses these recorded requests. DB probe latency measures a single round trip on the acquired connection; connection setup time remains unmeasured.

`withTenant` marks each transaction with an opaque SHA-256 scope in PostgreSQL `application_name`. A warehouse enters the tag only after successful live authorization recorded by the server; tenant-only/background work receives a separate tag. `database_lock_wait` joins `pg_locks.waitstart` to the current database role's explicitly tagged tenant/selected-warehouse sessions. It reports current waiting-request count and maximum/mean elapsed lock wait in milliseconds. It returns no PID, query, actor, or other warehouse/company metadata and needs no `pg_monitor` grant. Tenant-only/unattributed work and completed waits are explicitly excluded; this is a current snapshot, not lock history. A live wait warns; unknown start time or unavailable statistics remain unknown. Actual PostgreSQL regression induces simultaneous same-role waits in two warehouses and a foreign company, verifies only the requested warehouse is counted, and excludes an unclassified tenant-only wait.

Alerts include `tenant:{id,name}`, `warehouses:[{id,code,name}]`, `references:[{kind,business_id,business_number,request_id}]`, `observed_at` and `action:{path,authorization}`. Actual order UUIDs, integration event IDs/queue sequence numbers, and persisted failed-request UUIDs are used where applicable. Aggregate/configuration alerts have no invented business/request number. References are capped at ten and contain no raw event, address, token, SQL, or error detail. Links use `/dashboard/v2?warehouse_id=...&tab=...&object_id=...` or `event_id=...`; login, active manager membership and explicit warehouse access are rechecked by existing API boundaries. An unavailable warehouse yields no actionable identifier/link.

The GET API only collects. An operator enables CLI delivery with `WMS_ALERT_WEBHOOK_URL` (HTTPS, no URL user/password/query/fragment), `WMS_ALERT_OUTBOX_FILE` (private SQLite file), and optional `WMS_ALERT_WEBHOOK_TOKEN` (Bearer header). No default external destination is configured. The operator controls the receiver and its authorization; the webhook URL/token never enter stdout or persisted payloads. Node 24 with `node:sqlite` is required. The CLI commits the report's allowlisted envelopes to a 0600 SQLite outbox with FULL synchronous durability before network I/O. Delivery uses a five-second timeout, refuses redirects and accepts only HTTP 2xx. The receiver must persist `Idempotency-Key`/body `dedup_key` and atomically suppress duplicate effects: an accepted response lost before local acknowledgement can be sent again.

Repeated observations of the same active incident in the same company/warehouse/receiver scope enqueue once. A successful report without that incident resolves it; recurrence gets a new dedup key. Failed delivery survives process restart, retries after 30 seconds with exponential backoff capped at one hour, and remains as `failed` after eight attempts. Configure a periodic operator scheduler to invoke the CLI; the script does not install one. `WMS_ALERT_DRAIN_ONLY=true` retries persisted due entries without a DB connection; add `WMS_ALERT_REQUEUE_FAILED=true` only for an operator-directed retry of terminal failures. The SQLite outbox is operational state and requires its own protected backup and disk-capacity management; application DB dumps do not include it.

`notifications` reports enqueued/sent/retained/failed counts. HTTP acceptance proves receiver transport acceptance only; it does not prove a human read or acted on the alert. Unit tests use a local loopback receiver for failure/restart/retry/dedup and redirect refusal. Actual external delivery, operator scheduling and real-recipient acknowledgement have **not** been executed.

The outbox also retains the last successfully collected exact company/warehouse/receiver context. On a DB outage the CLI can enqueue a sanitized critical readiness alert using that cached metadata; it labels the metadata as previously observed, invents no business/request number, and does not resolve other active incidents. A never-observed or changed scope is not sent as a verified warehouse alert. In-flight leases expire after a process crash so due deliveries can resume from disk.
