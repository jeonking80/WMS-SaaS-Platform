# Performance candidates and deferred options

The working source now includes optional Node cluster deployment support and per-request lookup indexes as candidates for validation. Full local application verification with `WMS_STANDALONE=1` passed; the later external supervisor follow-up and its focused checks are recorded below. The cluster option has not been adopted for production, an actual Docker image has not been qualified, and no measured throughput benefit is established for either candidate. Complete-state caching and copy-on-write remain deferred. The fourth official run failed acceptance, fixed-cohort recovery and completion; its zero normal-window technical failures do not establish G3 qualification. See [fourth-run evidence](v2-congestion-fourth-final-recovery.json).

## Per-request lookup indexes in the current candidate

`location-projection.ts` builds a first-match location map and blocked-location set from the current authorized references for each projection. Both engine stock annotation and response stock annotation use it. `snapshot` constructs one set of currently counting/submitted locations for A/locked projection. `scan-reference-index.ts` creates lazy first-match indexes for lots, reservations, picks and document lines during each scan normalization call. The indexes retain original row references and collection precedence, and the scan helper preserves the old missing-ID, strict-match and malformed-row lookup behavior at the original validation point.

These indexes exist only within the current call. They do not cache warehouse bodies, permissions, names or results across requests or transactions. The complete state read, isolated command clone, current reference queries, live authorization, scan/barcode validation, stock comparison, legacy hydration, and full state/ledger/reservation reconciliation remain in place. State arrays and response scope are not truncated. No workload rates, durations, timeouts, resource limits or acceptance thresholds change. Reducing repeated local scans is an implementation hypothesis; there is no measured throughput or official acceptance claim for these changes.

The ordered JSON aggregation reader remains rejected as a performance fix: the bounded [row-versus-aggregate comparison](v2-state-reader-comparison.md) was slower for that candidate, and the current baseline retains ordered body rows. The cache prerequisites below remain unresolved; these request-local indexes do not supply a cross-transaction content revision.

## Complete-state cache

Current reads lock the warehouse header, then fetch every ordered body in `src/server/v2/workflow/object-storage.ts:25`. Writes preserve a pre-hydration serialized baseline (`:21`) and compare all bodies (`:38`). `workflow/index.ts:23` additionally checks stock, and `:176` performs response hydration, projections and reconciliation. These steps remain required on a cache hit. Authorization must remain live, before the locked read.

A version-only process cache is unsafe today. The legacy compatibility trigger in migration `1792368000019_v2-object-state.sql:108` writes `NEW.version` and `NEW.updated_at` without requiring either to change. A legacy body rewrite can therefore retain the same business version and timestamp. The application role also has direct header/body DML grants. Neither business version, timestamp, body count nor maximum changed-version proves that all body content is unchanged.

A cross-transaction cache requires these prerequisites:

1. A database-enforced content revision covering every supported header/body writer, including compatibility writes, inserts, deletes and maintenance paths. Use an opaque never-reused generation or suitably managed sequence plus database-incarnation epoch; do not rely on `xmin` as a durable cache protocol. All writers must retain header-before-body locking. A body trigger that acquires the header only after a body row is locked can introduce a lock-order inversion. Legacy-version compatibility and direct-DML policy need explicit review before choosing revision enforcement.
2. Cache lookup only after the normal header lock is acquired and the current content revision, business version and storage format are read. Key scope includes process pool/database incarnation, tenant and warehouse. A miss follows the existing separate post-lock body query; never merge the pre-wait statement snapshot with a body cache fill. Recheck live authorization/RLS visibility first; never cache actor names, permissions, response projections or repaired state.
3. Cache only the complete exact persisted state, including all ordered arrays, empty placeholders, duplicate IDs, JSON null/scalar bodies and extension fields. Give each operation an isolated mutable working graph; never hand the cached baseline to hydrators or the engine. The immutable serialized persisted baseline must remain distinct from legacy repairs and approval-separation changes so legitimate repairs still persist.
4. Publish only committed persisted content. `withTenant` (`src/server/db/tenant.ts:8`) owns COMMIT/ROLLBACK, while `writeWorkflowState` executes earlier. A generic after-COMMIT callback is insufficient unless it handles savepoints: integration processing creates `integration_business` at `src/server/v2/integration/index.ts:125` and can roll it back at `:138`, then commit a business-rejection status. A candidate captured inside that savepoint must be discarded on rollback, or publication must prove its revision survived the outer commit. Multiple writes must publish only the last surviving candidate. Commit failure, connection loss and uncertain commit must publish nothing.
5. Capture a detached candidate at the persistence boundary rather than retain mutable `after` references. Compact `databaseSnapshot` uses shallow sharing for some bodies before legacy hydration; a later clone of that reference can include changes not represented by the persisted SQL. Request-level maps must not retain discarded transaction graphs.
6. Bound payload bytes, entries and single-entry size, with LRU eviction and no business effect on cache failure. A possible starting envelope is 64 MiB owned serialized payload, 32 warehouses and 8 MiB per entry, with oversized entries bypassing cache. These are design values, not measured sizing. Raw JavaScript object graphs and baseline maps need additional accounting; logical JSON bytes do not guarantee actual heap usage. A serialized-buffer cache provides a clearer payload bound but retains parse/copy cost. Monitor RSS/heap and include transient per-request copies and per-process multiplication in the shared memory budget.

A token checked under every lock handles writes from other processes without relying on notification delivery. Notifications may accelerate eviction but cannot establish correctness. Restore or migration must change the database incarnation or restart/clear caches. Header deletion/recreation must never reuse a valid token. Cache publication racing a later commit may at worst leave a stale entry that fails the next token check; it must never return that entry as current.

This is a substantial storage/transaction protocol, not a small optimization. Existing measured state-read awaits include locks, SQL, parsing and event-loop delay, so their total is not an estimate of removable cache cost.

## Copy-on-write alternative

`engine.ts:38` deep-clones the full original state before command execution; `:93` updates stock annotations and reconciles the complete result. A transaction-local copy-on-write draft could retain all state and clone only mutated branches, with the same final reconciliation and persistence diff. It does not require distributed invalidation or a new database revision, making its consistency boundary narrower than a process cache.

It still needs a complete mutation audit. Commands mutate nested lines, lots, reservations, picks, package state, approvals and arrays; stock annotation touches every stock row. Legacy hydration runs before the engine, and compact snapshot hydration can mutate shared bodies afterward. Draft escape, shallow nested sharing, array reorder/delete, alias reuse and exception paths could corrupt the original. A shallow top-level spread is not sufficient. No special hot/cold path or skipped validation is acceptable. Keep `bodyBaseline`, replay checks, scan/reference checks, stock comparison and persisted ledger reconciliation exact. Compare a reusable transaction-local draft implementation against the existing engine with both complete states/results and unchanged original input, including failures. This option targets clone cost only; it does not remove body reads or reconciliation.

## Fourth-run observation and limits

Frozen build `9xt7hww5jhA_G4dbro5r6` / commit `9d9e608` ran the unchanged 5,400-event profile with diagnostics off and the adopted 5-second server budget. Processor client timeouts were zero, but final normal acceptance p95 was 1,919/1,913ms and fixed recovery/completion failed. Both original final boundaries were exported completely and independent physical bucket conservation had zero differences; unfinished originals still failed. A single workflow GET was cancelled at the original 35-minute deadline, outside the normal window. The first three failures remain unchanged.

Two read-only OS samples, 37.73 seconds apart during fallback, observed 39.32 server CPU-seconds (1.042 average cores) and 83.54 cgroup CPU-seconds (2.214 average cores), in the visible application controller cgroup, which reports four cores/32 GiB. Later inspection could not establish that Docker PostgreSQL shares that effective ancestor; these samples do not measure a proven combined application/database envelope. Throttling increased by one period/0.0074 seconds. This establishes usage during that interval, not JavaScript event-loop saturation, a database wait cause, spare capacity across the full run, or a measured benefit from two processes. No cluster/cache/copy-on-write candidate was applied to the official frozen runtime.

## Optional Node cluster under the same budget

The default Docker runner still executes one `node server.js`; `npm start` still executes one `next start`. The current optional implementation is `deploy/cluster-launcher.mjs` with `deploy/compose.cluster.yaml`: one database-free Node primary supervises one or two identical standalone workers sharing one port with `SCHED_RR`. This uses Node's standard cluster facility, with no HAProxy, added reverse-proxy hop, request replay or new integration worker. The existing public origin and TLS/header-trust policy remain unchanged. Scheduling balances new TCP connections; keepalive may pin a client's requests to one worker. No benchmark-only affinity or client connection changes are allowed.

Each worker has its own JavaScript event loop and heap. Different warehouses may execute CPU work concurrently, while PostgreSQL still serializes work on one warehouse. This can also increase contention and memory consumption. The observed four-core/32-GiB host quota does not prove idle CPU, an event-loop bottleneck or a benefit from two workers. The overlay requires an already reviewed parent cgroup shared by database, web, background worker, existing local TLS proxy and diagnostic client; it does not create or enlarge those limits. Two heaps and framework caches consume the same total memory budget.

`WMS_DB_POOL_MAX` is now validated in the web pool configuration. The launcher partitions the unchanged configured web maximum of five into five for one worker or three plus two for two workers. Authentication, readiness, telemetry and business work share each worker's existing pool; the primary has none. Operations credentials are rejected, and no new operations connection is part of the workload. A replacement starts only after its predecessor exits, but configured3+2 alone does not prove that all dead-worker PostgreSQL backends have disappeared before replacement. The absolute live-backend cap remains an isolated real-PostgreSQL lifecycle gate.

The supervisor implements current-worker readiness reports, bounded crash replacement, shutdown admission control and drain acknowledgments before SIGTERM. API handlers, telemetry and tracked identity work retain their lifecycle barrier even after a client disconnect. Expiring per-operation tokens prevent detached descendants from bypassing drain. Namespaced IPC contains health/lifecycle metadata, and rejected new work uses fixed-label minimal telemetry. The independent static review corrected inherited-environment leakage and nested-operation drain accounting before source application. This does not establish actual Next preload/bundle behavior, complete SSR streaming drain, Docker packaging, or live auth/transaction correctness. Docker health status alone neither removes traffic nor restarts an unhealthy live process; the deployment edge still needs a reviewed readiness policy. Details and remaining gates are in [the cluster option](../deploy/cluster-option.md).

Business state, sessions, idle-lock updates, authentication rate limits and integration scheduling remain database-backed. PostgreSQL request/header/entity/advisory locks, transaction-local tenant context and RLS remain authoritative across workers. Full state, live authority and reconciliation are preserved; no new business cache or in-memory correctness lock is introduced. Both workers must share the same image/build, public origin, auth secret and compatible framework deployment settings. Framework cache coordination and version skew remain runtime review items.

Before a throughput comparison, qualify the actual standalone image and lifecycle against an isolated schema-20 copy: cross-worker authorization/revocation and idle lock; concurrent original-key replay and writes; tenant/warehouse isolation; disconnect and worker death around commit; startup/readiness/replacement; ordinary and disconnected-handler shutdown; actual connection cap and independent stock/ledger conservation. The passing local application verification does not replace these runtime gates.

A controlled comparator must use the identical build/schema, two logically identical fresh database copies, fixed cohort and unchanged rates/timeouts/checks/instrumentation, configured connection cap five, and the same total parent CPU/memory envelope. Compare one worker with pool five against two with pools three/two; an additional one-worker launcher arm can measure primary overhead. Preserve the existing edge path in both arms; do not introduce HAProxy solely for this option. Capture per-PID CPU/event-loop delay/RSS and requests, aggregate cgroup CPU/throttling/memory, database waits and pool pressure, complete request outcomes, committed cohort throughput, replay/auth behavior and fixed-boundary conservation. Diagnostic improvement alone would not establish production adoption or G3 success; required official qualification remains separate. The previous four official failures remain evidence against declaring completion.
