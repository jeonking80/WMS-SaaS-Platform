작성: 2026-10-20 UTC. **설계 검토안이며 아래 구조 변경은 미구현, 효과는 미계측이다.**

이 문서는 현행 시험의 실패를 통과로 바꾸거나 기획서의 목표를 변경하지 않는다. 원문 기획서 13장의 정상 접수 1초, 자동 반영 5초, 정상 교대 확정 1.5초, 혼잡 종료 후 10분 회복과 실제 8시간 조건을 유지한다. 외부 송신률 감소, 검증 삭제, 풀 크기 증가, HTTP 타임아웃 연장으로 통과를 주장하지 않는다.

## 현재 시험과 검토 범위

- 첫 혼잡 실행 `89990772-835e-4b2d-b9ee-4750ad668da0`은 실패했다. 실제 25분을 완료하지 못했고 미완료 업무가 남았다. 해당 run ID의 보존 보고서를 근거로 삼는다. `v2-congestion-full-latest.json`은 후속 실행 때 교체될 수 있는 최신 별칭이므로 내부 run ID를 확인해야 한다.
- 작성 시점 후속 혼잡 실행도 진행 중 성능 목표 미달이 보고되었다. 진행 중 수치는 최종 분포나 원인 측정으로 취급하지 않는다. 공급 종료 시점의 고정 peak backlog 판정과 추가 drain 최종 정합성 판정은 별개다. 35분에 최종 업무가 완료되어도 peak 종료 후 10분 회복 조건을 소급 통과시키지 않는다.
- 8시간 교대 실행은 시작하지 않았다. 준비된 사본, 기준 재고, 키는 시험 수행이나 합격의 근거가 아니다.
- 창고 전체 상태 비용의 구체적인 기여도와 아래 대안의 성능 효과는 측정하지 않았다. 이 검토 중 앱 소스 편집, DB 변경, 테스트 또는 부하 실행을 하지 않았다.

## 코드에서 확인되는 처리 경로

`src/server/v2/workflow/index.ts`의 `lockState`는 창고 상태 행을 `FOR UPDATE`로 읽고 정규 stock과 aggregate 일치를 확인한다. `engine.ts`의 `applyCommand`는 상태 전체를 `structuredClone`하고 업무 및 대사를 수행한다. `persist`는 변경 stock, 요청 결과, 새 원장과 작업 실적을 같은 트랜잭션에 쓰며, 전체 상태를 다시 JSON 직렬화하여 저장한다. 기본 응답은 추가 snapshot 계산과 직렬화를 포함한다.

누적되는 주문, 입고, 포장, 출하, 반품, 승인, 실사, 배정, 교대 자료가 이 경로의 읽기·복제·저장 크기를 증가시킬 가능성은 있다. 그러나 이것만으로 관측 지연의 주원인이 확정되지는 않는다. 풀 대기, 인증과 권한 조회, 잠금, SQL 왕복, CPU, GC, TOAST/WAL, 응답 생성, telemetry 저장을 분리해야 한다.

`src/server/v2/integration/index.ts`의 `processEvents(limit=50)`는 최대 50개 사건을 각각 별도 트랜잭션으로 순차 처리한다. 15초 HTTP 응답 타임아웃은 여러 사건을 처리한 배치의 합산 시간일 수 있다. 단일 사건 처리에 15초가 걸렸다는 증거가 아니다. 응답이 유실되더라도 이미 커밋된 사건을 재처리하여 중복 효과를 내면 안 된다.

## 대안 1: 객체 body 분리, 기존 창고 잠금 유지

가장 작은 구조 전환의 후보는 완전한 현재 객체 body를 별도로 저장하고, 창고 전체 JSON에서 누적 과거 body를 매번 복제·갱신하지 않는 것이다. 처음에는 창고 단위 `FOR UPDATE`와 전역 version 순서를 유지한다. 이 단계는 잠금 직렬화 자체를 제거하지 않는다.

새 `v2_workflow_object_state`를 예로 들면 회사, 창고, kind, ID, 객체 version, 마지막 변경 창고 version, hot 여부, 전체 body가 필요하다. 회사·창고 복합 FK, FORCE RLS, 실제 app 권한, scope/활성/부모 참조 인덱스도 필요하다. 기존 `objects`에 없는 승인·배정·교대까지 무조건 그 등록부의 FK로 연결해서는 안 된다. 등록부 backfill 및 kind 확장 여부를 먼저 정해야 한다.

같은 업무 트랜잭션에서 객체 변경, stock 변경, 불변 원장, 요청 해시와 결과, 작업 실적, 외부 사건·revision 반영, 창고 version을 함께 커밋한다. 외부 번호 유일성과 수령 ID 유일성은 기존 정규 테이블을 유지한다. 정상 업무 경로를 우회하는 시험 전용 저장 경로를 만들지 않는다.

기존 JSON을 보존한 채 전체 객체를 동일 ID/version/body로 backfill하고 독립 parity를 확인한다. 필요하면 한시적으로 같은 트랜잭션에서 dual write하여 읽기 전환을 검증한다. dual write 중에는 전체 JSON 쓰기 비용이 남으므로 이를 최종 성능 개선으로 주장할 수 없다. 명시적인 저장 형식 버전과 전환 경계가 필요하다. 전환 후 구 JSON을 원본으로 사용하는 롤백을 하려면 그 기간의 변경을 빠짐없이 되돌려 반영할 절차도 필요하다.

대형 JSON의 일부를 SQL `jsonb_set`으로 바꾸는 것만으로는 큰 JSONB datum과 TOAST 재작성 비용이 제거되지 않는다. JS의 전체 읽기와 복제가 남으면 효과가 더 제한될 수 있다. 이 방안도 측정 없이 근본 해결이라고 부를 수 없다.

## 활성 상태와 보존 이력의 경계

hot/cold는 보관 위치이며 업무의 영구 종료 선언이 아니다. 완료 주문의 연결 추가, 입고 수정, 배송 정정, 반품, 과거 실적 보상처럼 나중에 다시 필요한 자료를 요청할 수 있어야 한다.

- 주문은 모든 명세 수량이 취소·출하로 종결되고, 예약 잔량이 0이며, pick의 active/packed/cancel_pending이 0이고, 미완료 포장이나 관련 미결 승인이 없을 때만 hot에서 제외할 후보가 된다.
- 입고와 반품은 미수령 잔량, lot pending/normal/hold, 미해결 초과·마감 승인 등을 확인해야 한다. `closed` 한 필드만으로 결정하면 안 된다.
- 출하 인계 완료는 배송 완료와 다르다. `shipment.delivery`와 `shipment.delivery.correct`가 과거 출하를 조회·갱신할 수 있어야 한다.
- `return.request`는 같은 출하 명세의 **이미 닫힌 반품의 received까지** 누계하여 반품 한도를 계산한다. 과거 반품을 hydrate하지 않고 활성 반품만 보면 초과 반품을 허용한다.
- 보류 lot가 0이 되었더라도 원수령·초과 승인·원인 actor의 이력은 남아야 한다. 승인 분리 판단에서 과거 lot와 수령 actor를 찾을 수 있어야 한다.
- 배정은 현재 담당자 head를 빠르게 조회하되 이전 배정 이력을 보존한다. 교대 보고서, 완료·해제 실사와 결정된 승인은 이력 페이지에서도 조회할 수 있어야 한다.
- 진행 실사와 잠금, 위치 차단, 미결 승인, 미해결 수령·예약·피킹은 hot에서 제외하지 않는다. 실제 backlog가 증가하면 활성 자료도 증가한다. 최대 N개를 잘라내어 활성 크기를 제한하면 안 된다.

명령의 target뿐 아니라 참조하는 객체의 폐쇄 집합을 같은 트랜잭션에서 hydrate해야 한다. 대표적으로 package→order/pick, shipment→package/order, return→shipment와 이전 반품 누계, approval→lot/count/receipt, correction→원원장·요청·기존 승인, task→객체·현재 담당자가 포함된다.

현재 `reconcile`은 전체 주문의 예약 R 및 활성 pick P 합계와 stock을 비교한다. 단일 target만 로드하면 이 검증은 성립하지 않는다. 초기안은 모든 nonzero R/P와 미완료 업무를 hot에 유지해야 한다. 종결 객체 검증을 생략하려면 사전 검증된 불변 전체 body 버전과 검증 proof, 재변경 시 재검증이 필요하다. proof 없이 과거 명세 검사를 제거하면 검증 삭제다. 독립 전체 대사는 hot/cold 양쪽과 원장 전체를 검사해야 한다.

GET snapshot, 보고서, CSV, 원문 수량 oracle도 cold 자료를 계속 찾을 수 있어야 한다. 모든 명령의 응답에 cold 전체를 다시 조립하면 응답 CPU·전송 비용은 남는다. 같은 일반 업무 검증을 수행하는 최소 응답(version/result/변경 객체·위치)과 페이지별 이력 조회 계약을 검토할 수 있다. 기존 응답 호환과 UI의 명시적인 과거 자료 조회를 함께 설계해야 하며, 시뮬레이터만 검증이 덜한 응답 경로를 사용하게 해서는 안 된다.

## 대안 2: 객체별 동시 갱신

이 단계는 더 큰 변경이며 대안 1과 분리해야 한다. 대상 객체와 관련 stock 위치를 결정적인 순서로 잠그고, 같은 주문·위치의 경쟁만 직렬화하는 방식이다. 이동의 양쪽 위치, 여러 포장을 포함하는 출하, 반품 누계, 담당자 변경은 전체 참조 집합의 정렬 잠금이 필요하다.

추가로 다음을 설계해야 한다.

1. 요청별 advisory 잠금과 tenant/request 유일성으로 동일 키의 중복 효과를 막는다. 권한·담당자는 실제 쓰기 시점에 다시 확인한다.
2. 위치 실사의 lock은 현재 존재하는 stock 행뿐 아니라 새 위치별 stock 행의 phantom까지 막아야 한다. 위치 guard와 모든 물리 명령의 잠금 계약이 필요하다.
3. 짧은 전역 version 갱신을 마지막에 유지하더라도 원장 페이지 경계는 커밋 순서와 일치해야 한다. 단순 sequence는 낮은 version의 미커밋 원장이 이후 페이지에 나타나는 문제를 만든다.
4. reader의 header SHARE→stock SHARE와 writer의 stock UPDATE→header UPDATE 순서는 deadlock을 만들 수 있다. 읽기와 쓰기 전체 잠금 순서를 함께 정해야 한다.
5. 독립 snapshot은 repeatable-read MVCC 및 커밋 순서 version과 함께 설계한다. 여러 HTTP 페이지의 고정 원장 boundary를 유지한다.
6. shift.close, cutover, 창고 전체 대사 등에는 진행 writer를 포함하는 명시적인 barrier가 필요하다. pending correction이 현재 창고 version에 의존하는 기존 의미도 보존한다.

창고 잠금을 제거하는 코드를 먼저 넣고 나중에 이 조건을 맞추는 순서는 권하지 않는다.

## 필요한 계측과 회귀

계측은 응답 본문 전체 완료까지의 기존 client 시간을 유지하면서 서버 단계를 추가한다. 풀 연결 대기, 인증·권한 재검사, 창고/객체 잠금 대기, 상태 SQL 읽기와 JSON 크기·배열 건수, JS 복제·업무·대사 CPU, stock/원장/실적 SQL, 상태 직렬화·UPDATE·커밋, snapshot 생성, telemetry, 전체 batch 시간을 분리한다. 요청·사건·회사·창고와 단계 시간을 연결하고 비밀·원문 개인정보는 기록하지 않는다. 표본 계측 자체의 오버헤드도 공개한다.

피크 회사당 5개 외부 사건/초의 계획 비중은 대략 주문 3.5×4개 물리 명령, 입고 1×3개 물리 명령, 외부 생성·수정 5개로 회사당 약 22개 업무 쓰기/초를 요구한다. 정상 구간은 약 4.4개/초다. 실제 분할, 재시도, 조회, 배정은 별도다. 이는 부하 구조를 설명하는 계산이며 현재 시스템의 측정 처리량이나 병목 원인을 뜻하지 않는다.

구조 변경 시 최소 회귀 범위는 다음과 같다.

- 마이그레이션 전후 모든 객체 body·version·수량·actor·배송 스냅샷 parity, 재실행 가능성, 부분 실패 롤백, 복원·전환 후 재개.
- 같은 요청 중복·다른 본문 충돌, 수령 ID·외부 번호 재전송, 커밋 후 응답 유실 및 WMS 재시작 후 효과 1회.
- 다른 회사·창고 접근 및 RLS, 숨겨진 다른 창고의 공유 master 사용 중 비활성 차단, 권한 회수·담당자 변경.
- 같은 SKU/위치 동시 예약의 초과 방지, 양쪽 이동 원자성, 다중 포장 출하, 취소 후 복귀, 보상과 후속 업무의 경합.
- cold 출하의 배송 정정, cold 출하에서 복수·닫힌 반품 누계, cold 원주문 연결 추가, lot 기반 승인자 분리.
