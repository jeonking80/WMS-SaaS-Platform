# Bounded clone diagnostic procedure

Preparation only. Execution requires the root operator's go after local verification and the production build finish. This does not resume or replace failed run `c83531b5-faad-4e95-836e-26c7056ed465`.

Use only the separately restored schema-19 diagnostic database. Preserve the frozen schema-18 copy and verified source snapshot/dump; neither is a runtime target. The original source lived in the default development database, which was released for reuse after verified preservation; its current live contents are not the failed-run evidence. Private database bindings are in `/tmp/wms-diagnostic-c835-20261020-two-copy/clone-bindings.env`. Do not copy their values into evidence, logs, or arguments.

Start an isolated loopback runtime from the newly verified production build. Record its build ID, source commit/tree hashes, instrumentation module hash, runtime environment, pool settings, migration version and initial aggregate backlog status counts. Use `WMS_ENVIRONMENT=test`; diagnostics are enabled only when `WMS_TIMING_DIAGNOSTICS=1`. Keep the original port 3021 stopped. Derive machine-key environment bindings from the private authorized original launcher without printing them, and point private targets only at the diagnostic runtime.

The private runner JSON requires `diagnostic_only: true`, `database_schema_version: 19`, `build_id`, `instrumentation: "on"` or `"off"`, and the existing `targets` schema (`url`, `company_id`, `warehouse_id`, `source_key_env`, `process_key_env`, `worker_key_envs`). Reuse existing accepted backlog; no new source events, idempotency substitutions, forced retries, or original-profile resume.

After go, invoke `scripts/diagnostics/bounded-timing.mjs` with private binding path and sanitized output path, and environment `WMS_DIAGNOSTIC_GO=isolated-diag19`. It performs six sequential requests per target: test connection validation, workflow GET, process limits 1/5/50, workflow GET. Processing selects at most 56 events per target. A request failure stops execution without retry. A finally block atomically writes completed-request evidence plus a fixed failure category, including transport, response decode and timeout failures; it excludes raw errors. The client records complete response-body/JSON time and aggregate event statuses, excluding identities and payloads. Preserve safe `wms_timing_diagnostic` records separately from ordinary server logs, which may contain sensitive operational details.

Compare phase distributions and actual processed counts. Server spans are inclusive and nested; do not sum them. Client elapsed includes response transfer and decoding while server request time ends before diagnostic output and transport. Timer/bookkeeping/finalization measures cover only parts of instrumentation cost; output overhead is unmeasured. A meaningful enabled/disabled comparison requires the same build/configuration and equivalent fresh diagnostic restores, because each process request changes the backlog. Sequential off/on against one evolving copy is exploratory only. This tiny bounded batch cannot qualify load performance, hardware latency, or the failed run's recovery.

Stop the diagnostic runtime afterward. Preserve the runner output, safe span records, initial/final aggregate counts and exact build metadata; do not export auth values, business IDs, event payloads, raw SQL, or ordinary server logs into public docs.
