# WMS v2 누적 원장 조회 성능 시험

기준: [현장 운영 기획서 v1.1](WMS-현장운영-고도화-기획서.md) 13장. 실행기: [v2-performance.mjs](../scripts/v2-performance.mjs), [페이지 보존 검사](../scripts/v2-inventory-page-proof.mjs). 결과 원문: [v2-performance-latest.json](v2-performance-latest.json).

이 시험은 원장 100만 행이 쌓인 조건에서 실제 DB 쿼리, 인증된 업무 API, 브라우저 데이터 표시 시간을 측정한다. 교대 운영·혼잡·실기기·실제 배포환경 시험의 합격을 대신하지 않는다. 직접 SQL로 만든 이력은 조회 성능 준비 자료이며 수령·검수·적치 업무의 성공 실적으로 계산하지 않는다.

## 격리와 데이터

- 연결은 루프백 `TEST_DATABASE_URL`이며 DB 이름이 `_test`로 끝나야 한다. 실행마다 새 `wms_v2_perf_<run_id>_test` DB를 만든다. 기존 애플리케이션 DB와 기존 테스트 DB의 업무 자료를 변경하지 않는다.
- PostgreSQL의 DB 설명에 실행 식별자를 넣고 정리 전에 이를 확인한다. 다른 실행 DB·프로세스를 재사용하거나 종료하지 않는다.
- 회사 A/B 각각 창고 1개, 위치 20개(보관 16·수령/대기/출하/보류 각 1), SKU 100개, 위치·품목 잔량 1,600행, 원장 500,000행을 준비한다. 총 원장은 1,000,000행이다. 각 원장 효과는 S +1이고 1,600개 보관 슬롯에 312/313EA를 배분한다. 회사별 H/S는 500,000이고 R/P/Q/B는 0이다. 독립 기준값과 기준정보 식별자는 `v2-performance-baseline.json`에 저장하며 기대 수량은 WMS 응답이 아닌 생성 규칙에서 계산한다.
- 원장 20행마다 별도 준비 요청을 두어 총 요청 수는 50,000이다. 입력 사건·실제 작업 실적 수는 0이다. 주문·수령·피킹 이력을 만들어 업무 시험 통과로 제시하지 않는다.
- `ANALYZE` 후 측정한다. SQL 준비는 관리자 연결을 사용하지만 측정은 `NOSUPERUSER NOBYPASSRLS`인 `wms_app`과 FORCE RLS를 사용한다. DB 쿼리에도 현재 회사·사용자·창고 범위를 설정한다.
- API는 별도 포트의 사전 빌드된 Next.js 서버(standalone 산출물이 있으면 `/tmp`의 독립 사본)를 사용한다. `DATABASE_URL`은 전용 시험 DB로 바꾸고 `WMS_ENVIRONMENT=test`로 실행한다. 인증 계정은 이 DB에서만 발급한 합성 계정이다. 토큰·쿠키·암호·연결 문자열은 결과에 저장하지 않는다.

p95는 정렬한 성공 표본의 `ceil(n×0.95)`번째 값이다. 실패 요청을 빠른 성공으로 집계하지 않으며 오류가 한 건이라도 있으면 그 항목은 실패다. 원시 표본·표본 수·p50·p95·최댓값과 오류 수를 모두 보존한다. 동일 오류가 3회 반복되면 추가 표본 공급을 중지하고 실제 시도 수와 워밍업 실패를 기록한다. 이미 진행 중인 동시 요청은 정리한다. 일반 화면 목표는 데이터 표시 p95 2초다. API/DB 2초는 원인 분석용 부가 기준이며 화면 목표의 대체 근거가 아니다.

### 페이지 단위 표시의 다음 검증 계약 — 아직 미실행

UI의 100행 페이지와 검증 코드는 저장했으며 현재 25분 API 부하 실행 중에는 서버 준비·DB 조회·구문 검사·테스트·성능 측정을 실행하지 않는다. 현재 저장된 최신 결과는 아래 `_ceZRl`의 **1,600행 동시 DOM 실패**다. 페이지 단위 표시의 성공 근거가 아직 없으며, 부하 종료와 후속 구현 수정의 새 빌드/전체 회귀 뒤 실행 슬롯을 받아 측정한다. 현재 API 부하의 빌드와 후속 읽기 성능 빌드의 검증 범위도 분리한다.

새 표시 프로필은 `inventory-pages-v1`이다. 같은 전용 DB와 독립 manifest SHA `55e439d6049193d52295763a29042aa07c3a1fd27070da700df3b2b8204af7aa`, 총 100만 원장, 회사별 1,600개 위치·품목 자료를 유지한다. DB/API 쿼리 범위·항목별 100회·동시 5개·화면 회사별 10회·회사별 p95 2초·오류/누락/워밍업 실패 조건은 유지한다. 다른 표본 수/동시 수로 실행한 자료는 이 프로필의 합격으로 판정하지 않는다. 화면 표시량만 첫 페이지 100행으로 달라지므로 원래 1,600행 동시 DOM의 성공/실패와 직접 같은 조건으로 비교하지 않는다. 합격 측정 서버는 `WMS_TIMING_DIAGNOSTICS=0`을 명시해 별도 opt-in 단계 진단의 비용이 섞이지 않게 한다.

시간 측정은 기존처럼 진입 시작부터 재고 탭 선택, 첫 행 표시, 두 번의 animation frame과 화면 계약 확인까지다. 모든 측정에서 `data-stock-total=1600`, `data-stock-page-index=0`, `data-stock-page-size=100`과 실제 100행을 확인한다. 표본을 마친 뒤 별도 브라우저 문맥에서 A/B 회사 각각 다음 보존 검사를 수행한다. 이 검사 시간은 p95 표본에 넣지 않고, `inventory_preservation.passed`를 전체 합격의 필수 조건으로 추가한다.

- 16페이지를 순서대로 방문해 각 100행과 행당 두 추적 버튼을 확인한다. 1,600개 `(item_id,location_id)`의 합집합이 독립 생성 manifest와 정확히 같아야 하며 중복/누락/추가가 모두 0이어야 한다. 모든 행의 H/S/A/R/P/Q/B도 독립 기대값과 같아야 한다.
- 매 페이지의 7개 전역 합계가 페이지 크기와 무관하게 전체 1,600행의 기대 합계와 같아야 한다. 마지막 페이지에서 내보내는 CSV도 1,600행 전체이며 키·7지표·회사/창고/필터/시각/버전/EA/건수 metadata를 확인한다.
- 마지막 페이지의 품목·위치를 선택해 전체 자료 대상 품목 검색/선택 결과 16행과 품목+위치 1행, 전체 합계와 첫 페이지 초기화를 확인한다. 품목 필터 CSV 16행도 같은 독립 기준값과 비교한다.
- 필터를 해제하고 마지막 페이지로 다시 이동해 `연결 주문`의 실제 문맥과 `원장 추적`의 실제 조회 응답 범위를 확인한다. fixture에는 업무 주문이 없으므로 연결 주문 제목/문맥 확인을 예약 업무 성공으로 해석하지 않는다. 실제 예약 연결·모바일·빈 범위/페이지 보정은 UI 담당의 별도 E2E 범위다.

보존 검사의 원시 업무 응답이나 인증 자료를 artifact에 저장하지 않는다. 기준값/관측값 해시·개수·일치 여부·진행 단계별 오류만 남긴다. 기존 실패 원문과 진단 trace는 덮어쓰지 않는다. 새 실행 보고서에는 새 BUILD_ID/산출물 SHA, 벤치마크/보존 검사/UI 소스 SHA와 표시 계약을 함께 기록한다.

측정 업무/API 요청은 GET 조회 100%다. 정상적인 요청 지표·인증 세션 유지 쓰기는 발생할 수 있으며 물리 재고·업무 문서는 바꾸지 않는다. 스캔/확정 p95 1.5초, 외부 접수 p95 1초·반영 5초, 누적 원장 조건의 8시간 교대 부하, 혼잡 5,400개 고유 사건, 장애 해소 10분 기준은 별도 시험이다. 그 결과가 없으면 해당 항목은 미실행으로 남긴다. 로컬 루프백 수치를 공개 운영 지연으로 표현하지 않는다.

## 실행

빌드와 대규모 부하 시험은 측정과 분리한다. 저부하 회귀 검사 등 다른 프로세스가 함께 실행되면 보고서의 `concurrent_other_workloads`에 명시하고 독점 호스트 측정으로 표현하지 않는다. 실행기는 빌드하지 않는다.


브라우저의 최댓값은 1,587ms였다. PC Chromium과 API 클라이언트는 서버와 같은 컨테이너에서 루프백으로 연결했다. 전체 회귀 통합검사와 복구 드릴의 DB I/O가 끝난 뒤 측정했으며 장시간·혼잡 부하는 대기시켰다. 공유 호스트의 작은 편집·단위시험 프로세스까지 배제한 독점 호스트 결과는 아니다.

DB는 18개 마이그레이션이 적용된 전용 시험 DB이며 앱 역할은 `NOSUPERUSER NOBYPASSRLS`다. API/화면은 독립 standalone 사본의 빌드 `_P7skz_iVUWWknhOU9rgS`를 사용했다. 이후 추가된 승인 분리 보강·선택 포장 무게·배송 상태 정정·외부 개시 재고 화면 경로는 이 빌드 측정 범위에 포함되지 않는다. 최신 소스의 전체 경로 성능 통과로 확대해석하지 않는다.

초기 조사에서는 원장 500,000행 대사 SQL이 권한 함수의 행별 실행 때문에 단일 실행 10,187ms가 걸렸다. [계획 근거](v2-performance-rls-plan.json)에 같은 누적량에서 권한 범위를 문장당 한 번 계산하도록 변경한 전후 `EXPLAIN ANALYZE BUFFERS`를 보존했다. 테넌트 FORCE RLS와 창고 범위, 사람의 정지·권한 회수, 키 환경·만료·회수 검사는 유지했으며 실제 제한 역할의 SQL 보안 회귀를 통과했다. 이 초기 단일 실행은 최종 동시 5개 표본의 p95와 구분한다. [초기 진단](v2-performance-initial-diagnostic.json)의 API 503 및 브라우저 실행 오류는 시험 도구의 권한/실행파일 설정 오류였으므로 제품 API·화면 지연 판정 근거로 쓰지 않는다.

측정 서버와 독립 사본은 종료·정리했고 전용 DB는 후속 8시간 시험에 순차 인계하기 위해 보존했다. [독립 기준값](v2-performance-baseline.json)의 SHA256은 `55e439d6049193d52295763a29042aa07c3a1fd27070da700df3b2b8204af7aa`다. 측정 중 물리 재고 변경은 없었다. 후속 시험이 시작되면 이 DB에 읽기 성능 시험을 다시 실행하거나 정리하지 않는다. 8시간·혼잡·실기기·실제 제공자 복구 목표의 판정은 해당 별도 보고서를 확인해야 한다.
