## 이번 최종 대조에서 확인한 구현 차이

### 업무 엔진

1. `order.damage`와 `order.return_picked(outcome=hold)`는 B를 증가시키지만 해제 가능한 lot를 만들지 않았다. 최종 소스는 보류 lot와 `result.lot_ids`를 생성하며 원주문행/원요청 실적과 연결한다. 실제 PG 검사는 두 경로의 해제→검수→적치까지 확인한다.
2. `order.update`가 완료 포장 하나라도 있으면 배송지 변경 전체를 거절했다. 최종 소스는 미포장 잔량에 새 기본 주소를 적용하고 이미 완료/인계한 포장의 복사 스냅샷은 보존한다. 완료 포장 내용 자체를 바꾸려면 해제·재확인해야 한다. 실제 PG 주소/포장/정정 검사를 확인한다.

### WMS 화면

1. 일반 입고/반품의 검수 보류 lot는 API로 해제할 수 있으나 화면은 과납 lot와 `snapshot.holds`만 노출했다. 일반 품질 보류에서도 실물 확인→해제→검수→적치를 이어야 한다.
2. receipt/update의 `expected_at`, order/update의 `due_at`은 API가 지원하지만 수정 화면에 입력이 없었다.
3. 피킹리스트는 계획·출하·취소 수량의 일반 명세를 출력하며 실제 예약 출발 위치·품목·미피킹 예약 수량이 없었다.
4. 업무 홈에서 입고 지연/연계 오류의 해결 진입이 없고 재고 행에서 연결 주문·원장으로 좁히는 추적 진입이 없었다. 별도의 연계/원장 탭 존재와 업무 문맥을 유지한 진입은 구분한다.
5. 재고/원장/master/마감 CSV는 확인했으나 입고예정·주문·출하 전표 CSV는 없어 보강을 요청했다.

최종 소스에서 위 다섯 경로와 선택 포장 무게·명시적 배송 정정·외부 개시 수입 보강을 확인했다. `pickListRows`는 실제 예약 행의 원주문행·출발 위치·남은 예약·누적 피킹·담당자를 출력하며, `Update`는 변경 예정일/납기를 API에 전달한다. 일반 품질 보류는 입고/반품 예외 화면에서 해제할 수 있고 재고 화면의 연결 주문/원장 진입은 선택한 품목·위치 문맥을 넘긴다. 화면은 회사·창고·필터·버전 경계를 포함한 전표 CSV를 제공한다. 최종 브라우저 실행 결과는 주 작업자의 검증 기록을 따르며 이전 빌드의 실행을 새 경로의 합격으로 옮기지 않는다.

### 연계 오류 목록의 전체 범위

기존 화면과 GET 목록은 최초 100건만 가져와 화면에서 상태를 골랐고 다음 페이지·외부번호 검색이 없어 101번째 오류가 숨겨졌다. 별도의 실제 PG 시험에서 정식 접수한 101개 봉투를 조회용 상태(앞100 applied, 마지막1 quarantined)로 설정하자, 수정 전 오류 필터 요청도 applied 100건을 반환해 결함을 재현했다. 이 상태 fixture는 조회 검사이며 100개 업무가 성공했다는 근거가 아니다.

서버는 전체 조회 범위의 상태별 집계·상태 필터·정확한 외부번호/원천 검색과 100+1 sequence 페이지를 제공하도록 보강했다. 기계 키 원천 제한, 회사/창고 RLS와 기존 사건 단건 폴링은 유지한다. 독립 PostgreSQL 검사 4개가 수정 전 RED→수정 후 PASS이며 잘못된 입력400·다른 원천403·타회사/창고 건수0도 검사했다. [조회 근거](v2-integration-query-latest.json)를 따른다. 별도 신규 `v2-integration-list.spec.ts`는 빌드 `-oBhg3XQlSYuVZ5MbZfge`에서 실제 로그인·고유 회사/창고의 101건 fixture로 홈 오류→사건 선택·상태/원천/외부번호 검색·100+1 페이지·원래 사건 재처리와 무재고 효과를 3.1초에 통과했다. 전체 회귀의 다른 검사 결과와 이 개별 합격은 구분한다.

### 독립 시뮬레이터

현재 UI/`validateConfig`는 시나리오·모드·seed·사건 수·수량 범위·예정일/납기·작업자 수·공급 간격·중복/응답유실 토글·통신단절 시간을 지원한다. 기획 10.1의 근무시간, 부족/파손/중복/지연 **비율**, 작업자 역할/속도/오스캔/교대/중단 행동 편집은 지원하지 않았다. CLI의 고정 T 시나리오/부하 프로필은 해당 시나리오 실행 근거이며 편집 UI 구현의 대체 근거가 아니다. 실행 이력과 개별 JSON 보고서 보기/다운로드는 있으나 **실행 간 비교**도 없었다. simulator 담당자에게 묶어서 전달했다.

후속 보강에서는 위 설정을 저장·실행하는 `mixed_pattern`과 실제 `task.assign` 인계, 중단 후 동일 키 재개, 두 실행 비교 UI/API를 추가했다. [설정 실행 smoke](v2-settings-smoke-latest.json)는 실제 두 주문에 부족/파손/오스캔·중복·지연·응답유실을 적용하고 별도 감독자의 실물 처리와 인계·재개 후 독립 차이 0으로 통과했다. [브라우저 설정/비교 근거](v2-settings-ui-latest.json)도 통과했다. 설정을 적용할 수 없는 고정 수락 시나리오에 비율을 넣으면 거절하여 효과 없는 설정이 성공처럼 저장되지 않는다. 이 작은 설정 검사는 25분/8시간 규모의 통과로 확대하지 않는다.

독립 코드 읽기에서는 `validateConfig`→seed에 따른 실물 계획/`op.options`→SQLite 저장→runner의 실제 HTTP 실행을 확인했다. 근무시간은 Asia/Seoul의 실제 신규 발송 경계를, worker interval은 다음 명령의 영속 시각을, delayed 옵션은 사건별 추가 지연을 제어한다. 역할은 별도 supervisor 키에 연결하고 인계는 미확인 요청 정리 뒤 감독자 키의 정식 `task.assign`과 실제 새 담당자 검증을 거친다. 저장 smoke를 다시 집계하면 지연4·중복 확인4·응답유실24·중단1·인계1, 부족/오스캔 거절 각각2, 초기 발송28개의 시각 하한 준수, 최종 차이0/미완료0이다. 따라서 화면 필드만 추가한 상태와 구분된다.

### 운영 관측

초기 `database_lock_wait`는 자기 연결의 대기 잠금만 조회한 뒤 항상 `unknown/TENANT_ATTRIBUTION_UNAVAILABLE`을 반환했다. identity 담당자가 이후 성공한 회사·창고 권한의 SHA `application_name`과 `pg_locks.waitstart`를 사용하도록 보강했다. 담당자의 실제 PG 검사는 동시에 A1/A2/B1 창고의 잠금을 유도해 선택한 A1의 대기 요청 1개와 30ms 이상의 실제 지연만 집계하고 미분류·타사/타창고를 제외했다. `pg_monitor`, PID/SQL 노출 없이 관측하는 [계약](v2-monitor-contract.md)을 확인한다. DB 연결 항목은 현재 열린 pool 연결의 한 번 왕복 시간을 표시하고 연결 생성 시간은 측정하지 않는다고 명시한다.

## 외부 개시재고 독립 재검토

추가된 `operations/opening-import.ts`와 migration0017, 내부 opening 어댑터를 별도로 검토했다. CSV 원본·원본 해시·추출 시각·코드 대응·행 오류·요청자·별도 승인자·회차는 불변 테이블에 보존하고 테넌트/창고 FORCE RLS와 복합 FK를 적용한다. 기존 MVP 전표/원장/잔량/전환 이력이 있는 창고에 다시 개시재고를 추가하지 않는다. 이관 원장은 `EXTERNAL_OPENING`이며 수령 이력을 만들어 넣지 않는다.

리뷰에서 관리자 검사를 창고 잠금 밖에만 수행하던 경계를 찾아 잠금 후 같은 트랜잭션에서 현재 active 관리자·회사·창고 grant를 `FOR SHARE`로 재확인하도록 보강했다. 원본 조회 GET도 같은 방식으로 검사한다. 요청 키 advisory 잠금을 창고 잠금보다 먼저 잡아 회사 내 서로 다른 창고의 같은 키 충돌도 409로 처리한다. 빈 v2 상태는 JSON version뿐 아니라 영속 stock/ledger/request/object/performance/receiving 행도 확인한다.

수락 22개와 전환/외부 개시 11개를 함께 실행해 **33/33 PASS**(2026-10-20 13:26 UTC, 6.26초), 해당 TypeScript 검사를 통과했다. 외부 개시에는 같은 승인 동시 2회 중 1회 반영/1회 replay, 다른 창고의 같은 키 409, 실제 창고 잠금 대기 중 admin→worker 회수 후 승인 차단, 손상된 빈 aggregate 뒤 영속 v2 이력 거절을 포함한다. application_name 계측 변경으로 기존 잠금 관측이 달라진 수락 helper는 시험마다 독립 발급한 PG 역할과 현재 DB의 실제 `wait_event_type=Lock`을 확인하도록 수정했다. 대기 검사를 생략하거나 시간 경과만으로 통과시키지 않는다.

## 2026-10-21 후속 업무 흐름 대조

아래 누락을 추가로 확인해 수정했다. 집중 단위 검사 25개와 실제 PostgreSQL 수락 검사 25개는 통과했고, 통합 전체 회귀도 단위250·시뮬레이터55·PG191·브라우저44개 및 빌드 통과로 확인했다. 이 기록은 G3~G5 합격이나 전체 기획 완료 선언이 아니다.

- **RET-01 / OPS-02:** 미도착 승인 잔량을 마감한 반품에도 보류 실물이 남으면 다음 담당자와 사유를 요구한다. 엔진·진행 건수·교대 화면·시뮬레이터의 인계 조건을 일치시켰다. 기존 작업자는 차단되고 새 작업자가 보류 해제→재검수→적치를 이어 수행하는 PG 흐름을 확인했다.
- **INV-03 / OPS-02:** 계수 중 실사는 실사 작업으로 인계한다. 제출된 실사는 기존 승인 대기 인계로 처리한다. 시작자와 모든 실제 계수자 이력, 영속 기준 수량을 유지하며 인계 이후에도 두 계수자 모두 자기 승인이 금지된다.
- **INV-03 / AC-10:** 강제 해제된 실사의 오래된 승인을 반려해도 이전 실사와 기준 수량을 되살리지 않는다. 현재 제출 상태와 대상 버전이 일치할 때만 계수 중으로 되돌린다. 반려 이력은 남기되, 재계수는 새 실사를 시작해 이동 이후의 실제 장부 기준으로 수행한다. PG 검사는 이동 후 원위치8·도착위치2·총실물10을 보존하고 이전 실사의 재제출을 거절한다. 이전 빌드에서 전체 잘못된 차감 경로를 별도로 실행한 결과는 아니다.
- **OUT-04 / OPS-01:** 내부 포장명세에 고유 포장·주문·피킹·주문행 식별값, 회사·창고, 저장된 배송지, 출력 시각과 상태 버전을 표시한다. 현재 주문 배송지나 주소록으로 과거 포장 주소를 대체하지 않는다. 기존 출력 HTML 이스케이프와 출력 실패 시 무변경 동작을 유지한다. 실제 브라우저에서 현재 주문 주소 변경 후 두 번 재출력해 저장된 포장 배송지·식별값·출력 시각과 재고·원장·업무 상태 무변경을 확인했다.
