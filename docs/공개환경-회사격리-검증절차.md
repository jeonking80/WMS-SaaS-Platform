[실행 JSON](public-isolation-verification-latest.json)을 근거로 한다. 이전의 CONNECT403은 준비 단계 당시 기록이며, 이번에는 접근 허용 환경에서 실제 공개 앱 응답을 확인했다. 기존 [공개 UI 업무 검증](공개배포-검증결과.md)과 별도의 API 검사다.

## B 회사 준비

운영자가 B 생성 SQL 실행을 완료했다. 암호화 전달본은 기존 A 관리자 비밀번호를 메모리에서만 사용하여 AES-256-GCM 인증 후 복호화했고, B 회사 식별자를 확인한 뒤 원본 자격 파일을 `wx`·0600으로 복원했다. 평문·비밀번호를 출력하지 않았고 계정 재생성·초기화·비밀번호 변경은 하지 않았다. 아래 생성 명령과 SQL 안내는 최초 준비 절차이며, 이미 생성된 B 회사에는 재실행하지 않는다.

최초 준비는 공개 가입·회사 생성 API 대신 운영자 SQL 경로를 사용했다.

```sh
node scripts/generate-isolation-b.mjs
```

생성되는 `artifacts/neon-isolation-b.sql` 전체를 Neon SQL Editor의 `wms_demo`에서 초기화 소유자 계정으로 실행한다. 별도 회사 `71000000-0000-4000-8000-000000000001`과 세 역할 계정 및 합성 기준정보·전표·재고를 생성한다. 기존 A 회사 ID/이메일과 분리하며, B 회사나 계정이 이미 있으면 전체 트랜잭션을 거절한다. 기존 계정 암호를 재설정하지 않는다. 마지막 결과는 demo_users=3, credential_accounts=3이어야 한다.

`artifacts/neon-isolation-b-credentials.json`은 해당 SQL과 한 쌍이다. 두 파일은 0600 권한으로 독점 생성하며 기존 파일을 덮어쓰지 않는다. SQL에는 암호 해시가, JSON에는 비공개 암호가 있으므로 Git·채팅에 게시하지 않는다. 실행 환경을 옮길 경우 원래 SQL과 일치하는 자격 파일을 안전하게 사용해야 한다. 기존 B에 새로 생성한 다른 암호 파일을 사용하면 인증되지 않는다.

## 양방향 검사

앱에 접근 가능한 환경에서 A/B 파일을 준비한 다음 실행한다. Node 24의 지원되는 프록시를 사용하며 TLS 검증을 끄지 않는다.

```sh
NODE_USE_ENV_PROXY=1 PUBLIC_DEPLOYMENT_URL=https://wms-saa-s-platform.vercel.app \
  node scripts/verify-public-isolation.mjs
```

검사 범위:

- A/B 관리자 로그인, 실제 소속 회사 확인
- 상대 회사의 합성 전표·재고가 실제로 존재하는지 소유자 세션으로 먼저 확인
- 상대 품목 재고·원장 목록 0건
- 상대 전표 상세·확정 이력 직접 접근 404
- 상대 전표 취소 요청 404 (이미 확정된 합성 전표만 대상으로 하므로 초안 취소나 재고 거래를 실행하지 않음)
- 원래 전표·재고 미변경 및 원장 대조 일치
- 회사별 독립 세션, 요청 ID 및 no-store 응답

결과는 `artifacts/public-isolation/result.json`에 비밀 없이 저장된다. `completed:true`인 실행만 통과로 기록한다. 첫 오류에서 중단하고 비밀 포함 가능성이 있는 원문 네트워크 예외는 출력하지 않는다. 이 검사는 API 검사이며 별도 UI 검사를 수행했다고 기록하지 않는다.

## 준비 단계의 확인 기록

- 생성기와 검사기 Node 문법 검사 통과
- 생성 SQL의 B 전용 ID/이메일, DB 이름·기존 계정 거절 조건 확인
- 세 역할의 생성 암호가 SQL의 Better Auth 해시와 일치함을 실제 검증
- SQL에 평문 암호가 포함되지 않음을 확인
- 공개 검사 시도: 접속 차단으로 미완료. 공개 B 생성·로그인·격리 성공을 주장하지 않음
