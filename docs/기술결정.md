# WMS Lite 기술 결정

> 2026-10-20 결정: GitHub Actions는 사용하지 않는다. 자동 검증은 로컬 `npm run verify`로 대체한다.

작성일: 2026-10-19. 개발계획서 P0-01의 결정 기록이다. 실행 검증 결과는 [0단계 검증 결과](0단계-검증결과.md)에 별도로 기록한다.

## 1. 애플리케이션과 실행 환경

- Node.js 24.19.0, npm 11.9.0을 사용한다. `.nvmrc`와 `package.json`에 실행 범위를 기록한다.
- Next.js 16.4.2, React 19.3.1, TypeScript 7.0.2, Tailwind CSS 4.3.3으로 하나의 웹 애플리케이션을 구성한다.
- 패키지 직접 의존성은 정확한 버전으로 저장하고 전이 의존성은 `package-lock.json`에 고정한다. 재설치는 `npm ci`를 사용한다.
- App Router 화면과 Route Handlers를 사용한다. DB 연결이 필요한 경로는 Node.js 런타임으로 실행한다.
- 아직 업무 기능을 구현하지 않았으므로 첫 화면에는 초기 개발 상태를 표시한다.

## 2. DB와 마이그레이션

- PostgreSQL 17.9의 공식 `postgres:17.9-bookworm` 이미지를 사용한다. Docker Compose 실행 가능 여부와 이미지 다운로드를 현재 클라우드에서 확인했다.
- SQL은 `pg` 8.23.1로 실행하고, 마이그레이션은 `node-pg-migrate` 9.0.0의 SQL 파일 방식으로 관리한다. ORM은 추가하지 않는다.
- 개발 DB는 영속 볼륨, 통합 테스트 DB는 별도 컨테이너의 임시 볼륨을 사용한다. 테스트는 `_test`로 끝나는 DB 안에 독립 스키마를 만든다.
- 최초 마이그레이션은 회사 등록부 `tenants`를 생성한다. P1에서 인증·소속 테이블과 `items`·RLS 마이그레이션을 추가했다.
- `postgres`는 로컬 역할 준비에만 사용한다. P1의 앱 연결은 비소유자 `wms_app`, 마이그레이션은 소유자 `wms_migrator`로 분리했다.
- 시각은 `timestamptz`로 저장하고 업무 일별 집계·표시는 `Asia/Seoul` 기준으로 설계한다.

## 3. 인증 라이브러리 선택

Better Auth 1.7.11을 선택하고 정확한 버전을 설치했다. P1에서 인증 경로·세션·초기 계정·소속 확인을 구현했다.

선택 근거는 npm 공식 배포 패키지의 메타데이터·타입·구현을 확인한 결과다.

- Next.js 14~16, React 18~19 및 `pg` 8 계열 연동을 지원한다.
- `database: new Pool(...)`로 PostgreSQL 연결을 전달하고 `toNextJsHandler`로 App Router에 연결할 수 있다.
- 이메일·비밀번호 인증과 `disableSignUp` 옵션을 제공하여 공개 가입을 막을 수 있다.
- 인증 테이블은 `user`, `session`, `account`, `verification`을 포함한다. 비밀번호 해시는 라이브러리의 계정 생성 경로에서 처리한다.
- P0에서는 관리자 플러그인을 호환성 검사에만 사용했다. 실제 앱에는 관리자 플러그인을 넣지 않는다. 개발 계정은 별도 스크립트가 공식 `hashPassword`와 SQL 트랜잭션으로 생성하고 공개 생성 경로를 두지 않는다.

공식 웹 문서는 이 환경에서 접근이 거절되어 npm 배포물로 호환 인터페이스를 확인했다. P0의 `tests/integration/auth-library.test.ts`는 라이브러리 독립 호환성 검사로 유지한다. 실제 앱은 버전 관리 SQL 마이그레이션으로 인증 스키마를 만들고 P1 E2E에서 로그인·쿠키·세션·출처·회사 권한을 검증한다.

P1에서는 초기 계정 생성, 로그인·세션 확인, 로그아웃·만료, 공개 가입·잘못된 출처 차단을 확인했다. 쿠키 세션 캐시는 비활성화하고 역할·활성 소속은 매 요청 DB에서 읽어 역할 변경을 즉시 반영한다. 최초 소속 조회는 세션의 사용자 ID로만 수행하고, 그 결과를 트랜잭션의 회사 컨텍스트로 사용한다. 외부 배포는 HTTPS와 보안 쿠키를 요구하고, 로컬 프로덕션 빌드 검증에 한해 loopback HTTP를 허용한다.

인증 요청 제한은 라이브러리 기본값을 유지한다. 현재 단일 프로세스의 메모리 제한 저장소이며 여러 인스턴스에 배포하려면 P7에서 공유 저장소와 신뢰하는 프록시 설정을 검토한다. 테스트는 제한을 끄거나 IP를 위조하지 않고 Retry-After를 따른다.

참조: [Better Auth npm](https://www.npmjs.com/package/better-auth/v/1.7.11), [Next.js npm](https://www.npmjs.com/package/next/v/16.4.2), [node-pg-migrate npm](https://www.npmjs.com/package/node-pg-migrate/v/9.0.0).

## 4. 테스트와 CI

- Vitest의 unit/integration 프로젝트로 빠른 단위 검사와 실제 PostgreSQL 검사를 분리한다.
- Playwright는 프로덕션 빌드로 서버를 띄우고 Chromium에서 초기 화면·상태 확인 API를 검사한다.
- `/api/health`는 서버 응답 가능 여부, `/api/ready`는 실제 DB 연결과 최초 테이블 조회 가능 여부를 확인한다. 준비되지 않은 DB는 503을 반환한다.
- GitHub Actions는 잠금 설치·타입 검사·단위 검사·DB 마이그레이션·통합 검사·빌드·E2E를 실행한다. CI 실행 여부와 로컬에서 같은 명령을 실행한 결과는 구분해 기록한다.

## 5. 이번 단계에서 확정하지 않은 사항

반대 거래 모델, 멱등 응답 계약, 수량 상한·비활성화 규칙은 개발계획서의 해당 선행 단계에서 확정한다. 데모 배포 공급자와 비용은 아직 정하지 않았다. 현재 Docker 기반 독립 실행을 기준으로 앱·DB 자원 요구를 확인하며, 외부 데모 배포는 P7에서 진행한다.


## 2단계 결정 (2026-10-20)

- 전표 API 경로는 `/api/documents`로 확정한다. DB 테이블명은 inventory_documents/inventory_document_lines다.
- 기준정보 코드는 trim·대문자 정규화, 최대 64자다. 이름 최대 128자, 수량은 1~1,000,000,000 정수, 명세는 중복 없이 1~20개다.
- 기준정보를 삭제하지 않고 비활성화한다. 초안에서 참조 중인 기준정보 및 활성 위치가 있는 창고의 비활성화를 거절한다. 현재고 잔량 검사는 3단계에서 추가한다.
- 버전은 1부터 시작한다. 전표 행 잠금 후 비교·증가하며 명세 교체와 상태 변경을 같은 트랜잭션에서 처리한다. 참조 FOR SHARE와 기준정보 FOR UPDATE로 비활성화 경쟁을 제어한다.
- 자체 업무 API의 쿠키 인증 변경 요청은 JSON 및 설정된 인증 origin을 요구한다. DB 오류 상세는 클라이언트에 노출하지 않는다.
- 모든 검증은 로컬에서 실행한다. GitHub Actions는 만들거나 실행하지 않는다.


## 3단계 결정 (2026-10-20)

- 현재고는 bigint로 저장하고 누적 상한을 JavaScript 안전 정수 최댓값으로 제한한다. 조회 JSON에서는 문자열로 반환한다.
- 입고 확정은 전표 행 잠금과 회사별 멱등 키 advisory lock을 사용한다. 성공 응답까지 같은 트랜잭션에 저장하여 통신 실패 재시도를 지원한다. 성공 키를 임의 만료시키지 않는다.
- 원장·감사·멱등 기록은 앱 계정으로 수정·삭제할 수 없다. 현재고도 앱 DELETE를 허용하지 않는다.
- 조회자도 재고·원장·대조 조회는 허용한다. 전표 초안 접근 제한은 유지한다.
- 화면은 저장된 전표만 확정하며, 응답을 받지 못한 요청의 최초 키·버전을 sessionStorage에 보관한다.
- 실제 PostgreSQL 트리거 오류 주입과 독립 연결 잠금 경합, 브라우저에서 커밋된 응답을 차단한 재시도를 로컬 검증한다. 프로덕션 오류 주입 경로는 추가하지 않는다.


## 4단계 결정 (2026-10-20)

- 입고·출고는 공통 확정 서비스를 사용하며 기존 입고 멱등 키 해시를 보존한다. 출고는 출발 위치에서 음수 원장과 POST_OUTBOUND 감사 동작을 기록한다.
- 모든 품목 잔량을 일정 순서로 잠근 뒤 전체 수량을 검사한다. 부족 품목이 있으면 전체 미반영이며 없는 출고 잔량 행은 만들지 않는다.
- 확정 요청의 잠금 대기를 1초로 제한하고 잠금 실패는 전체 롤백 후 RETRYABLE_TRANSACTION으로 구분한다. 재시도는 최초 키·버전을 유지한다.
- 참고 재고는 위치·품목 필터로 조회해 목록 상한에 따른 잘못된 0 표시를 피한다. 화면의 값은 예약 재고가 아니다.
- 동시 출고 검증은 실제 잔량 행을 잠근 제어 연결과 독립 실행 연결을 사용하고, 두 요청이 DB 잠금 대기에 도달했음을 확인한 후 해제한다.


## 5단계 결정 (2026-10-20)

- 별도 취소 유형 대신 원본의 역방향 전표를 POSTED로 생성하고 reversal_of_id로 연결한다. 원본은 REVERSED로 바꾸되 posted_at을 유지한다. 반대 전표는 재확정·재취소할 수 없다.
- 취소 효과는 원본 원장의 증감을 반대로 계산한다. 원본·반대 거래를 각각 남기며 부분 취소를 제공하지 않는다.
- 입출고·이동·취소가 공통 재고 효과/잠금 함수를 사용한다. 위치·품목 UUID 순서의 잠금으로 반대 방향 이동에도 순서를 통일한다.
- 취소는 관리자만 허용하며 멱등 응답 재반환에도 현재 관리자 권한과 회사 접근을 검사한다.
- 비활성 기준정보의 과거 취소는 허용한다. 취소가 재고를 복구해도 기준정보 활성 상태는 자동 변경하지 않는다.
- 클라이언트는 취소 요청도 최초 키·버전을 보존한다. 상세에는 원본과 반대 전표 ID 및 각 처리 시각을 표시한다.
