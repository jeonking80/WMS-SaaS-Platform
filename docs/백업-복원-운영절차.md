# 백업·복원 운영 절차

백업에는 계정 해시·세션·업무 데이터가 포함될 수 있다. Git에 넣지 않고 접근을 제한한 저장소에 보관한다. 저장소의 `backups/`와 `artifacts/`는 Git에서 제외한다.

## 실제 복원 검증

```sh
npm run test:restore
```

이 명령은 현재 로컬 PostgreSQL 컨테이너 안에 임의 이름의 독립 소스 DB를 만들고, 빈 DB에 전체 마이그레이션을 적용한다. 합성 업무 데이터를 넣어 `pg_dump` custom 형식으로 백업하고 다른 새 DB에 `pg_restore --single-transaction --exit-on-error`로 복원한다. 데이터 지문·행 수·원장 대조와 제한된 앱 계정의 권한을 검증한 뒤 자신이 만든 DB와 파일만 정리한다.

`BOOTSTRAP_DATABASE_URL` 또는 `BACKUP_DATABASE_URL`의 로컬 postgres 연결이 필요하다. `BACKUP_CONTAINER` 기본값은 `wms-lite-db-1`이다. 연결 주소와 컨테이너의 PostgreSQL system_identifier가 같아야 한다. 이 스크립트는 기존 클러스터의 앱 역할이나 비밀번호를 변경하지 않는다.

## 최신 로컬 실측 결과

2026-10-20 13:21 UTC 실제 독립 DB 복원 검증은 **PASS**했다. 원본과 복원본의 40개 public 테이블 전체 행 지문과 모든 public 시퀀스 상태가 일치했고, 18개 마이그레이션·33개 강제 RLS 테이블을 확인했다. 신규 v2 테이블 23개 각각에 비어 있지 않은 합성 데이터를 넣었다. 외부 개시재고 원본 CSV 2건의 해시·추출시각·검증 행/오류와 승인/반려 결정 2건, 부모 연결·실행자·요청 ID도 보존하고 불변성 및 회사/창고 복합 FK를 확인했다. public 테이블이 추가되어 검증 목록에서 빠지면 테스트가 실패한다.

배송지 1건과 연결된 출고의 거래처·배송주소 스냅샷, 전표번호를 보존했다. 전표번호 1·2와 시퀀스 사용값 3의 간격도 보존했고, 복원 DB 시퀀스의 다음 값 4를 발급했다. 전환 완료 창고의 신규 legacy 전표는 계속 거절되는지도 확인했다. 기존 재고 70과 v2의 S50/R10/P5/Q12/B3(H70), v2 원장 6행 및 집계 상태를 독립 대사해 불일치 0건을 확인했다. 미처리 승인·작업 인수자, workflow 요청 응답, 적용 완료/재시도 대기 외부 사건, CSV 적용 이력, 성공/오스캔 거절 요청 지표, 소비된 재설정 링크와 교체/회수 키도 보존했다. 앱 계정 인증·권한 및 회사 격리도 통과했다. 원본 지문은 그대로였으며 생성한 두 DB와 백업 파일을 정리했다. 기존 개발 DB 업무 행은 수정하지 않는다.

비밀정보를 제외한 실행 결과는 [restore-verification-latest.json](restore-verification-latest.json)에 보관한다. 이 결과는 동일 로컬 클러스터 검증이며 원격 제공자의 복원이나 실제 HTTP 로그인까지 검증한 결과는 아니다. 합성 SQL fixture의 보존 검증이며 실제 업무 명령 실행 통과를 대신하지 않는다. PITR·외부 저장소 복원·실측 RPO/RTO는 미실행이다. 실행별 합성 DB 2개와 0600 백업 파일은 종료 시 정리한다.

덤프에는 SHA-256과 완료 시각을 부여하고, 체크섬이 다르면 대상 DB를 만들기 전에 복원을 거절한다. 전표번호와 연계 사건 sequence의 사용값 3을 보존한 뒤 다음 값 4를 실제 발급해 시퀀스 간격까지 확인한다. 제한된 앱 권한과 관리자 연결 양쪽에서 신규 불변 트리거도 검사한다.

최신 결과의 `tenants[합성회사UUID]`는 모니터가 읽는 증거 형식이다: `tenant_id`, `completed_at`, `archive_sha256`, `restore_verified_at`. `WMS_BACKUP_EVIDENCE_FILE`로 이 형식의 파일을 지정할 수 있지만, 이번 파일은 삭제된 합성 회사의 로컬 시험 증거이므로 실제 운영 회사의 백업 증거로 사용하지 않는다. `provider_restore_verified_at`은 실제 제공자 복구를 마친 뒤만 운영 증거에 기록하며 이번 실행에서는 생성하지 않는다.

## 로컬 DB 백업

```sh
npm run db:backup
```

기본 연결은 `.env.local`의 `BOOTSTRAP_DATABASE_URL`이다. 기존 파일을 덮어쓰지 않으며 새 파일을 소유자 전용 모드로 만든다. 기본 출력 경로와 크기가 출력된다. `BACKUP_FILE`로 경로를 지정할 수 있다. 백업은 RLS에 의해 일부 회사가 누락되지 않도록 관리 연결로 수행하며, 앱 웹서비스에는 이 연결을 제공하지 않는다.

## 별도 DB 복원

```sh
BACKUP_FILE=/안전한/경로/백업.dump \
RESTORE_DATABASE_NAME=wms_restore_review \
npm run db:restore
```

대상 이름은 `wms_restore_`로 시작해야 하며 기존 DB와 원본 DB는 거절한다. 실패 시 원본은 건드리지 않고 새 대상 DB를 남겨 조사할 수 있게 한다. 복원 성공 메시지만으로 서비스 전환을 하지 않는다. 행 수, 인증·소속, 회사별 재고 대조와 앱 역할/RLS 검사를 먼저 수행한다.

덤프는 DB 내부 데이터·스키마·권한을 보존하지만 클러스터 역할과 비밀번호 자체는 포함하지 않는다. 이 도구는 동일한 로컬 클러스터에 역할이 존재하는 복원 검증용이다. 다른 클러스터나 외부 제공자 복원은 역할 준비, 소유권 및 앱 권한을 별도로 적용하고 다시 검증해야 한다.

## 공개 데모 운영 시

Railway 등 외부 PostgreSQL에는 이 로컬 전용 스크립트를 그대로 적용하지 않는다. 제공자의 백업 기능 또는 PostgreSQL 17 클라이언트의 암호화된 관리 연결을 사용한다. 자격 증명은 제공자 비밀 설정이나 제한된 passfile로 전달하고 명령줄·로그·Git에 넣지 않는다. TLS 검증을 끄지 않는다.

권장 운영 기준은 매일 백업, 배포·마이그레이션 전 추가 백업, 보관 기간 7일 이상이다. 이는 운영 정책 제안이며 자동 스케줄이나 원격 백업 저장소를 이번 로컬 검증으로 구축한 것은 아니다. 실제 제공자 연결 후 저장 위치·접근 권한·보관 비용·복원 주기를 확정한다.

복원 후에는 `/api/ready`, 실제 로그인, 소속/역할, 회사별 `/api/stock/reconcile`, 대표 확정 이력을 확인한다. 이전 세션 유지 여부와 인증 시크릿 변경 시 재로그인 정책을 결정한다. 장애 원인이 데이터에 있으면 앱 이미지만 이전 버전으로 바꾸어 해결된다고 가정하지 않는다. 파괴적인 다운 마이그레이션을 자동 실행하지 않는다.

## 실제 HTTP 업무의 복원 후 재개 (T12)

`node --env-file-if-exists=.env.local scripts/v2-recovery-replay.mjs`는 기존 DB 대신 임의 이름의 새 source/restore DB와 전용 3301 서버를 사용한다. 사전에 검증할 소스의 standalone production build가 있어야 하며 이 명령은 build하지 않는다. `.env*`를 제외한 독립 실행 사본을 사용하므로 같은 checkout의 후속 build와 섞이지 않는다. `WMS_RECOVERY_RUNTIME`으로 미리 보존한 standalone 사본을 지정하고 `WMS_RECOVERY_PORT`로 3300~3399 사이의 다른 전용 포트를 선택할 수 있다.

운영 드릴만 관리자 연결을 사용해 새 DB·마이그레이션·dump/restore를 준비한다. HTTP 서버는 `.env.local`을 로드하지 않는 별도 임시 실행 디렉터리에서 제한된 `wms_app` 연결로 실행하며 관리자 DB 연결이나 시뮬레이터 DB 연결을 받지 않는다. 실제 일회 초대 수락·로그인·기준정보·100개 수령/검수/적치·외부 주문·담당 배정·예약 40개 확정 뒤 추가 수령 30개의 확정 응답과 별도 외부 사건 접수 응답의 본문을 의도적으로 버린다. 요청/사건 키는 발송 전에 0600 저널에 보존한다.

별도 legacy 창고에서는 정식 전표 API로 입고 60개를 생성·확정하고 실제 원전표와 원장 ID를 기록한다. 전환 API의 원장 대사·스냅샷 확인을 거쳐 S40/Q10/B10으로 개시한 뒤 신규 주문 12개를 예약한다. 복원 후 원전표번호와 원래 legacy 행 전체, 개시 원장 3개 ID, 예약을 비교하고 원래 전환/예약 요청을 다시 보내도 한 번의 결과로 재개되는지 확인한다. 기존 운영 DB의 전표를 변경하지 않는다.

서버를 중지한 처리 경계에서 모든 public 행·정책·RLS 상태·시퀀스 지문을 비교하며 새 DB에 복원한다. 복원 서버에서 같은 세션 쿠키와 저널의 같은 요청/사건 키로 재개해 원확정 결과·버전, 예약 40·담당 작업, 사건 접수 ID를 확인하고 수령 30개의 재고 효과가 1회인지 대사한다. 검증 범위는 응답 본문을 버린 로컬 장애 재현이며 실제 통신망 장애나 제공자 복구를 대신하지 않는다. 성공 시 `docs/v2-recovery-replay-latest.json`에 비밀을 제외한 증거를 저장한다. 실패/미실행을 성공으로 기록하지 않는다.
