# 최신 성능 검증

측정: 2026-10-20T08:04:39.941Z ~ 2026-10-20T08:04:51.925Z

현재 production 빌드에서 원장 10,000건 기준 API 6개·화면 5개 모두 p95 2초 목표를 충족했다. 가장 느린 화면은 확정 이력으로 p95 483.4ms였다. 이 결과는 단일 로컬 순차 측정이며 운영 부하나 다중 사용자 성능을 보장하지 않는다.

## 측정 방법

로컬 `wms_lite`, 기존 앱·마이그레이션 연결과 `DEMO_PASSWORD`, 시스템 Chromium 및 최신 production 빌드가 필요하다. 다른 서버·빌드·검증 작업을 중지한 상태로 실행한다. 비밀 값은 결과에 저장하지 않는다.

```sh
npm run build
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium PERF_EXPLAIN=1 \
  PERF_REPORT_PATH=docs/performance-verification-latest.json npm run test:performance
```

스크립트는 빌드하지 않고 자체 production 서버를 loopback 3200 포트에 시작한다. 전용 임의 테넌트의 품목 100개 × 위치 100개로 전표·명세·원장·잔량·감사 로그 각 10,000행을 만든다. 실제 행 수와 목록 API 전체 건수 및 재고 대사를 확인하고 통계를 갱신한다. 각 대상마다 준비 실행 1회 후 5회 측정하며 p95는 nearest-rank 방식으로 최댓값과 같다. 시드·시작·로그인·통계 갱신·실행계획 진단은 시간에서 제외한다.

브라우저는 전체 페이지 이동부터 실제 표 행 표시와 연속 animation frame 2회까지 측정한다. 재고는 잔량·원장 양쪽 표를 확인한다. 홈은 운영 지표·7일 차트·최근 확정 전표가 표시될 때까지 기다린다. 로그인한 회사가 측정 테넌트와 같은지도 확인한다.

## 확인한 병목과 수정

최초 현재 빌드 측정은 원장 API가 HTTP 503 `RETRYABLE_TRANSACTION`을 반환했다. 실제 앱 역할의 `EXPLAIN ANALYZE`로 원장 조회에서 감사 로그를 행마다 탐색하는 실행계획을 확인했다. 감사 로그 전체 탐색은 10,000회, 매번 제외한 행은 9,999개였고 전체 실행 시간은 8,128.331ms로 앱의 3초 쿼리 제한을 초과했다.

`pagedLedger`는 회사·전표·작업별 최신 작업자를 한 번 계산해 원장과 연결하도록 바꿨다. 원본 확정과 확정 취소의 작업자 구분은 유지했다. 수정 후 동일 규모 진단은 감사 로그 전체 탐색 1회, 실행 50.825ms였다. 진단 연결의 60초 제한은 실행계획 수집에만 적용했으며 앱의 3초 제한은 변경하지 않았다. 쿼리 단위·대시보드 통합 27개 검사와 production 빌드가 통과했다.

모든 측정 완료 후 소유 테넌트 확인을 거쳐 합성 업무·계정 데이터를 삭제했고 자신이 시작한 서버를 종료했다. 실패 진단 실행도 같은 정리를 완료했다. 기존 데모 회사 행은 수정하지 않았다. SQL 진단은 읽기 전용이며 벌크 적재 뒤 통계 갱신은 공유 테이블의 통계에 영향을 준다.

원본 결과와 실행계획은 [performance-verification-latest.json](performance-verification-latest.json)에 보관한다. 기존 [6단계 성능 측정](6단계-성능측정.md)은 과거 측정 기록으로 유지한다.
