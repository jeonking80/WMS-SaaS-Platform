# 최신 앱 직접 운영테스트

기존 공개 주소는 `https://wms-saa-s-platform.vercel.app`이며 최신 운영 화면은 `/dashboard/v2`다. 공개 반영은 DB 업데이트 후 앱 배포 순서로 진행한다. 이 문서는 배포 완료 선언이 아니다.

## DB 연결 준비

현재 Codex에는 Neon 관리자 연결이나 Vercel 관리 인증이 제공되어 있지 않다. 따라서 Neon SQL Editor의 실행만 계정 소유자가 해야 한다. 비밀번호나 연결 문자열을 채팅에 보낼 필요는 없다.

1. Neon에서 기존 `wms-demo` 프로젝트 → SQL Editor → `wms_demo` DB를 선택한다.
2. [업데이트 SQL](../deploy/neon-field-operations.sql) 전체를 한 번 실행한다. GitHub에서는 Raw를 열어 전체 복사한다. 기존 초기화 SQL을 실행하지 않는다.
3. 마지막 결과가 `field_operations_ready = true`, `migrations_applied = 22`, `test_warehouse = 운영테스트 창고`인지 확인한다.

이 파일은 기존 마이그레이션 이력이 올바른지 확인한 뒤 누락된 추가 변경만 적용한다. 기존 계정·비밀번호·전표·재고·원장을 초기화하거나 기존 창고를 전환하지 않는다. 별도 `운영테스트 창고`와 유형별 위치 5개, 테스트 거래처·배송지·품목·바코드를 준비하고 기존 활성 사용자에게 해당 창고 접근 권한을 부여한다. 재실행해도 기존 시험 실적을 덮어쓰지 않는다.

## 앱 배포 후 접속

DB 실행 결과가 확인되면 검증한 앱을 main에 반영해 기존 Vercel 연결로 배포한다. 기존 `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`과 로그인 계정은 유지한다. GitHub Actions는 사용하지 않는다.

1. `https://wms-saa-s-platform.vercel.app/dashboard/v2`로 접속하고 기존 계정으로 로그인한다.
2. 창고에서 **운영테스트 창고**를 선택한다.
3. **입고 작업**에서 거래처 **운영테스트 거래처**, 품목 **운영테스트 품목**으로 입고예정을 등록한다.
4. 수령 → 검수 → 정상 보관 적치를 직접 진행한다. 준비된 위치는 수령·검수대기, 정상 보관, 피킹·포장대기, 출하대기, 품질·과납보류다.
5. **출고 작업**에서 같은 거래처와 **운영테스트 배송지**를 선택해 주문 → 예약 → 피킹 → 포장 → 출하를 진행한다.

실제 스캐너가 없으면 화면의 검색 선택 방식과 확인 사유를 사용한다. 품목 EA 바코드는 `OPS-TEST-ITEM-EA`, 위치 바코드는 `OPS-V2-RECV`, `OPS-V2-STORE`, `OPS-V2-PICK`, `OPS-V2-SHIP`, `OPS-V2-HOLD`다. 승인 업무는 작업자와 다른 승인권자 계정으로 진행한다.

이 환경은 직접 업무를 조작하기 위한 운영테스트 대상이다. 기존 혼잡 시험의 응답 속도·완주 미달 기록은 그대로 유지한다.

## 배포 준비 검증

`node scripts/verify-neon-field-operations.mjs`는 별도 PostgreSQL 17에서 제한된 DB 소유자로 기존 10개 마이그레이션과 합성 데모를 만든 뒤 업데이트한다. 원래 계정·비밀번호·전표·재고·원장의 전체 기존 행 보존, 22개 적용, 재실행 보존, 잘못된 대상/이력 거절, 제한된 앱 권한, 원래 관리자 로그인, 최신 운영 화면과 실제 10개 수령을 확인한다. 외부 Neon/Vercel 실행과는 구분한다.
