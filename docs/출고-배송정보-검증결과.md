# 출고처·배송지 보완 검증

작성일: 2026-10-20 (Asia/Seoul). 출고 확인창의 ‘도착: 없음’이 실제 납품 목적지를 설명하지 못하는 문제를 해결한다. 모든 에이전트는 gpt-6.1-sol을 사용했고 GitHub Actions는 사용하지 않았다.

## 변경

- 새 출고 초안에 받는 거래처·배송지를 필수로 입력한다. 확인창과 전표 상세·확정 이력에도 표시하고 검색할 수 있다.
- 창고 내부 출발/도착 보관위치와 외부 배송지를 구분한다. 입고·이동은 종전 재고 효과를 유지한다.
- 거래처는 앞뒤 공백을 제거한 1~128자, 주소는 1~500자다. 누락·초과·다른 유형의 배송정보는 서버에서도 거절한다.
- 마이그레이션 0007(총 8개)은 nullable 두 필드와 쌍 유효성 제약을 추가한다. 기존 계정·원본 전표·재고는 변경하지 않는다.
- 과거 확정 전표의 미등록 정보는 null로 보존한다. 기존 출고 초안은 정보를 채워 저장한 뒤 확정한다. 과거 성공 멱등 키 재반환과 확정 취소는 계속 동작한다.

## 검증

```sh
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium NEXT_TELEMETRY_DISABLED=1 npm run verify
node scripts/verify-neon-init.mjs
node scripts/verify-neon-init.mjs --upgrade
node scripts/verify-neon-demo.mjs
```

새 단위 테스트 19개는 누락·공백·길이·유형, 직접 서비스 호출, 레거시 초안 차단과 성공 응답 재반환을 검사한다. 새 PostgreSQL 통합 테스트 4개는 저장·수정·상세·검색·회사 격리, 기존 초안 보완, 반대 전표와 원본 정보 유지, DB 제약을 검사한다. 새 브라우저 테스트는 실제 작성·주소 수정·확정 확인창·읽기 전용 이력·역할·다른 회사 차단을 확인한다.

기존 테스트의 유효한 출고 데이터에 배송정보를 추가하고, 선택 상자/텍스트 영역은 접근성 역할로 찾아 옵션·본문 텍스트에 따른 잘못된 대기를 제거했다. 기대 결과나 기존 재고 검증 조건을 완화하지 않았다. 최초 실행에서는 마이그레이션 개수 기대값이 7로 남아 실패해 8로 갱신했다. 브라우저의 구 선택자가 남은 실행을 중단한 뒤 수정본으로 재실행했다.

Neon용 로컬 검증은 슈퍼유저가 아닌 CREATEROLE DB 소유자로 수행했다. 빈 DB의 8개 적용 및 기존 7개 DB의 추가 업그레이드·반복 실행을 통과했고, 과거 출고 JSON에서 새 null 필드를 제외한 값이 그대로임을 확인했다. 원래 제한 앱 계정 권한, 데모 계정 세 역할 로그인과 재고 대조도 통과했다. 사용자 Neon DB에 직접 접속한 것은 아니다.

타입 검사와 프로덕션 빌드는 통과했다. 단위 119개·통합 46개가 통과했고, 브라우저는 전체 실행에서 29개 중 27개가 통과했다. 나머지 P6 두 건은 로그인 요청 제한(429)을 고려하지 않은 테스트와 Next.js 알림까지 함께 찾는 선택자 문제였다. 서버의 Retry-After를 따르도록 하고 오류 문구로 선택자를 한정한 뒤 P6 3개를 다시 실행해 모두 통과했다. 신규 배송정보 시나리오도 별도 실행에서 통과했다. 수정 후 확인한 고유 테스트는 총 194개이며, 수정 후 전체 검증 체인을 한 번 더 실행한 결과로 표현하지 않는다.

## 배포 순서

기존 공개 앱을 유지하기 위해 DB 변경 파일과 설정 도구를 먼저 main에 게시한다. 입력 화면·API의 새 코드는 실제 Neon 추가 SQL의 실행 결과를 확인한 다음 공개 앱에 반영한다. 새 코드는 두 열을 사용하므로 DB 변경 전에 배포하지 않는다.

입력 화면·API와 관련 테스트·문서는 `feat/outbound-delivery` 브랜치에 게시한다. 운영 DB의 추가 작업을 확인한 뒤 main에 반영한다.

사용자는 [추가 SQL](../deploy/neon-outbound-delivery.sql)을 Neon의 wms_demo SQL Editor에서 전체 실행한다. 마지막 결과 delivery_ready=true, delivery_columns=2를 확인한다. 계정 초기화나 기존 데모 시드를 다시 실행할 필요는 없다. 관리자 접속정보는 채팅으로 전달하지 않는다.
