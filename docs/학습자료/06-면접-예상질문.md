# 06. 면접 예상 질문

답변은 **결론 → 이유 → 근거(코드·테스트)** 순서로 짧게 하세요. 아래 답변은 예시이니 본인 말로 바꿔서 연습하세요.

## 1. 1분 자기소개 + 프로젝트 소개 (예시)

> 여러 회사가 함께 쓰는 창고관리 SaaS를 혼자 기획하고 개발했습니다. 처음에는 전표 기반 재고관리 MVP로 시작했고, 이후 입고예정부터 수령·검수·적치, 주문 예약·피킹·포장·출하까지 현장 흐름으로 확장했습니다.
> 가장 신경 쓴 것은 재고가 틀리지 않게 하는 것입니다. 모든 재고 변화를 지울 수 없는 원장에 기록하고, 통신이 끊겨 같은 확정이 두 번 들어와도 한 번만 반영되게 했고, 회사 간 데이터는 DB의 행 수준 보안으로 격리했습니다.
> 마지막으로 오퍼레이터가 한 화면에서 납기 위험·품절 예상·입고 지연을 보고 바로 처리 화면으로 가는 운영 관제와, 자연어로 창고 현황을 물어보는 AI 조회 도우미를 붙였습니다. 테스트는 단위·DB 통합·브라우저를 합쳐 600개가 넘고, 공개 데모로 배포해 두었습니다.

## 2. 3분 시연 순서

1. **운영 관제** (40초): KPI의 빨간 칸(납기 초과) → 조치 필요의 첫 줄 → "열기"로 해당 주문 화면 이동
2. **출고 처리** (60초): "지금 할 일" 안내 → 예약에서 가용재고 비교 → 피킹 스캔(확정 전 할 일 안내가 바뀌는 것 보여주기)
3. **AI 도우미** (40초): "곧 품절될 품목은?" → 답변 아래 "조회: 품절 예측" 표시 → 읽기 전용이라 재고를 바꾸지 않는다는 설명
4. **신뢰성** (40초): 확정 중 연결이 끊기면 "확정 결과 복구"가 뜨는 구조, 원장과 현재고 대사

## 3. 예상 질문과 답변 예시

### 물류·도메인

**Q1. 물류를 원래 알았나요?**
처음엔 몰랐습니다. 그래서 먼저 기획서에 업무 흐름과 예외(과납·미납·파손·부분 출하)를 정리하고 시작했습니다. 실제 현장 경험이 없다는 한계는 알고 있고, 그래서 현장 운영 데이터로 검증하는 단계가 남아 있다고 문서에 명시했습니다.

**Q2. 피킹과 출하 중 언제 재고가 줄어드나요?**
출하 때만 줄어듭니다. 피킹은 보관(S)에서 출하 대기(P)로 상태와 위치만 바꿉니다. 창고 밖으로 나가는 순간에만 총 실물이 줄어야 실사와 장부가 맞습니다.

**Q3. 예약을 왜 따로 두나요?**
여러 주문이 같은 재고를 동시에 가져가는 걸 막고, 부족을 피킹 전에 알기 위해서입니다. 기본은 전체 확보이고, 부족하면 운영자가 "가능 수량만 예약"을 명시적으로 고릅니다.

**Q4. 과납이 오면 어떻게 처리하나요?**
예정 범위는 검수 대기로, 초과분은 사유와 함께 보류로 기록합니다. 기록 자체는 작업자가 할 수 있지만, 정상 재고로 인정하는 건 다른 책임자의 승인이 필요합니다.

**Q5. 쿨스의 CFS 업무와 어떤 관련이 있나요?**
CFS의 반입·분류·반출은 제 프로젝트의 수령·검수·적치, 피킹·포장·출하와 같은 구조입니다. 운영 관제는 현장 상황을 한 화면에 모은다는 점에서 관제·디지털 트윈과 같은 목적입니다. 다만 컨테이너 단위 관리나 항만 일정 연계는 직접 다뤄 보지 않아서 배워야 할 부분입니다.

### 설계·백엔드

**Q6. 멀티테넌시는 어떻게 구현했나요?**
한 DB에 모든 행 `tenant_id`, PostgreSQL RLS로 현재 세션의 회사 행만 보이게 했습니다. 트랜잭션마다 `set_config`로 회사를 설정하고, 앱 DB 계정은 RLS를 우회할 수 없게(`NOBYPASSRLS`) 만들었습니다. 코드에서 WHERE를 빠뜨려도 DB가 막는 이중 방어입니다.

**Q7. 같은 요청이 두 번 오면요?**
화면이 요청마다 UUID를 만들어 먼저 저장하고 보냅니다. 서버는 그 ID와 요청 해시, 응답을 저장해서 같은 ID가 오면 저장한 응답을 돌려주고, 내용이 다르면 거절합니다. 결과를 못 받은 요청은 화면이 "확정 결과 복구"로 같은 ID로만 조회·재전송하게 합니다.

**Q8. 동시에 같은 재고를 예약하면요?**
창고 업무 상태 행을 `FOR UPDATE`로 잠가 같은 창고의 명령을 순서대로 처리합니다. 화면이 보던 버전과 다르면 `VERSION_CONFLICT`로 최신 상태를 다시 보게 합니다.

**Q9. 창고 단위 잠금이면 느리지 않나요?**
맞습니다. 처리량 상한이 있고, 혼잡 시험에서 목표에 못 미친 결과도 숨기지 않고 기록했습니다. 소규모 창고를 대상으로 정합성을 먼저 택했고, 개선한다면 품목·위치 단위 잠금이나 명령 큐로 분리하는 방향을 검토하겠습니다.

**Q10. 원장을 왜 수정 불가로 만들었나요?**
재고 사고가 나면 원인을 추적할 수 있어야 하기 때문입니다. DB 트리거로 UPDATE·DELETE를 막고, 잘못된 실적은 반대 방향 실적으로 정정합니다. 덕분에 감사, 처리량 집계, 품절 예측을 같은 원장에서 바로 계산할 수 있었습니다.

**Q11. 엔진을 순수 함수로 만든 이유는?**
업무 규칙을 DB 없이 빠르게 테스트하기 위해서입니다. "현재 상태 + 명령 → 새 상태 + 원장 행"만 계산하고, DB 쪽(index.ts)은 잠금·멱등 확인·저장·대사만 담당합니다.

**Q12. 테스트는 어떻게 나눴나요?**
업무 규칙은 단위 테스트, 트랜잭션·동시성·RLS는 실제 PostgreSQL 통합 테스트, 화면 흐름은 Playwright로 검사합니다. GitHub Actions 대신 로컬에서 `npm run verify` 한 번으로 전부 돌립니다.

### 프런트엔드·UX

**Q13. "설명 없이 쓰는 화면"을 어떻게 만들었나요?**
업무마다 다음 할 일을 서버 공용 함수로 계산해 "검수할 수량 24 EA"처럼 보여주고, 확정 버튼이 비활성이면 이유를 바로 위에 씁니다. 단계 버튼에는 남은 수량과 완료를 색으로 표시했습니다.

**Q14. 차트 라이브러리를 왜 안 썼나요?**
필요한 차트가 시간대별 막대 4개뿐이라 인라인 SVG로 충분했고, 번들 크기와 의존성을 줄였습니다. 네 계열을 한 차트에 몰지 않고 작은 차트 4개로 나눠 읽기 쉽게 했습니다.

### AI

**Q15. AI 도우미는 어떻게 동작하나요?**
Claude API의 도구 호출을 씁니다. 읽기 전용 도구 7개를 정의해 두면, AI가 질문에 맞는 도구를 고르고, 서버가 사용자 권한으로 계산한 결과를 돌려주고, AI가 그걸 한국어로 요약합니다.

**Q16. AI가 잘못된 정보를 지어내면요?**
수량은 도구 결과에서만 가져오라고 지시했고, 답변 아래에 어떤 조회를 썼는지 표시합니다. 숫자는 관제 화면에서 바로 대조할 수 있습니다.

**Q17. 보안은요?**
쓰기 도구가 없어서 재고를 바꿀 수 없고, 도구는 로그인한 사용자가 이미 볼 수 있는 데이터만 계산합니다. 품목명 같은 사용자 입력은 지시가 아니라 데이터라고 시스템 프롬프트에 명시했습니다. 요청 출처 검사로 다른 사이트에서 비용을 쓰게 하는 것도 막았습니다.

**Q18. API 키가 없거나 장애가 나면요?**
빠른 질문은 같은 도구를 직접 실행해서 답합니다. 관제 화면 자체는 AI와 무관하게 동작합니다.

**Q19. 개발에 AI를 얼마나 썼나요?**
많이 썼습니다. 저는 기획서·개발계획서로 범위와 수락 기준을 정하고, AI 에이전트가 구현하면 테스트와 검증 기록으로 확인하는 방식으로 일했습니다. 그래서 오늘 설명드린 설계 결정은 제가 정하고 검증한 부분입니다. (실제로 설명할 수 있는 만큼만 말하세요.)

**Q20. 품절 예측은 정확한가요?**
단순 가중 평균이라 계절성이나 프로모션은 반영하지 못합니다. 설명 가능성과 최근 변화 반영을 우선했고, 개선한다면 요일 계수와 실제 조달 기간, 예측 대비 실제 오차 추적을 넣겠습니다.

### 협업·태도

**Q21. 가장 어려웠던 점은?**
(본인 경험으로) 예: 결과를 못 받은 확정을 다시 보낼 때 새 요청으로 보내면 이중 반영된다는 걸 알고, 요청 ID를 먼저 저장하는 구조로 바꾼 것.

**Q22. 다시 만든다면 바꿀 것은?**
처음부터 코드 포맷터를 적용하겠습니다. 초기 코드가 압축된 형태라 나중에 정리했습니다. 또 현장 사용자 인터뷰를 더 일찍 했을 것입니다.

**Q23. 테스트가 실패하면 어떻게 하나요?**
원인을 재현한 뒤 고칩니다. 테스트를 끄거나 건너뛰지 않습니다. 성능 목표 미달처럼 바로 못 고치는 건 기록으로 남깁니다.

**Q24. 로우코드 플랫폼(이지빌더)과 이 경험은 어떻게 연결되나요?**
업무 화면을 반복해서 만들며 "목록-상세-단계별 처리-확정" 패턴을 공통 부품(확정 폼, 검색 선택)으로 묶었습니다. 이런 패턴을 설정으로 찍어내는 게 로우코드의 핵심이라고 생각합니다.

**Q25. TMS 쪽 일을 맡으면?**
제 프로젝트는 출하 인계까지가 WMS 범위이고, 이후 배송 상태만 기록합니다. 배차·경로는 새로 배워야 하지만, 상태 전이·멱등·원장 같은 신뢰성 설계는 그대로 적용할 수 있습니다.

### 짧게 답할 기술 질문

**Q26. RLS의 단점은?** 모든 쿼리가 회사 설정 후 실행돼야 하고, 정책이 복잡해지면 성능·디버깅이 어려워집니다.
**Q27. 낙관적 잠금과 비관적 잠금의 차이는?** 낙관적은 버전 비교 후 충돌 시 실패, 비관적은 먼저 잠그고 처리. 이 프로젝트는 창고 행은 비관적, 업무 객체는 버전으로 낙관적.
**Q28. Next.js App Router에서 API는 어디에?** `src/app/api/**/route.ts`의 GET/POST 함수.
**Q29. 왜 Vercel + Neon?** 무료로 공개 데모를 운영하기 위해서. Docker 배포 구성도 따로 둠.
**Q30. 인덱스를 어떻게 정했나?** 조회 패턴 기준. 예: 원장 `(tenant_id, warehouse_id, created_at, id)`는 기간 조회·페이지 넘김용이라 관제 집계에도 그대로 쓰임.
